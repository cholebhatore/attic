Cloud Learning Path

One reference, built level by level, no prior cloud knowledge assumed. Start here, bookmark it, share it — it keeps growing.

How this path is structured

Maybe you've only ever used something like Render's free tier. Maybe you've never deployed anything, anywhere. Either way, you're fine — this path starts from zero and assumes nothing. If you have used Render before: good news, that's an actual cloud platform already, just one that quietly hides almost everything from you. We're about to un-hide it, one layer at a time. No gatekeeping, no "just Google it," no assuming you already know what a region is.

Sequencing: the four Foundations levels are cloud-agnostic theory — concepts that hold up whether you end up on GCP, AWS, both, or something else entirely. From there we go hands-on with GCP first, because its console is friendlier and Cloud Run is a genuinely solid serverless on-ramp. But this is never a GCP-only tour — every technology we introduce gets explained on GCP and AWS side-by-side, since AWS runs most of the industry and you'll need to read it fluently regardless. Once the concepts click on GCP, the AWS track mirrors the exact same levels — you're translating what you already get, not learning cloud a second time from scratch. The last stretch is cloud-agnostic again — the stuff that separates "can deploy a project" from "actually gets production infrastructure."

Every level keeps the same shape: theory → glossary → hands-on → self-check. Theory always comes first — know what you're doing and why before you touch a console.

FOUNDATIONS · LEVEL 01

What is "the cloud", really?

Goal: by the end of this level you can explain, in your own words, what a cloud provider actually sells you, why "serverless" doesn't mean no servers, and where Render, GCP, and AWS each sit on the same underlying spectrum.

1. You've already used a cloud. Render is one.

When you push code to Render, it builds a container image, puts it on a machine somewhere, attaches a URL, restarts it if it crashes, and gives you logs. You never picked a machine size, a region's networking rules, or a disk type — Render decided all of that for you and hid it.

GCP and AWS sell the exact same underlying thing — computers, storage, and networking, sitting in enormous buildings called data centers, that you rent by the second instead of buying outright. The difference is how many of the decisions they make for you versus leave to you. That single idea — where a service sits on the "decisions made for you" spectrum — is the most important mental model in this entire path. Almost every cloud concept you'll learn is really just "where does this sit on that spectrum, and what do I gain or give up by moving along it."

Anchor analogy Think of it like transport, not tech: owning a car (you maintain everything) → renting a car (someone else maintains it, you still drive) → taking a taxi (you just state a destination) → public transit (fixed route, cheapest, least control). Buying physical servers is "owning a car." A raw cloud VM is "renting a car." A platform like Cloud Run or Render is "taking a taxi." A fully managed SaaS tool is "public transit." Nothing here is objectively best — the right choice depends on how much control you actually need for the trip.

2. The four service models

Every cloud service you'll ever touch falls into one of four buckets, defined purely by who manages what:

Model You manage Provider manages Example
IaaS
Infrastructure as a Service		 OS, runtime, app, scaling, patching Physical hardware, virtualization, network, power GCP Compute Engine, AWS EC2
PaaS
Platform as a Service		 Your application code OS, runtime, patching, scaling infrastructure Render, GCP App Engine, AWS Elastic Beanstalk
FaaS / Serverless
Function/Container as a Service		 A single function or request-handler's code Everything else, including scaling to exactly zero GCP Cloud Run & Cloud Functions, AWS Lambda
SaaS
Software as a Service		 Your data/configuration only The entire application Gmail, Notion, GitHub itself
Where you've already been Render sits in PaaS, closer to FaaS on its free tier (your service can idle/sleep, similar in spirit to scale-to-zero). This path takes you one level "down" the stack first — into IaaS with raw VMs — so you understand what PaaS/FaaS is automating away, before bringing you back "up" into GCP's PaaS/FaaS tools like Cloud Run with full understanding of what's happening underneath.

3. Same app, three different deploys

Theory sticks a lot better once you can picture it as one concrete thing happening three different ways. Say you've built a small Node.js/Express API — the kind of thing you'd currently just push straight to Render.

The same app, at every layer of the stack
  • IaaS route — AWS EC2 / GCP Compute Engine: you provision a virtual machine, SSH into it, install Node yourself, pull your code, run it with something like pm2 so it survives a reboot, and open a firewall port. Nothing gets fixed silently — if the process dies at 3am, it stays dead until you notice and SSH back in. Maximum control, maximum responsibility.
  • PaaS route — Render / AWS Elastic Beanstalk / GCP App Engine: you push code or a Dockerfile, and the platform builds it, runs it, restarts it on crash, and hands you a URL. You never see the underlying VM at all. This is exactly where Render already had you.
  • Serverless route — AWS Lambda / GCP Cloud Run: your Express app gets wrapped so each incoming request spins up (or reuses) a lightweight instance, handles it, and can disappear completely once traffic stops. Cloud Run is the friendlier version of this for a beginner because it just runs a normal Docker container — same app, no code rewrite — whereas Lambda historically wanted your code in a specific handler shape (it supports containers now too, but the ergonomics still lean more "function" than "app").

Same couple hundred lines of Express code, three completely different operational realities — who patches the OS, who restarts a crash, who decides if you pay for idle time. This is exactly the spectrum from section 1, just applied to one real app instead of talked about in the abstract. We'll actually run this deploy for real — GCP first, then the AWS equivalent — starting around Level 2 and 5.

4. Serverless doesn't mean "no servers"

This is the single most misleading term in cloud computing, and you asked about it directly, so let's be precise. There are absolutely still servers. "Serverless" means you never provision, size, patch, or manage the server — the provider allocates one to run your code only when a request arrives, and reclaims it when there's no traffic.

  • Scale to zero: if nobody's using your app, you can run (and pay) literally nothing.
  • Pay-per-use: billing is usually per-request and per-100ms of compute, not per-hour-the-machine-existed.
  • Statelessness: your code shouldn't assume anything saved to local disk will still be there next time it runs — the "server" underneath may be a completely different physical machine on the next request.
  • Cold starts: the trade-off for scaling to zero — the very first request after idling has to wait for a fresh instance to boot, which can add noticeable latency.
Common beginner confusion "Serverless" (Cloud Run, Lambda) and "PaaS" (Render, App Engine) overlap a lot in practice, and providers blur the marketing on purpose. The technical distinction that actually matters: true serverless platforms scale to zero and bill per-request; classic PaaS often keeps at least one instance warm and bills per-time-running. You'll feel this difference directly once you deploy on both.

5. Building blocks you'll keep hearing

Region
A specific geographic area with its own cluster of data centers (e.g. asia-south1 = Mumbai, on GCP). You pick a region to keep your app physically close to your users, for latency and legal/data-residency reasons.
Zone / Availability Zone
A region is split into multiple isolated zones (separate power, cooling, networking) so a failure in one doesn't take down the whole region. Spreading resources across zones is how you get resilience without a second region.
Resource hierarchy
How a cloud account organizes everything you create. On GCP it's Organization → Folder → Project → Resources; every single thing — a VM, a bucket, a Cloud Run service — lives inside exactly one Project. AWS's version is Organization → Organizational Unit → Account → Resources — the Account plays the same role GCP's Project does, just one level "bigger" (AWS accounts often hold more than a GCP project would).
IAM (Identity and Access Management)
The system that decides who (a person, or a service acting on its own) can do what to which resource. Both clouds call this exact concept "IAM" — GCP attaches permissions via roles on a resource, AWS via JSON policy documents attached to users/roles. Same job, different syntax. You'll go deep on this in Level 6/11 — for now, just know every action in the cloud is checked against an IAM policy first.
Managed vs. unmanaged
"Managed" means the provider handles operational upkeep (patching, backups, failover) for you, for a price premium. A self-hosted Postgres on a VM is unmanaged; GCP Cloud SQL and AWS RDS are both managed equivalents for the exact same job. This is the same spectrum from section 1, applied to a single service.
SLA (Service Level Agreement)
A contractual uptime promise (e.g. "99.95% available per month"), with credits owed to you if the provider misses it. A good habit: whenever you pick a service, glance at its SLA — it tells you how much the provider is willing to bet on it.

6. Why anyone uses cloud instead of buying their own servers

  • Elasticity — scale from 1 user to 1 million and back down, without ever buying hardware.
  • Capex → Opex — no large upfront hardware purchase (capital expense); you pay ongoing, variable operating expense instead, which is why cloud bills scale with your traffic.
  • Global reach — deploying "closer" to users in another continent is a config change, not a construction project.
  • Managed services — you get a production-grade database, queue, or cache without becoming a database administrator.
  • The honest trade-off: at very large, steady, predictable scale, owning hardware can be cheaper — this is why some giant companies run hybrid or their own data centers. For a beginner-to-mid-size project, this almost never applies to you yet, but it's worth knowing the "cloud is always cheaper" claim isn't universally true.

FOUNDATIONS · LEVEL 02

Compute: VMs → containers → serverless

Goal: by the end of this level you can explain what a VM actually is under the hood, why a container isn't just "a smaller VM," which AWS service is the real equivalent of GCP Cloud Run (it's not what most tutorials tell you), and you'll have manually run a Node app on a raw VM at least once — so every abstraction after this feels earned, not magic.

1. Zooming into one slice of the stack

Level 1 covered the whole spectrum at a high level — IaaS, PaaS, FaaS, SaaS. This level zooms into just compute: the layer that actually executes your code. Everything below is still that same spectrum, just examined up close, with your hands actually on a keyboard by the end of it.

2. Virtual machines: renting a full computer

A VM is a slice of a real physical machine, carved out by software called a hypervisor, that behaves like its own independent computer — own OS, own kernel, own disk, own IP. Underneath, dozens of VMs share one physical box, but from inside your VM you can't tell, and you're not supposed to be able to.

When you create one, you pick two things: a machine type (how much CPU/RAM) and a boot image (which OS, pre-installed). GCP calls the OS template an image; AWS calls it an AMI (Amazon Machine Image) — same concept, different name, and worth memorizing because "AMI" shows up constantly in AWS docs.

Concept GCP (Compute Engine) AWS (EC2)
Smallest free-tier-friendly size e2-micro t2.micro / t3.micro
General machine families e2, n2, c2, m1... t, m, c, r...
OS template Image AMI (Amazon Machine Image)
Attached storage Persistent Disk EBS (Elastic Block Store)
Anchor analogy A hypervisor is like a landlord who's converted one big house into several fully separate flats — each tenant (VM) has their own locked front door, own kitchen, own everything, and genuinely can't tell there's another flat on the other side of the wall. The building (physical server) is shared; the living experience is not.

3. Containers: a lighter unit than a VM

A container is not a smaller VM, even though tutorials often gloss over this. A VM virtualizes hardware and runs a whole separate kernel. A container shares the host machine's kernel and just gets an isolated view of processes, filesystem, and network (using Linux features called namespaces and cgroups) — it only packages your app plus its exact dependencies, not an entire OS.

  • Startup: a VM boots in tens of seconds to minutes (it's booting a whole OS); a container starts in milliseconds to a couple seconds.
  • Density: you can pack far more containers than VMs onto the same hardware, since there's no duplicated OS overhead per unit.
  • Portability: a container image runs identically on your laptop, a teammate's laptop, and production — "works on my machine" stops being a meaningful complaint.

A container image is the packaged, frozen blueprint (your code + runtime + dependencies); a container is that image actually running. You build an image once (usually from a Dockerfile) and push it to a container registry so any platform can pull and run it: GCP's is Artifact Registry, AWS's is ECR (Elastic Container Registry).

Common beginner confusion A "VM image/AMI" and a "container image" are two completely different things that just happen to share the word "image." A VM image contains an entire operating system. A container image contains only your app and its dependencies, and relies on whatever machine runs it to already have a compatible kernel. Don't mix them up in your head — they solve the same-sounding problem ("package something to run elsewhere") at completely different layers.

4. Serverless compute: two different flavors, not one

This is the part almost every "GCP vs AWS" comparison article gets slightly wrong, so let's be precise. Serverless compute actually splits into two distinct families, and each cloud has an answer for both:

  • Serverless functions — a single function, triggered by an event (HTTP request, file upload, message on a queue), that runs briefly and exits. GCP Cloud Functions and AWS Lambda are the direct equivalents of each other here.
  • Serverless containers — you bring a whole Docker container (any language, any framework, long-lived HTTP server), and the platform runs it, scales it, and can scale it to zero. GCP Cloud Run is squarely in this bucket. AWS actually has two answers: AWS App Runner, which is the closest experience to Cloud Run (push a container or connect a repo, get a URL, done), and AWS Fargate, the serverless compute engine underneath ECS or EKS — more powerful and more knobs, but you're also setting up a cluster/service/task definition around it rather than just deploying a container directly.

So: if someone says "what's the AWS version of Cloud Run," the honest answer is "App Runner is the closest UX match, Fargate is the closest architectural match" — not a single clean 1:1, which is exactly the kind of nuance that's easy to miss from surface-level comparisons.

Layer GCP AWS
IaaS — full VM Compute Engine EC2
Serverless containers (Render-like) Cloud Run App Runner (simple) / Fargate via ECS or EKS (more control)
Serverless functions Cloud Functions Lambda
Container registry Artifact Registry ECR
VM autoscaling group Managed Instance Group (MIG) Auto Scaling Group (ASG)

5. Choosing the right compute for the job

  • Need full OS-level control, or software that must run continuously and stateful in a specific way (e.g. a game server, a custom daemon): VM — Compute Engine / EC2.
  • Have a containerized HTTP app, want it to autoscale (including to zero) without managing servers: Cloud Run / App Runner.
  • Small, event-triggered piece of logic — resize an uploaded image, respond to a queue message, glue two services together: Cloud Functions / Lambda.
  • Multiple interdependent containers at real scale, needing fine-grained orchestration: this is Kubernetes territory (GKE / EKS) — a later level, just noting it exists so the map stays complete.
Hands-on for this level

Goal: manually run a tiny Node.js server on a raw VM, so you feel exactly what Cloud Run/App Runner will later do for you automatically.

  1. In the GCP console, go to Compute Engine → VM instances → Create Instance. Choose e2-micro, keep the default Debian/Ubuntu image, and pick a free-tier-eligible region (currently us-west1, us-central1, or us-east1 — check cloud.google.com/free for the current list, it does shift over time).
  2. Once it's running, click SSH next to the instance — this opens a terminal straight in your browser, no key pair setup needed.
  3. Install Node: sudo apt update && sudo apt install -y nodejs npm
  4. Write a one-file server: nano server.js, paste a minimal http.createServer that responds "hello from a real VM," save, then run node server.js.
  5. In a second SSH tab, run curl localhost:3000 (or whatever port you used) and watch your own request hit code you're running on a machine you provisioned yourself.
  6. Stop the VM when you're done (or delete it) so it doesn't sit there burning free-tier hours.
  7. Optional parallel step: do the same on AWS — launch a t2.micro EC2 instance, notice you now have to explicitly create/download a key pair and open port 22 (and 3000) in a Security Group before you can even SSH in. GCP quietly handles both of those for you by default; AWS makes you do it explicitly. Neither is "wrong" — it's a real difference in how much is decided for you, straight out of Level 1's spectrum.

Storage & databases

Goal: know exactly which storage type to reach for (object, block, or file) and which database family fits a given data shape — and spot the one classic beginner trap: spinning up a managed SQL database and getting a surprise bill, because unlike Compute Engine or Cloud Storage, it has no always-free tier.

1. Why this matters right after "serverless"

You just learned Cloud Run/Lambda instances are stateless and disposable — anything they write to local disk can vanish the moment that instance recycles. So where does data actually live? That's this entire level. Storage and compute are deliberately separate concerns in cloud architecture, and understanding that separation is what makes the rest of this path click.

2. Three shapes of storage

"Storage" isn't one thing — it's three genuinely different products, each shaped for a different access pattern:

Object storage
A flat store of files ("objects"), each addressed by a key/URL, with no real folder structure underneath (folders in the console UI are cosmetic). Built for huge scale, cheap storage of things like images, videos, backups, and datasets — not for a database or a filesystem your app edits in place. GCP: Cloud Storage. AWS: S3.
Block storage
A raw virtual disk attached to exactly one VM at a time, formatted with a normal filesystem (ext4, NTFS...). This is what your VM's boot disk and any extra attached drives actually are. GCP: Persistent Disk. AWS: EBS (Elastic Block Store).
File storage
A shared network filesystem multiple VMs can mount and read/write at once (via NFS), useful when several machines need to see the same files live. GCP: Filestore. AWS: EFS (Elastic File System).
Anchor analogy Object storage is a warehouse with a single barcode per box — you don't browse shelves, you scan a code and it's retrieved. Block storage is a filing cabinet bolted to one specific desk (VM) — only that desk's owner uses it. File storage is a shared office cabinet with one key copied for the whole team — several desks can open it at once.

3. Databases: matching the shape of your data

Beyond raw storage, you'll almost always need a proper database. The first real fork in the road is relational vs. NoSQL, and it's about the shape of your data and how you'll query it, not which one is "more modern."

Type Best for GCP AWS
Managed relational (SQL) Structured data with relationships, joins, transactions — orders, users, invoices Cloud SQL (Postgres/MySQL/SQL Server) RDS (Postgres/MySQL/SQL Server/etc.)
Globally-distributed relational Relational data at massive, multi-region scale Cloud Spanner Aurora (with Global Database)
NoSQL document/key-value Simple, high-throughput lookups by key — sessions, user profiles, flexible schemas Firestore DynamoDB
In-memory cache Sub-millisecond reads for hot data — rate limits, leaderboards, session caching Memorystore (Redis) ElastiCache (Redis/Memcached)

The practical rule of thumb: if you're picturing tables with foreign keys and you'll want to ask questions like "all orders for this user, joined with product names" — relational. If you're picturing "give me this one document by its ID, fast, at huge scale, and I don't care about joins" — NoSQL.

The trap almost every beginner falls into Compute Engine's e2-micro and Cloud Storage both have genuine always-free quotas — you can leave them running and pay nothing. Cloud SQL and RDS do not. Even the smallest managed SQL instance bills by the hour from the moment it exists, free trial credit aside. It's easy to spin one up "just to try it" and forget about it. For this level's hands-on, we're deliberately using Firestore/DynamoDB instead — both have real always-free tiers — and we'll come back to Cloud SQL/RDS later with explicit cost guardrails once you're ready to budget for it.

4. Consistency and durability, briefly

Two words you'll see constantly in docs, worth knowing precisely rather than glossing over:

  • Durability — the odds your data survives hardware failure. Object storage like GCS/S3 is designed for extreme durability (often quoted as "eleven nines") by silently keeping multiple copies across different hardware.
  • Consistency — whether a read immediately after a write is guaranteed to see that write. Strong consistency means yes, always. Eventual consistency means usually, but there can be a brief window where different readers see slightly stale data. Object storage historically leaned eventual (both GCS and S3 now offer strong read-after-write consistency for most operations, a relatively recent improvement worth knowing since a lot of older articles still describe the old eventual-consistency behavior).
Hands-on for this level
  1. In the GCP console, go to Cloud Storage → Buckets → Create. Make a bucket with a globally-unique name, default settings are fine. Upload any small file from your computer.
  2. Click the uploaded file and note its public URL structure — try making it public (or generate a signed URL) and open that link in a private browser tab to confirm it actually serves the file.
  3. Go to Firestore → Create Database (choose Native mode, any region). Manually add a collection (e.g. notes) and one document with a couple of fields (e.g. title: "hello", done: false) straight from the console UI.
  4. Refresh and confirm the document is really there — that's the entire mental model of a document database: no schema to define up front, no migration, just a document with fields.
  5. Optional parallel step: do the S3 + DynamoDB equivalents on AWS — create an S3 bucket and upload the same file, then create a DynamoDB table and manually add one item via the console. Compare how much more setup DynamoDB's console asks for upfront (a table needs a defined partition key, even though the document body itself stays schemaless) versus Firestore's more improvisational feel.

Glossary

Object / Blob
A single file stored in object storage, addressed by a unique key.
Partition key
The field DynamoDB (and similar systems) uses to decide which physical partition stores a given item — chosen up front when you create the table.
Durability
The probability your stored data survives underlying hardware failure over time.
Consistency (strong vs. eventual)
Whether a read immediately after a write is guaranteed to reflect that write (strong), or might briefly return stale data (eventual).
Schema-on-write vs. schema-on-read
Relational databases enforce a schema when data is written (schema-on-write). Many NoSQL stores let you write whatever shape you want and only care about structure when you read it back (schema-on-read).

Networking & IAM basics

Goal: understand how your resources talk to each other privately, how traffic gets routed in from the internet, and who's allowed to do what to what — enough to reason about a real architecture diagram. This is "basics" on purpose; full IAM policy-writing depth is its own later level.

1. The private network you don't see yet

Every VM, container, and managed service you've created so far has actually been sitting inside a private virtual network the whole time, provisioned automatically with sensible defaults. This level makes that network visible and explains the vocabulary.

2. VPC and subnets

A VPC (Virtual Private Cloud) is your own isolated slice of network — private IP ranges, routing, and rules — that only your resources live inside. Both clouds literally use the same term, "VPC," which is rare and convenient. The genuinely different part is subnets:

  • GCP subnets are regional — one subnet automatically spans every zone in a region, so a VM in any zone of that region can use it.
  • AWS subnets are zonal — one subnet lives in exactly one Availability Zone, so a multi-zone AWS setup needs a separate subnet per zone by design.

This trips people up constantly when translating AWS diagrams to GCP or vice versa — it's a real architectural difference, not just naming.

3. Controlling traffic: firewalls, security groups, and NACLs

Concept GCP AWS
Instance/service-level traffic rules Firewall rules (VPC-level, apply via tags or service accounts) Security Groups (stateful, attached to instances/interfaces)
Subnet-level traffic rules — (no separate layer; firewall rules cover it) Network ACLs (stateless, attached to the subnet itself)

AWS genuinely has two layers here — Security Groups and Network ACLs — while GCP handles it with one: firewall rules attached at the VPC level. Neither approach is more "correct"; AWS's extra layer gives you a coarser subnet-wide backstop, GCP's single layer is simpler to reason about.

4. Load balancing

A load balancer sits in front of multiple instances of your app and spreads traffic across them. Here's a real, easy-to-miss difference: GCP's load balancer is global by default — one anycast IP address automatically routes users to your nearest healthy region. AWS load balancers are regional — an Application Load Balancer (L7, understands HTTP) or Network Load Balancer (L4, raw TCP/UDP) lives in one region, and going truly global needs an extra product layered on top (CloudFront or Global Accelerator).

5. DNS — you already know most of this

Given the DNS resolution chain, record types, and Route 53 routing policies you've already worked through, this needs less explaining than the rest: GCP Cloud DNS is the direct equivalent of AWS Route 53 — a managed, authoritative DNS host you point your domain's nameservers at, which then resolves your friendly domain to whatever's in front of your Cloud Run service, load balancer, or VM.

6. IAM basics: principals, roles, and a real difference in mental model

Both clouds answer the same question — who can do what to which resource — but structure the answer differently:

Principal
Anything that can be granted permissions: a human user, a group, or a non-human identity acting on behalf of a running service.
Service account (GCP) vs. IAM Role (AWS)
This is the real mental-model difference. On GCP, a service account is a first-class identity with its own email-like address — you create it once and attach it to whatever resource needs it (a VM, a Cloud Run service). On AWS, an IAM Role isn't really a standing identity — it's more like a costume: a resource "assumes" the role temporarily to borrow its permissions, and there's no persistent account behind it the way there is with a GCP service account.
Role / Policy
A named bundle of permissions. GCP: predefined roles (e.g. Storage Object Viewer) or custom roles you build yourself. AWS: managed policies (AWS-authored or your own customer-managed ones) or inline policies attached directly to a role.
Principle of least privilege
Grant the smallest set of permissions that lets something do its job, nothing more — the single most important habit in cloud security, and the one beginners skip most often by reaching for broad "Editor"/"Admin" roles out of convenience.
Worked example Say your Cloud Run service needs to read files from the bucket you made in Level 3. On GCP: create a service account, grant it the Storage Object Viewer role scoped to that bucket, then attach that service account to the Cloud Run service — it can now read the bucket and nothing else. On AWS: create an IAM Role with a policy granting s3:GetObject on that bucket's ARN, then attach the role to your Lambda function or Fargate task — same outcome, same underlying principle, different plumbing.
Hands-on for this level
  1. In the GCP console, go to VPC network → Firewall and look at the rules that already exist on your default network (usually default-allow-internal, default-allow-ssh). You didn't create these — GCP did, when your project was born. Read what each one actually allows.
  2. Go to IAM & Admin → Service Accounts → Create Service Account. Create one called something like bucket-reader.
  3. Go back to your Level 3 Cloud Storage bucket → Permissions → grant that new service account the Storage Object Viewer role, scoped to just this bucket.
  4. If you still have your Level 2 VM running: attach that service account to it (Compute Engine lets you change this from the instance's settings while it's stopped), restart it, SSH back in, and run gsutil cat gs://your-bucket-name/your-file — no keys, no passwords, just an identity the VM was handed. This is the exact mechanism Cloud Run will use in Level 5.
  5. Optional parallel step: on AWS, create an IAM Role with an S3 read policy scoped to your Level 3 bucket, and attach it as an "instance profile" to your EC2 instance to do the same thing with the AWS CLI's aws s3 cp.

Deploy your first Cloud Run service

Goal: take your Level 2 raw-VM Node app and actually deploy it to Cloud Run for real — source code to public HTTPS URL — and understand every step in between, including the two different ways to get there and what each config knob controls.

1. The anatomy of a deploy

Every Cloud Run deploy, no matter how you trigger it, goes through the same pipeline: your source code → a container image → a container registry → Cloud Run pulls and runs it → you get a URL. Levels 2–4 explained each piece separately (containers, storage, IAM); this level wires them into one working path.

2. Writing a Dockerfile — the blueprint for your image

A Dockerfile is a short recipe telling Docker how to build your container image, line by line. For a small Node app it's genuinely short: 

FROM node:20-slim
WORKDIR /app
COPY package*.json ./
RUN npm install --production
COPY . .
ENV PORT=8080
EXPOSE 8080
CMD ["node", "server.js"]

Read it top to bottom exactly as it executes: start from a base image with Node already installed, set a working directory, copy just the dependency manifest first and install (so Docker can cache this expensive step separately from your actual code), copy the rest of your code in, and declare the command that runs when a container starts. Cloud Run expects your app to listen on the port in the PORT environment variable (it defaults to 8080) — this one convention trips up almost every beginner's first deploy, so bake it in from the start: app.listen(process.env.PORT || 8080).

3. Two ways to get to a deployed service

Method What happens When to use it
Source deploy
gcloud run deploy --source . 		Cloud Build automatically detects your language and builds a container for you using Buildpacks — no Dockerfile required at all. Fastest path for a straightforward app; great for this level's hands-on.
Image deploy
build → push → gcloud run deploy --image 		You explicitly build the image from your own Dockerfile, push it to Artifact Registry, then point Cloud Run at that exact image. Whenever you need control the Dockerfile gives you — custom base images, specific build steps, reproducible builds.

Buildpacks (used by source deploy) are a genuinely useful beginner on-ramp, but understanding the Dockerfile path matters because it's what CI/CD pipelines almost always use in practice — that's exactly what Level 7 builds on.

4. The config knobs that actually matter

Concurrency
How many simultaneous requests one container instance will handle before Cloud Run spins up another. Higher concurrency = fewer instances = cheaper, but only works if your app doesn't choke under parallel load.
Min / max instances
Min instances above 0 keeps at least that many warm, eliminating cold starts for those — at the cost of paying for idle capacity, which quietly breaks the "scale to zero" benefit from Level 1/2. Max instances caps runaway scaling (and runaway cost) during a traffic spike or bug.
Memory / CPU allocation
Set per revision, same idea as picking a VM's machine type, just scoped to one container instance instead of a whole machine.
Request timeout
How long Cloud Run waits for your app to respond before giving up — matters for anything slow like a big file upload or a long-running computation.

5. Secrets and custom domains, briefly

Never bake a real secret (API key, DB password) directly into your image or a plain environment variable — reference it from Secret Manager instead, so it's fetched at runtime and access is controlled by IAM (this gets a full hands-on in Level 6). For a custom domain instead of the auto-generated *.run.app URL, Cloud Run supports direct domain mapping — you already know DNS well from before, so this is just "point a CNAME/A record at what Cloud Run tells you," nothing new conceptually.

6. The same deploy on AWS

This is where the asymmetry from Level 2 becomes very concrete. Deploying the identical containerized app looks meaningfully different depending which AWS service you pick:

Running it Automatic Automatic Create a Cluster and a Service (desired count, load balancer attachment) yourself
Public URL Given automatically Given automatically You wire up an Application Load Balancer yourself

App Runner is genuinely the closer match in day-to-day experience — a handful of clicks or one CLI command, no cluster to think about. Fargate gives you real orchestration primitives (useful once you need multiple interdependent services), but you're assembling infrastructure Cloud Run and App Runner both hide from you by design.

  2. From Cloud Shell or your local terminal with gcloud authenticated, run: gcloud run deploy my-first-service --source . --region us-central1 --allow-unauthenticated
  3. Watch the output — it builds, pushes to Artifact Registry automatically, and prints a live https://...run.app URL. Open it, or curl it.
  4. In the console, open your service's Revisions tab and try changing min instances from 0 to 1, redeploy, and compare how fast the very first request feels afterward versus before (cold start vs. always-warm).
  5. Optional parallel step: push the same image to ECR (aws ecr commands) and deploy it via App Runner, pointing it at that image — compare how many steps it took versus the single gcloud run deploy command.

IAM & security deep dive

Goal: go past Level 4's "attach a role" basics into how IAM policies are actually structured and evaluated, how to avoid the classic mistakes (long-lived keys, overly broad roles), and the equivalent hardening patterns on AWS — precise enough that you could review someone else's IAM setup and spot a real problem.

1. What a policy actually is

On GCP, an IAM policy is a set of bindings — each one pairs a role with the members who hold it — attached to a resource. Policies are inherited down the resource hierarchy from Level 1: a binding on an Organization applies to every Folder, Project, and resource underneath it, unless something more specific overrides it. GCP is, by default, allow-only — if no binding grants an action, it's denied by default; explicit Deny policies exist but are a newer, less commonly reached-for feature.

On AWS, a policy is a JSON document with an Effect (Allow or Deny), one or more Actions, a Resource, and optional Conditions — attached either to an identity (user/group/role) or, for some services, directly to the resource itself (an S3 bucket policy, for instance). AWS evaluates every applicable policy together, and an explicit Deny always wins, no matter how many Allows exist elsewhere. That's a real structural difference from GCP's model, and it matters: on AWS you can safely bolt on a hard Deny as a backstop; on GCP the more common pattern is simply not granting the broader role in the first place.

2. Custom roles vs. predefined convenience

Predefined roles (GCP) and AWS-managed policies (AWS) are convenient but almost always broader than one specific app actually needs — Storage Object Viewer lets something read every object in a bucket, even if your app only ever touches one folder's worth of files. A custom role (GCP) or customer-managed policy (AWS) lets you bundle only the exact permissions the job requires. This is more setup upfront and is exactly what real least-privilege design looks like in practice, not just the phrase from Level 4.

3. The single most common real-world mistake: static keys

Why downloaded keys are a liability A downloaded GCP service account JSON key, or an AWS IAM user's access key pair, is a long-lived secret that works from anywhere, forever, until someone manually revokes it — and they leak constantly (committed to Git by accident, pasted into a support ticket, left in a CI log). The fix on both clouds is the same principle: never create one if you can avoid it. For anything running inside the cloud (a VM, Cloud Run, Lambda, Fargate task), attach the identity directly — exactly what you did in Level 4's hands-on — so credentials are short-lived and automatically rotated behind the scenes. For anything running outside the cloud that still needs access (most commonly, a CI/CD pipeline like GitHub Actions), use Workload Identity Federation (GCP) or an OIDC-based IAM Role (AWS) — both let an external system prove its identity and receive short-lived temporary credentials, with zero long-lived keys ever created or stored.

4. Secrets management

Passwords, API keys, and tokens your app needs at runtime belong in a dedicated secrets service, not in code or plain environment variables: Secret Manager (GCP) or AWS Secrets Manager / Systems Manager Parameter Store (AWS, which genuinely has two overlapping options — Secrets Manager adds automatic rotation and costs more per secret, Parameter Store is cheaper/simpler and fine for values that don't need rotation). Access to a given secret is itself controlled by IAM, so you grant only the specific service account/role that needs it — the same least-privilege habit, applied to data instead of infrastructure.

5. Guardrails above the project level

Concept GCP AWS
Fine-grained conditional access IAM Conditions (e.g. time-bound, resource-tag-based grants) Policy Condition blocks (e.g. restrict by source IP, require MFA)
Ceiling on what a role can ever be granted — (closest analog: scoping custom roles tightly from the start) Permission Boundaries — caps what an IAM entity's own policies can grant, even if someone attaches something broader later
Org-wide guardrails Organization Policy Service (e.g. "no public buckets anywhere in this org") Service Control Policies (SCPs) — same idea, enforced at the AWS Organizations level
Who-did-what audit trail Cloud Audit Logs CloudTrail

Permission Boundaries are a genuinely AWS-specific concept worth remembering by name — they're how larger AWS orgs safely let a team create their own IAM roles without risking someone accidentally grants themselves admin.

Hands-on for this level
  1. Go to IAM & Admin → Roles → Create Role. Build a custom role containing only storage.objects.get and storage.objects.list — nothing else — and name it something like bucket-reader-minimal.
  2. Revoke the predefined Storage Object Viewer role you granted in Level 4's hands-on from that service account, and grant this new custom role instead, scoped to the same single bucket. Re-run the gsutil cat command from Level 4 to confirm it still works with a strictly narrower grant.
  3. Go to Secret Manager → Create Secret, store a fake value (e.g. demo-api-key-12345). Grant your Level 5 Cloud Run service's service account the Secret Manager Secret Accessor role, scoped to just this one secret.
  4. Redeploy your Level 5 Cloud Run service, this time referencing the secret as an environment variable sourced from Secret Manager (the --set-secrets flag on gcloud run deploy) instead of a plain --set-env-vars value — confirm your app can still read it.
  5. Optional parallel step: on AWS, write a customer-managed policy scoped to only s3:GetObject on your specific bucket ARN, and store a secret in Secrets Manager, granting your Fargate task role access to retrieve it.

Glossary

Binding
A GCP IAM pairing of one role with the members who hold it, attached to a specific resource.
Explicit Deny
An AWS policy statement with "Effect": "Deny" that overrides any Allow, no matter where else it's granted.
Workload Identity Federation
A way for an external system (like a CI pipeline) to exchange its own identity for short-lived GCP credentials, with no long-lived key ever created.
Permission Boundary
An AWS-specific ceiling on the maximum permissions an identity's policies can ever grant, regardless of what's attached later.
Org Policy / Service Control Policy (SCP)
An organization-wide guardrail restricting what's possible at all, beneath any individual IAM grant — GCP: Org Policy, AWS: SCP.

CI/CD with Cloud Build

Goal: stop manually typing gcloud run deploy — set up a real pipeline that builds, tests, and redeploys automatically on every push, and understand why AWS splits this into three products where GCP mostly uses one.

1. Why automate the deploy step

Every deploy so far has meant you, personally, typing a command. That's fine for learning, fragile for anything real — someone forgets a step, deploys the wrong branch, or just doesn't bother deploying a small fix. CI/CD replaces "a human runs a command" with "a pipeline runs the same steps identically, every single time, triggered automatically."

2. Core concepts, before any specific tool

Continuous Integration (CI)
Automatically build (and ideally test) your code on every push or pull request, catching breakage immediately instead of at deploy time.
Continuous Delivery / Deployment (CD)
Automatically ship the resulting build to an environment — delivery means it's ready to release with a manual approval step; deployment means it goes live with no human in the loop at all.
Pipeline
The ordered sequence of stages a change moves through: source → build → test → push artifact → deploy.
Trigger
What starts a pipeline run — a push to a branch, a pull request, a new tag, a schedule, or a manual click.

3. Cloud Build: GCP's answer

Cloud Build runs a pipeline defined in a cloudbuild.yaml file sitting in your repo — each step is literally a container image running one command. A minimal pipeline for your Level 5 app looks like this: 

steps:
  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'us-central1-docker.pkg.dev/PROJECT/repo/my-app', '.']
  - name: 'gcr.io/cloud-builders/docker'
    args: ['push', 'us-central1-docker.pkg.dev/PROJECT/repo/my-app']
  - name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
    entrypoint: gcloud
    args: ['run', 'deploy', 'my-first-service', '--image', 'us-central1-docker.pkg.dev/PROJECT/repo/my-app', '--region', 'us-central1']

A Build Trigger connects this file to your GitHub repo, so a push to main runs exactly these three steps with no one typing anything.

4. AWS's answer: three products, not one

This is a genuine, worth-remembering asymmetry — what Cloud Build does in a single product, AWS deliberately splits across three:

AWS product Role Roughly maps to
CodeBuild Runs the actual build/test commands, similar to one Cloud Build step Cloud Build's execution engine
CodePipeline Orchestrates the multi-stage flow (source → build → deploy) and wires the other two together Cloud Build's trigger + step sequencing, combined
CodeDeploy Handles the actual rollout to EC2, ECS/Fargate, or Lambda, including rolling/blue-green strategies The gcloud run deploy step in the pipeline above

None of this is "AWS is more complicated for no reason" — CodePipeline genuinely supports more exotic multi-account, multi-region release flows than Cloud Build does out of the box. For a small project it's more moving parts than you need; at real organizational scale, that separation becomes a feature.

5. The pattern that's increasingly replacing both: GitHub Actions

A lot of real teams skip Cloud Build and CodePipeline entirely and just run the pipeline in GitHub Actions, authenticating to whichever cloud via the keyless Workload Identity Federation / OIDC pattern from Level 6 — one CI tool, either cloud, no long-lived keys stored as GitHub secrets. This is genuinely a strong default choice today, and it's exactly what Level 12's AWS CI/CD level builds out in full; worth knowing the option exists even while you're using Cloud Build here.

6. Deployment strategies, briefly

  • Rolling deploy — replace old instances with new ones gradually, a few at a time.
  • Blue/green deploy — stand up the entire new version alongside the old one, then flip traffic over all at once (fast rollback: just flip back).
  • Canary deploy — send a small percentage of real traffic to the new version first, watch for problems, then ramp up. Cloud Run supports this natively via traffic splitting between revisions — genuinely one of its nicer built-in features.
Hands-on for this level
  1. Add the cloudbuild.yaml from section 3 to your Level 5 app's repo (adjust the project/repo names to your own).
  2. In the console, go to Cloud Build → Triggers → Create Trigger, connect your GitHub repo, and point it at this file, triggering on push to main.
  3. Make a tiny visible change to your app (edit the response text), commit, and push. Watch the trigger fire in the Cloud Build console — build logs, push, deploy — with you doing nothing but git push.
  4. Curl your live URL again and confirm the text actually changed, deployed entirely by the pipeline.
  5. Optional: deploy a second small change, then in the Cloud Run console try splitting traffic 90/10 between the old and new revision, and watch requests actually land on both if you refresh a few times.

Observability: logging & monitoring

Goal: be able to answer "is my app actually healthy right now, and if not, why" without guessing — using logs, metrics, and alerts on the service you've been building since Level 5, and know the AWS equivalents by name.

1. Why this comes after CI/CD, not before

Now that deploys happen automatically (Level 7), the risk shifts: a bad change can ship without you watching. Observability is how you'd actually notice.

2. The pillars, cloud-agnostic

Logs
Discrete, timestamped text or structured events — "what happened." Good for understanding one specific incident in detail.
Metrics
Numeric time-series measurements — request count, latency, error rate, CPU% — sampled continuously. Good for spotting trends and setting alerts.
Traces
The path a single request takes across multiple services, with timing for each hop. Most valuable once you have more than one service talking to another.

3. GCP's stack vs. AWS's stack — a branding difference worth knowing

Pillar GCP AWS
Logs Cloud Logging CloudWatch Logs
Metrics & dashboards Cloud Monitoring CloudWatch Metrics
Alerting Cloud Monitoring alerting policies CloudWatch Alarms
Tracing Cloud Trace X-Ray
Auto-grouped exceptions Error Reporting — (closest: CloudWatch Logs Insights queries)

GCP gives each pillar its own product name even though they're one integrated suite under the hood (historically branded "Stackdriver," now just "Cloud Operations"). AWS bundles logs, metrics, and alarms all under one umbrella brand, CloudWatch, with tracing split out separately as X-Ray. Functionally the two clouds cover the same ground — this is naming, not a capability gap.

4. Structured logging — worth doing from day one

Compare these two log lines:

// unstructured — hard to filter later
console.log("user logged in: " + userId);

// structured — every field is independently queryable
console.log(JSON.stringify({
  severity: "INFO",
  message: "user logged in",
  userId: userId
}));

Both Cloud Logging and CloudWatch Logs Insights automatically parse JSON-formatted log lines into filterable fields — so "show me every failed login for this specific user" becomes a real query instead of manually scrolling through text.

5. Alerting and uptime checks

An alerting policy (GCP) or CloudWatch Alarm (AWS) watches a metric and fires a notification when a condition holds — e.g. "error rate above 5% for 5 minutes." Notifications go out through a notification channel (email, Slack, PagerDuty) on GCP, or an SNS topic subscribers listen to on AWS. Separately, an uptime check (GCP) or a health check via Route 53 / CloudWatch Synthetics (AWS) periodically hits your public URL from outside your infrastructure entirely, catching the case where your whole app — not just one metric — is unreachable.

Where this is heading Once you're tracking metrics like error rate and latency, the natural next question is "how good does this actually need to be?" — that's an SLI (Service Level Indicator, the raw measurement), an SLO (Service Level Objective, your target for it), and an error budget (how much you're allowed to miss that target before you stop shipping new features and fix reliability instead). You don't need to operationalize this yet — just recognize the vocabulary; it resurfaces properly in Level 15.
Hands-on for this level
  1. Open Cloud Logging and find the request logs from your Level 5/7 Cloud Run service. Try a filter query like resource.type="cloud_run_revision" AND severity>=ERROR — even with no errors yet, get comfortable with the query bar.
  2. Add one structured log line to your app (log the incoming request's path as a JSON object, per section 4), push it through your Level 7 pipeline, and confirm the new field shows up as independently filterable in Cloud Logging.
  3. Go to Cloud Monitoring → Alerting → Create Policy. Set a condition on your Cloud Run service (e.g. request latency above some threshold, or 5xx error count above 0), and add your email as the notification channel. You don't need to actually trigger it — the goal is understanding the configuration shape.
  4. Create an Uptime Check pointed at your live Cloud Run URL and watch it report healthy from multiple global locations.
  5. Optional parallel step: if you built the App Runner/Fargate version earlier, open its CloudWatch Logs and create one CloudWatch Alarm on a basic metric, to feel the naming differences directly.

AWS does not — free-tier quotas exist (12 months on many services, "always free" on a few), but the instant you exceed them, or touch a service with no free tier at all (like RDS, echoing Cloud SQL's warning from Level 3), your card is charged with no automatic stop. This isn't a reason to be scared of AWS — it's a reason to set up a budget alert in the next five minutes, before you create anything else.
  • Root account: created automatically when you sign up, with unrestricted power over everything, including billing. Best practice, from day one: enable MFA on it, then stop using it for anything except account-level emergencies.
  • A separate identity for daily work: create an IAM user (or, the more modern path, an IAM Identity Center user) for yourself, and use that day-to-day instead of root — the same least-privilege instinct from Level 6, applied to your own login.
  • AWS Budgets: set a low-dollar budget (even $5) with an email alert. This is the single highest-value five minutes you'll spend in this entire level.
  • AWS Organizations: lets a company run many AWS accounts under one umbrella with SCPs applied centrally (from Level 6). Overkill for solo learning, but good to recognize since most real companies use it.

4. AWS CLI — and a subtle callback to Level 6

The standard aws configure command asks for an access key ID and secret access key — which are exactly the long-lived static keys Level 6 warned about. For learning, this is common and fine; for anything longer-term, the better path is aws configure sso, authenticating through IAM Identity Center so your CLI session uses short-lived, automatically-refreshed credentials instead of a permanent key sitting in a config file on your laptop.

5. Picking a region

AWS's oldest and most feature-complete region is us-east-1 (Northern Virginia) — often the cheapest too, and a sensible default while learning, the same way GCP's tutorials leaned on us-central1 earlier in this path. Production systems usually pick a region for latency to real users instead, exactly the same reasoning from Level 1.

Hands-on for this level
  1. Log in as root, enable MFA (an authenticator app is easiest), then go to IAM and create yourself a regular IAM user (or set up IAM Identity Center) with a policy scoped for this course rather than full AdministratorAccess if you're comfortable tightening it later.
  2. Go to Billing → Budgets → Create Budget, set a small monthly dollar threshold, and add your email as an alert recipient.
  3. Install the AWS CLI and run aws configure (or aws configure sso), then confirm it worked with: aws sts get-caller-identity — it should print back your account ID and user ARN.
  4. As a smoke test tying back to Level 3: aws s3 mb s3://your-unique-bucket-name to confirm the CLI can actually create real resources under your identity.

Deploy on ECS Fargate / Lambda

Goal: actually deploy your app both ways on real AWS infrastructure — as a Lambda function and as an ECS Fargate service — and feel firsthand exactly how much more assembly Fargate needs compared to Cloud Run's single command, and how Lambda's execution model genuinely differs from a long-lived container.

1. Two real paths, not just theory this time

Level 5 compared Cloud Run against App Runner and Fargate on paper. This level actually builds the AWS side for real, using the same app you've deployed throughout this path.

2. Path A — Lambda: a genuinely different execution model

A bare Lambda function doesn't run your app as a long-lived server at all — it's a single function invoked per event: 

exports.handler = async (event) => {
  return {
    statusCode: 200,
    body: JSON.stringify({ message: "hello from Lambda" }),
  };
};

Compare that to your Express app's app.listen(...) model from Level 2/5 — there's no persistent process handling multiple requests over time; each invocation is its own isolated execution. A Function URL gives a Lambda function a direct HTTPS endpoint, without needing the older, more complex API Gateway setup — the closest AWS gets to Cloud Run's "just get a URL" simplicity.

If you'd rather keep your existing Express app unchanged, the modern option is the open-source AWS Lambda Web Adapter — it lets an ordinary Dockerfile-based Express app run inside Lambda with a Function URL, translating Lambda's event model to a normal HTTP request behind the scenes, so you don't have to rewrite your app into the handler shape above.

3. Path B — ECS Fargate: the full assembly, piece by piece

This is where Level 5's "Fargate needs more wiring" claim becomes concrete. Getting your Level 5 Dockerfile running on Fargate means creating, in order:

  1. An ECR repository — push your image here first (docker push, same image, new destination).
  2. A Task Definition — a JSON spec naming the image, CPU/memory, container port, and two distinct IAM roles (see below).
  3. A Cluster — a logical grouping; with Fargate, there are no EC2 instances to manage inside it, just where tasks/services live logically.
  4. A Service — keeps a desired number of task copies running, restarts failed ones, and connects to...
  5. An Application Load Balancer + Target Group — the actual public entry point, health-checking your tasks and routing traffic to healthy ones.
A confusion unique to ECS: two roles, not one A Task Definition asks for two separate IAM roles, and mixing them up is a very common beginner mistake: the execution role is what ECS itself uses to pull your image from ECR and write logs to CloudWatch — infrastructure plumbing your code never touches. The task role is what your running application code assumes to do its own job — like reading from an S3 bucket. Grant only what each one specifically needs; conflating them is an easy way to accidentally over-grant.

One Cloud Run deploy versus roughly six AWS resources wired together — this is the exact trade-off named back in Level 5: more assembly, in exchange for finer control (multiple containers per task, custom health checks, integration with other ECS services) that Cloud Run and App Runner deliberately hide from you.

4. Choosing between them, now with real experience behind it

  • Lambda — best for small, event-triggered logic with unpredictable/bursty traffic; note the hard 15-minute execution limit and the fact each invocation is stateless and isolated.
  • Fargate/ECS — best once you need real orchestration control, multiple coordinated services, or specific networking/scaling behavior beyond what App Runner exposes.
  • App Runner (from Level 5) — still the closest match to Cloud Run's simplicity, worth defaulting to unless you specifically need what Fargate gives you.
Hands-on for this level
  1. Push your Level 5 Dockerfile's image to a new ECR repository: aws ecr create-repository, then docker tag / docker push to it.
  2. Create a Task Definition referencing that image, with an execution role using the AWS-managed AmazonECSTaskExecutionRolePolicy, and a separate (initially minimal) task role.
  3. Create a Cluster, then a Service on it referencing your Task Definition, attached to a new Application Load Balancer and Target Group. Wait for the target to show healthy, then hit the ALB's public DNS name in a browser.
  4. Separately, write the tiny standalone Lambda handler from section 2, enable a Function URL on it, and curl it directly — notice how much less assembly this needed.
  5. Optional: try the Lambda Web Adapter approach to run your actual Express Dockerfile inside Lambda with a Function URL, for a true side-by-side of the same app on both paths.

Glossary

Task Definition
The JSON spec describing a Fargate task's image, resources, and IAM roles.
Execution role vs. Task role
Execution role: infrastructure plumbing (pull image, write logs). Task role: your app's own permissions.
Cluster / Service / Target Group
Cluster: logical grouping of tasks. Service: keeps a desired count running. Target Group: the set of healthy endpoints an ALB routes to.
Function URL
A direct HTTPS endpoint for a single Lambda function, without needing API Gateway.

IAM policies & least privilege

Goal: write a real least-privilege IAM policy for the resources you created in Level 10, understand ARNs precisely enough to reference the exact resource you mean, and wire a real secret into your Fargate task the AWS-native way.

1. Making Level 6's theory concrete

Level 6 explained AWS policy structure and least privilege conceptually. This level does the actual thing, against your actual Level 10 resources.

2. ARNs — how AWS addresses everything

An ARN (Amazon Resource Name) is the precise identifier a policy uses to say "this exact resource, not others of the same type." The format: arn:partition:service:region:account-id:resource. A couple of concrete examples: 

arn:aws:s3:::your-bucket-name/*
arn:aws:ecs:us-east-1:123456789012:task-definition/my-first-service:*
arn:aws:secretsmanager:us-east-1:123456789012:secret:demo-api-key-AbCdEf

Notice S3 ARNs skip the region and account ID (bucket names are globally unique), while most other services include both — small inconsistencies like this are exactly why reading the actual ARN a console screen shows you matters more than guessing the format from memory.

3. Writing a real least-privilege policy

Say your Fargate task role should only be able to read one specific S3 bucket — nothing else, no write access, no other buckets: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::your-bucket-name",
        "arn:aws:s3:::your-bucket-name/*"
      ]
    }
  ]
}

Every line here is deliberate: the Action list has exactly two read-only permissions, and Resource names your specific bucket rather than "*" (which would grant access to every bucket in the account). This is what "custom policy instead of a predefined one," from Level 6, actually looks like written out.

4. Two tools for validating before you deploy

IAM Policy Simulator
A console tool that answers "would this policy allow this specific action on this specific resource" without actually performing the action — the fastest way to catch an overly broad or too-narrow policy before it ships.
IAM Access Analyzer
Scans your account's policies and resource configurations for unintended public or cross-account access — worth running periodically, even on a small learning account, just to build the habit.

5. Secrets Manager, wired in for real this time

An ECS Task Definition has a dedicated Secrets field (distinct from plain environment variables) that pulls a value from Secrets Manager at container startup, with access controlled by the task role — exactly the pattern Level 6 described, now actually connected to a real running task.

Hands-on for this level
  1. Write the least-privilege JSON policy from section 3 (adjusted to your actual bucket name), and attach it to your Level 10 Fargate task role.
  2. Open IAM → Policy Simulator, select that role, and confirm it allows s3:GetObject on your bucket but denies it on some other unrelated bucket ARN you type in — seeing an explicit deny in the simulator is the point.
  3. Create a secret in Secrets Manager with a fake value, then edit your Level 10 Task Definition to reference it via the Secrets field (not a plain environment variable), pointing at the secret's ARN, and redeploy the service.
  4. Confirm your running task can read the secret (log it once, temporarily, to verify — then remove that log line).
  5. Optional: run IAM Access Analyzer once and read through whatever it reports, even if the answer is "no findings."

Self-check before moving to Level 12

  • Why does the ARN format skip region and account ID for S3 but not for most other services?
  • What's wrong with writing "Resource": "*" in a policy meant to be least-privilege?
  • What does the Policy Simulator actually check, and why is that safer than testing a policy by deploying it and seeing what breaks?

CI/CD with GitHub Actions → AWS

Goal: build the actual keyless CI/CD pipeline teased since Level 6 — GitHub Actions authenticating to AWS via OIDC, with zero long-lived access keys stored anywhere, automatically building and deploying on every push.

1. Why GitHub Actions instead of CodePipeline here

Level 7 named CodePipeline/CodeBuild/CodeDeploy as AWS's native three-product answer to Cloud Build — a real, valid, deeper option, especially at larger scale. This level deliberately builds the GitHub Actions alternative instead, because it directly exercises the keyless-auth lesson from Level 6/11, and because it's a genuinely common real-world choice today, cloud-agnostic by nature.

2. Setting up trust: an OIDC Identity Provider

The whole point is that GitHub Actions never holds a stored AWS access key — instead, AWS is configured to trust tokens GitHub itself issues:

  1. In IAM, create an OIDC Identity Provider pointed at GitHub's issuer, token.actions.githubusercontent.com.
  2. Create an IAM Role with a trust policy that only allows a specific GitHub repository (and optionally branch) to assume it: 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:sub": "repo:your-username/your-repo:ref:refs/heads/main"
      }
    }
  }]
}

That Condition block is doing real work — it's the difference between "any GitHub Actions workflow anywhere can assume this role" and "only pushes to main in this exact repo can."

3. Scoping the role's permissions — Level 11, applied again

Attach a policy to this role granting only ecr:GetAuthorizationToken plus push/pull on your specific ECR repo ARN, and ecs:UpdateService/ecs:DescribeServices scoped to your specific cluster and service ARNs from Level 10 — the exact least-privilege habit from Level 11, applied to a CI pipeline instead of a running app.

4. The workflow file

name: Deploy to ECS
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-deploy-role
          aws-region: us-east-1
      - run: |
          aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
          docker build -t my-app .
          docker tag my-app:latest 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app:latest
          docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app:latest
          aws ecs update-service --cluster my-cluster --service my-service --force-new-deployment

Read the shape of it: permissions: id-token: write is what lets this workflow request an OIDC token at all; configure-aws-credentials exchanges that token for temporary AWS credentials scoped to exactly the role from section 2 — no AWS_ACCESS_KEY_ID secret stored in GitHub, ever.

5. The same idea, two clouds

Functionally, this is the exact same push → build → push image → redeploy shape as Level 7's Cloud Build trigger — just running on GitHub's infrastructure instead of a cloud-native build product, authenticating via OIDC on both ends rather than a stored key on either.

Hands-on for this level
  1. Create the OIDC Identity Provider and IAM Role with the trust policy from section 2, adjusted to your own GitHub username/repo.
  2. Attach the scoped ECR + ECS permissions policy from section 3.
  3. Add the workflow file from section 4 to your app's repo (the ARNs and image names adjusted to your own), referencing your new role's ARN.
  4. Push a small visible change to main, then watch the run under your repo's Actions tab — checkout, credential exchange, build, push, deploy.
  5. Curl your Level 10 ALB URL again to confirm the change actually shipped, end to end, with no human running a deploy command.

  • Where does the workflow ever store a long-lived AWS access key? (If your answer is "nowhere," you've got it.)
  • Why is this pipeline functionally equivalent to Level 7's Cloud Build trigger, despite running on completely different infrastructure?

Infrastructure as Code (Terraform)

Goal: stop clicking through consoles for anything real — describe your infrastructure in code, version it in git, and apply it the same way every time, on either cloud, with the same tool.

1. The problem with everything you've done so far

Every resource in Levels 1–12 was either clicked through a console or typed as a one-off CLI command. Neither leaves a trace of why something exists, neither is easy to review before it happens, and neither is trivially repeatable if you needed a second identical environment. Infrastructure as Code (IaC) fixes all three: you write the desired end state as code, commit it, and a tool figures out how to make reality match it.

2. Declarative vs. imperative — the core theory

An imperative script is a sequence of commands: "create this VM, then this bucket, then attach this role." You're responsible for ordering, for checking what already exists, for handling reruns safely. A declarative tool like Terraform flips this: you describe what should exist, and the tool computes the difference between that and what's actually there, then applies only the necessary changes. This is exactly the same mental shift as writing a shopping list versus narrating turn-by-turn driving directions to the store.

3. Terraform's core vocabulary

Provider
A plugin that knows how to talk to one platform's API — the google provider for GCP, the aws provider for AWS. Same Terraform tool, different provider per cloud.
Resource
One declared piece of infrastructure — a Cloud Run service, an S3 bucket, an IAM role. Each resource type is specific to its provider; there's no generic "compute resource" that works on both clouds.
State file
Terraform's own record of what it believes currently exists, used to compute the next diff. This is the single most important — and most commonly mishandled — concept in Terraform: lose or corrupt the state file and Terraform no longer knows what it's managing.
Plan / Apply / Destroy
The core workflow. terraform plan shows a dry-run diff with no changes made. terraform apply executes that diff for real. terraform destroy tears down everything the config manages — genuinely useful for cleanly removing every resource from a learning exercise in one command.
Variables / Outputs
Variables parameterize a config (region, project ID, image tag); outputs surface values back out after apply (like the resulting Cloud Run URL).
Module
A reusable, packaged bundle of resources — write a "web service" module once, reuse it for every app instead of copy-pasting the same resource blocks.
A genuine beginner trap: local state By default, Terraform writes its state file to your local disk. That's fine solo, but it means the state lives only on your laptop — lose the file, or have a teammate apply from a different machine, and Terraform loses track of reality. The production-grade fix is remote state: store the state file itself in a Cloud Storage bucket (GCP) or an S3 bucket with a DynamoDB table for locking (AWS), so anyone applying reads and writes the same shared source of truth, with locking to stop two people applying at once and corrupting it.

4. A minimal real example: your Level 5 Cloud Run service, declared

terraform {
  required_providers {
    google = { source = "hashicorp/google" }
  }
}

provider "google" {
  project = "your-project-id"
  region  = "us-central1"
}

resource "google_cloud_run_v2_service" "app" {
  name     = "my-first-service"
  location = "us-central1"

  template {
    containers {
      image = "us-central1-docker.pkg.dev/your-project-id/repo/my-app:latest"
    }
  }
}

The AWS shape for the same idea (App Runner) uses a different provider and different resource names, but the same plan → apply workflow: 

provider "aws" {
  region = "us-east-1"
}

resource "aws_apprunner_service" "app" {
  service_name = "my-first-service"
  source_configuration {
    image_repository {
      image_identifier      = "123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app:latest"
      image_repository_type = "ECR"
    }
  }
}
The misconception worth correcting up front "Terraform is multi-cloud" is true and misleading at the same time. You get one tool and one workflow across clouds — not automatically portable infrastructure. A google_cloud_run_v2_service block and an aws_apprunner_service block are not interchangeable; you still write cloud-specific resource blocks for each cloud, exactly like you've been learning GCP and AWS service-by-service this whole path. Terraform unifies how you apply changes, not what the resources are.

5. Where Terraform sits among its alternatives

  • Terraform (HashiCorp) — the most widely adopted, multi-cloud, its own HCL syntax. What we're using here.
  • CloudFormation — AWS's own native IaC tool, YAML/JSON, AWS-only.
  • Pulumi — write infrastructure in a real programming language (TypeScript, Python) instead of a dedicated config language, appealing if you'd rather stay in familiar syntax.
Hands-on for this level
  1. Install Terraform, then write a main.tf matching section 4's Cloud Run example, filled in with your actual project ID and image.
  2. Run terraform init (downloads the provider), then terraform plan — read the diff carefully before applying anything.
  3. Run terraform apply, confirm, and check the console: this should be recognizably the same service you deployed manually in Level 5, now defined in a file you can commit to git.
  4. Run terraform destroy and watch it cleanly remove exactly what it created — notice how much more confidence this gives you than manually hunting through console menus to delete things.
  5. Optional parallel step: write the AWS App Runner version from section 4 and run the same init → plan → apply → destroy cycle against your AWS account.

Kubernetes: GKE vs EKS

Goal: understand precisely what Kubernetes solves that Cloud Run and Fargate don't, the core objects you'd actually read in a real cluster's config, and get real kubectl practice — without needing to pay for an always-on cluster to do it.

1. Why this exists when Cloud Run/Fargate already work

Cloud Run, App Runner, and Fargate are excellent for a single containerized service. Kubernetes exists for what happens past that: many interdependent services that need to discover each other, fine-grained control over scheduling and resource sharing across a fleet of machines, and portability across clouds or even on-prem hardware. It is genuinely more powerful and genuinely more complex — not a default choice, but something worth understanding precisely since it underpins a huge share of real production infrastructure.

2. Core objects, explained plainly

Cluster
A set of machines managed together as one unit.
Node
One machine (a VM, usually) inside the cluster, running the agent that lets Kubernetes schedule work onto it.
Pod
The smallest deployable unit — one or more tightly coupled containers sharing network and storage. Most simple apps use one container per Pod.
Deployment
Manages a set of identical Pod replicas and handles rolling updates between versions — the K8s-native equivalent of the Managed Instance Group / Auto Scaling Group concept from Level 2.
Service (Kubernetes)
A stable network endpoint in front of a constantly-changing set of Pods. Pods get destroyed and recreated with new internal IPs all the time; a Service gives callers one address that doesn't change. Note: this is a different concept from an "ECS Service" in Level 10 — same word, different layer, worth not confusing.
Ingress
HTTP(S) routing rules for traffic entering the cluster from outside — the K8s-native equivalent of a load balancer's routing config.
Namespace
A way to logically partition one cluster — separate dev/staging/prod, or per-team, without needing separate clusters.
ConfigMap / Secret
Kubernetes' own way to inject configuration and secret values into Pods — conceptually parallel to Secret Manager from Level 6, but scoped to the cluster rather than the whole cloud account.

3. GKE vs. EKS: what "managed" actually means here

Both GKE and EKS run the Kubernetes control plane for you (the API server, scheduler, and cluster state store) — the hardest part to operate yourself — leaving you to manage just the worker nodes, or not even that:

  • GKE Autopilot — GCP manages node provisioning and scaling entirely too, the closest thing to "serverless Kubernetes" that still exposes the full Kubernetes API.
  • EKS with Fargate — the same idea on AWS: Pods run on Fargate instead of self-managed EC2 worker nodes, so there's no node fleet for you to patch or size.

Worth knowing as genuine history, not just marketing: Kubernetes itself was born out of Google's internal system (Borg), which is part of why GKE has long been considered the most polished managed offering — though EKS has closed that gap substantially in recent years.

4. A minimal Deployment + Service, read line by line

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 2
  selector:
    matchLabels: { app: my-app }
  template:
    metadata:
      labels: { app: my-app }
    spec:
      containers:
        - name: my-app
          image: my-app:latest
          ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector: { app: my-app }
  ports: [{ port: 80, targetPort: 8080 }]
  type: LoadBalancer

The Deployment says "keep 2 identical copies of this container running." The Service says "give callers one stable address, port 80, that load-balances across whichever Pods currently match app: my-app" — regardless of how many times those Pods get replaced underneath.

5. kubectl — the one genuinely portable tool in this whole path

kubectl is the command-line tool for talking to any Kubernetes cluster, and unlike almost every other tool in this course, the exact same commands work against GKE, EKS, or a cluster running entirely on your own laptop — a rare moment of real, not just marketed, portability.

Cost honesty before you spin anything up A real GKE or EKS cluster is not free even at idle — worker nodes bill continuously regardless of traffic, a real regression from Cloud Run/Lambda's scale-to-zero. For learning the YAML and kubectl workflow itself, use a free local cluster tool — kind (Kubernetes-in-Docker) or minikube — with zero cloud cost. Only spin up a real GKE Autopilot or EKS cluster if you specifically want that experience, and delete it immediately after.
Hands-on for this level
  1. Install kubectl and kind (or minikube) locally — no cloud account needed for this part.
  2. Create a local cluster: kind create cluster.
  3. Save section 4's YAML as app.yaml (swap in your own small test image), then kubectl apply -f app.yaml.
  4. Run kubectl get pods — you should see 2 Pods running. kubectl port-forward service/my-app-service 8080:80 and hit localhost:8080 in a browser or curl.
  5. Try kubectl scale deployment my-app --replicas=3 and run kubectl get pods again to watch a third Pod appear live.
  6. Optional, cost-aware: create a real GKE Autopilot cluster, apply the same YAML there instead of locally, confirm it works identically, then delete the cluster immediately afterward so it doesn't keep billing.

Cost, scaling & architecture patterns

Goal: think about a whole system the way an experienced engineer does — where cost actually comes from and how to control it, how scaling decisions get made, and how to define "good enough" precisely instead of vaguely, using the SLI/SLO vocabulary teased back in Level 8.

1. From individual services to one whole system

Levels 1–14 covered services one at a time. This level is about how they fit together into judgment calls — the kind you'd actually be asked to make on a real team.

2. Concrete cost optimization techniques

  • Right-sizing — don't allocate a VM's or Cloud Run task's memory/CPU "just in case." Look at actual usage in Cloud Monitoring/CloudWatch (Level 8) and size to what's really being used, with a sensible margin.
  • Scale-to-zero vs. reserved capacity — for spiky or unpredictable traffic, Cloud Run/Lambda's scale-to-zero (Level 2) wins on cost. For steady, predictable, always-on load, Committed Use Discounts (GCP) or Savings Plans / Reserved Instances (AWS) trade a commitment for a meaningfully lower rate than on-demand pricing.
  • Storage lifecycle policies — automatically transition old objects in Cloud Storage/S3 (Level 3) to cheaper cold tiers (Nearline/Coldline on GCP, Glacier on AWS) or delete them outright after N days, instead of paying standard rates for data nobody's read in months.
  • Data egress costs — the sneaky one. Moving data out of a cloud (to the public internet, or across regions) usually costs meaningfully more than storing or computing on it. Keeping traffic within one region, and one provider, is a real and often-overlooked lever.
  • Spot / Preemptible instances — deeply discounted compute the provider can reclaim with little notice. Excellent for fault-tolerant batch work (Spot VMs on GCP, Spot Instances on AWS) — bad for anything that can't tolerate an abrupt interruption.

3. Scaling patterns, in theory

  • Vertical scaling (a bigger machine) vs. horizontal scaling (more machines) — vertical has a hard ceiling and remains a single point of failure; horizontal scales further but requires your app to be stateless, the exact same requirement Level 2 introduced for serverless compute.
  • Reactive autoscaling (add capacity once a metric like CPU crosses a threshold) vs. predictive/scheduled scaling (scale up ahead of a known traffic pattern — a marketing email going out at 9am, say) — reactive is simpler and the default; predictive avoids the lag of reacting only after load has already arrived.

4. The Well-Architected Framework — a mental checklist, not a memorization exercise

Both clouds publish a framework for reviewing a system design against the same handful of concerns — AWS's Well-Architected Framework is the more widely referenced original; GCP publishes its own Architecture Framework covering equivalent ground. The pillars, worth recognizing by name rather than memorizing in depth: operational excellence, security, reliability, performance efficiency, and cost optimization. When reviewing any real design, running through these five as a checklist catches blind spots a narrower "does it work" review misses.

5. SLI, SLO, and error budget — properly this time

Level 8 mentioned these in passing; here's the actual discipline behind them, which originated at Google as part of Site Reliability Engineering:

SLI (Service Level Indicator)
The actual measured metric — e.g., "the percentage of requests that complete in under 200ms."
SLO (Service Level Objective)
Your target for that SLI over a time window — e.g., "99.9% of requests under 200ms, measured over a rolling 30 days."
Error budget
The failure room your SLO implicitly allows — 0.1% in the example above. While you're within budget, ship features at normal speed. Once you've burned through it, the discipline says: stop shipping new features and fix reliability first.
Worked example: growing past a hobby project Say your Level 5/10 app has actually picked up real users. The mature sequence isn't "add more regions" first — it's: right-size based on real Level 8 metrics → add horizontal autoscaling within your current region → ensure redundancy across zones within that region (Level 1's zones, not a whole second region) → only then consider true multi-region, and only if the SLO you've defined genuinely requires it. Reaching for multi-region before single-region redundancy is solid is one of the most common real over-engineering mistakes — most projects never actually need it.
Hands-on for this level
  1. Open Cloud Monitoring (or CloudWatch) for your actual Level 5/10 deployed services and look at real accumulated request count, latency, and CPU/memory usage.
  2. Based on what you see, make one concrete right-sizing change — e.g., lower your Cloud Run service's memory allocation if usage has consistently sat well below the current limit — and redeploy.
  3. Add a lifecycle rule to your Level 3 Cloud Storage bucket: transition objects older than 30 days to Nearline, or auto-delete them — a real, free-to-configure setting, not a simulation.
  4. Write down one precise SLO for your deployed app — e.g., "95% of requests succeed with under 500ms latency, measured over a rolling 7 days." It doesn't need to be enforced by tooling yet; the exercise is stating one precisely instead of vaguely.

Self-check before the capstone

  • Name three concrete ways to lower cloud spend without reducing reliability.
  • Why does horizontal scaling require statelessness while vertical scaling doesn't?
  • What's the practical consequence of burning through an error budget?
  • Why is reaching for multi-region before solid single-region redundancy usually a mistake?

Capstone: deploy your AI/agent stack

Goal: one integrated project that deliberately exercises every level in this path, rather than new theory — the actual point of everything from Level 1 onward.

The brief

Deploy a small AI/agent backend — a RAG API, an agent endpoint, anything with a request in, an LLM or retrieval step, and a response out — to both clouds, built so that every earlier level is genuinely exercised rather than skipped:

  • Compute (Levels 2, 5, 10): the app containerized and deployed to Cloud Run and its AWS equivalent (App Runner or Fargate) — the "GCP first, AWS parallel" structure from Level 1, now applied to one real project instead of separate exercises.
  • Storage & data (Level 3): embeddings or documents in Cloud Storage/S3, and/or a Firestore/DynamoDB collection holding retrieval metadata.
  • Networking & IAM (Levels 4, 6, 11): a least-privilege service account/task role, scoped to only the specific bucket and secret this app actually needs — nothing broader.
  • Secrets (Levels 6, 11): your LLM provider's API key stored in Secret Manager/Secrets Manager, referenced at runtime — never hardcoded, never a plain environment variable in your repo.
  • CI/CD (Levels 7, 12): a push-to-deploy pipeline on at least one cloud (Cloud Build or GitHub Actions with OIDC) so shipping a change is git push, not a manual command.
  • Observability (Level 8): structured logs for each request/response, and one real alert — e.g., on elevated error rate or latency.
  • IaC (Level 13): the entire thing declared in Terraform, applied with terraform apply, not clicked together by hand.
  • Optional stretch (Level 14): run it on GKE Autopilot or EKS with Fargate instead of Cloud Run/App Runner directly, if you want the Kubernetes experience on something real.
  • Cost & architecture (Level 15): one written SLO for the app, and a quick pass checking it stays within a sensible free-or-near-free budget for a personal project.

Suggested build order

Not new theory — just the same sequence you've already practiced, now applied to one project instead of separate throwaway exercises:

  1. Write and containerize the app (Level 2's Dockerfile discipline).
  2. Deploy manually once on GCP to confirm it works (Level 5), then again on AWS (Level 10).
  3. Wire in real storage and a least-privilege identity for each (Levels 3, 4, 6, 11).
  4. Move the secret out of code and into Secret Manager/Secrets Manager (Levels 6, 11).
  5. Rewrite the whole thing as Terraform, destroy the manual version, and reapply from code (Level 13).
  6. Add the CI/CD pipeline so future changes deploy themselves (Levels 7, 12).
  7. Add structured logging and one alert (Level 8).
  8. Write the SLO and sanity-check the cost (Level 15).

What "done" looks like

  • A `git push` deploys the app automatically, on at least one cloud, with no manual step.
  • No secret exists anywhere in your repo, environment variables, or Dockerfile.
  • The service account / task role could be shown to someone else without embarrassment about over-broad permissions.
  • Every resource involved is defined in a Terraform config, not sitting there because you clicked it into existence.
  • You could state, in one sentence, this app's SLO.

Where to go from here

This document stops here, but a few genuinely worthwhile next directions: pursue a recognized cloud certification to formalize what you've built (Google Associate Cloud Engineer or Professional Cloud Architect; AWS Certified Cloud Practitioner or Solutions Architect – Associate) — contribute to an open-source infra tool you've now used firsthand (Terraform providers, kubectl plugins) — or specialize further into adjacent tracks like data engineering, MLOps, or platform engineering, all of which build directly on everything in this path rather than replacing it.

That's the whole path, start to finish — first principles in Level 1 to a real, observed, automatically-deployed, cost-aware system here. Everything after this is depth, not a different foundation.
