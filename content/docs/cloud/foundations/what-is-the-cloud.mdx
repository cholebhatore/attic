  Explain in your own words what a cloud provider actually sells you, why "serverless" doesn't mean
  no servers, and where Render, AWS, and GCP each sit on the same underlying spectrum.
</Callout>

## 1. You've already used a cloud. Render _is_ one.

When you push code to Render, it builds a container image, puts it on a machine somewhere, attaches a URL, restarts it if it crashes, and gives you logs. You never picked a machine size, a region's networking rules, or a disk type — Render decided all of that for you and hid it.

GCP and AWS sell the exact same underlying thing — computers, storage, and networking, sitting in enormous buildings called data centers, that you rent by the second instead of buying outright. The difference is **how many of the decisions they make for you versus leave to you**. That single idea — _where a service sits on the "decisions made for you" spectrum_ — is the most important mental model in this entire path. Almost every cloud concept you'll learn is really just "where does this sit on that spectrum, and what do I gain or give up by moving along it."

<Callout type="info" title="Anchor analogy">
  Think of it like transport, not tech: owning a car (you maintain everything) → renting a car
  (someone else maintains it, you still drive) → taking a taxi (you just state a destination) →
  public transit (fixed route, cheapest, least control). Buying physical servers is "owning a car."
  A raw cloud VM is "renting a car." A platform like Cloud Run or Render is "taking a taxi." A fully
  managed SaaS tool is "public transit." Nothing here is objectively best — the right choice depends
  on how much control you actually need for the trip.
</Callout>

## 2. The four service models

Every cloud service you'll ever touch falls into one of four buckets, defined purely by **who manages what**:

| Model                                                   | You manage                                  | Provider manages                                   | Example                                       |
| :------------------------------------------------------ | :------------------------------------------ | :------------------------------------------------- | :-------------------------------------------- |
| **IaaS** — Infrastructure as a Service                  | OS, runtime, app, scaling, patching         | Physical hardware, virtualization, network, power  | GCP Compute Engine, AWS EC2                   |
| **PaaS** — Platform as a Service                        | Your application code                       | OS, runtime, patching, scaling infrastructure      | Render, GCP App Engine, AWS Elastic Beanstalk |
| **FaaS / Serverless** — Function/Container as a Service | A single function or request-handler's code | Everything else, including scaling to exactly zero | GCP Cloud Run & Cloud Functions, AWS Lambda   |
| **SaaS** — Software as a Service                        | Your data/configuration only                | The entire application                             | Gmail, Notion, GitHub itself                  |

<Callout type="info" title="Where you've already been">
  Render sits in **PaaS**, closer to FaaS on its free tier (your service can idle/sleep, similar in
  spirit to scale-to-zero). This path takes you one level "down" the stack first — into IaaS with
  raw VMs — so you understand what PaaS/FaaS is automating away, before bringing you back "up" into
  GCP's PaaS/FaaS tools like Cloud Run with full understanding of what's happening underneath.
</Callout>

## 3. Same app, three different deploys

Theory sticks a lot better once you can picture it as one concrete thing happening three different ways. Say you've built a small Node.js/Express API — the kind of thing you'd currently just push straight to Render.

<Callout type="info" title="The same app, at every layer of the stack">
  - **IaaS route — AWS EC2 / GCP Compute Engine:** you provision a virtual machine, SSH into it,
  install Node yourself, pull your code, run it with something like `pm2` so it survives a reboot,
  and open a firewall port. Nothing gets fixed silently — if the process dies at 3am, it stays dead
  until you notice and SSH back in. Maximum control, maximum responsibility. - **PaaS route — Render
  / AWS Elastic Beanstalk / GCP App Engine:** you push code or a Dockerfile, and the platform builds
  it, runs it, restarts it on crash, and hands you a URL. You never see the underlying VM at all.
  This is exactly where Render already had you. - **Serverless route — AWS Lambda / GCP Cloud Run:**
  your Express app gets wrapped so each incoming request spins up (or reuses) a lightweight
  instance, handles it, and can disappear completely once traffic stops. Cloud Run is the friendlier
  version of this for a beginner because it just runs a normal Docker container — same app, no code
  rewrite — whereas Lambda historically wanted your code in a specific handler shape (it supports
  containers now too, but the ergonomics still lean more "function" than "app").
</Callout>

Same couple hundred lines of Express code, three completely different operational realities — who patches the OS, who restarts a crash, who decides if you pay for idle time. This is exactly the spectrum from section 1, just applied to one real app instead of talked about in the abstract. We'll actually run this deploy for real — GCP first, then the AWS equivalent — starting with compute and container deployment.

## 4. Serverless doesn't mean "no servers"

This is the single most misleading term in cloud computing, and you asked about it directly, so let's be precise. There are absolutely still servers. "Serverless" means **you never provision, size, patch, or manage the server** — the provider allocates one to run your code only when a request arrives, and reclaims it when there's no traffic.

- **Scale to zero:** if nobody's using your app, you can run (and pay) literally nothing.
- **Pay-per-use:** billing is usually per-request and per-100ms of compute, not per-hour-the-machine-existed.
- **Statelessness:** your code shouldn't assume anything saved to local disk will still be there next time it runs — the "server" underneath may be a completely different physical machine on the next request.
- **Cold starts:** the trade-off for scaling to zero — the very first request after idling has to wait for a fresh instance to boot, which can add noticeable latency.

<Callout type="warn" title="Common beginner confusion">
  "Serverless" (Cloud Run, Lambda) and "PaaS" (Render, App Engine) overlap a lot in practice, and
  providers blur the marketing on purpose. The technical distinction that actually matters: true
  serverless platforms scale to zero and bill per-request; classic PaaS often keeps at least one
  instance warm and bills per-time-running. You'll feel this difference directly once you deploy on
  both.
</Callout>

## 5. Building blocks you'll keep hearing

**Region** — A specific geographic area with its own cluster of data centers (e.g. `asia-south1` = Mumbai, on GCP). You pick a region to keep your app physically close to your users, for latency and legal/data-residency reasons.

**Zone / Availability Zone** — A region is split into multiple isolated zones (separate power, cooling, networking) so a failure in one doesn't take down the whole region. Spreading resources across zones is how you get resilience without a second region.

**Resource hierarchy** — How a cloud account organizes everything you create. On GCP it's `Organization → Folder → Project → Resources`; every single thing — a VM, a bucket, a Cloud Run service — lives inside exactly one **Project**. AWS's version is `Organization → Organizational Unit → Account → Resources` — the **Account** plays the same role GCP's Project does, just one level "bigger" (AWS accounts often hold more than a GCP project would).

**IAM (Identity and Access Management)** — The system that decides _who_ (a person, or a service acting on its own) can do _what_ to _which_ resource. Both clouds call this exact concept "IAM" — GCP attaches permissions via roles on a resource, AWS via JSON policy documents attached to users/roles. Same job, different syntax. You'll go deep on this in the IAM & Security modules — for now, just know every action in the cloud is checked against an IAM policy first.

**Managed vs. unmanaged** — "Managed" means the provider handles operational upkeep (patching, backups, failover) for you, for a price premium. A self-hosted Postgres on a VM is unmanaged; **GCP Cloud SQL** and **AWS RDS** are both managed equivalents for the exact same job. This is the same spectrum from section 1, applied to a single service.

**SLA (Service Level Agreement)** — A contractual uptime promise (e.g. "99.95% available per month"), with credits owed to you if the provider misses it. A good habit: whenever you pick a service, glance at its SLA — it tells you how much the provider is willing to bet on it.

## 6. Why anyone uses cloud instead of buying their own servers

- **Elasticity** — scale from 1 user to 1 million and back down, without ever buying hardware.
- **Capex → Opex** — no large upfront hardware purchase (capital expense); you pay ongoing, variable operating expense instead, which is why cloud bills scale with your traffic.
- **Global reach** — deploying "closer" to users in another continent is a config change, not a construction project.
- **Managed services** — you get a production-grade database, queue, or cache without becoming a database administrator.
- **The honest trade-off:** at very large, steady, predictable scale, owning hardware can be cheaper — this is why some giant companies run hybrid or their own data centers. For a beginner-to-mid-size project, this almost never applies to you yet, but it's worth knowing the "cloud is always cheaper" claim isn't universally true.

## 7. First look at the consoles: GCP and AWS side-by-side

You're starting hands-on with GCP, so that's the account we're setting up in this module. But since every technology in this path gets explained on both clouds, here's the same map for AWS too — so the vocabulary isn't a surprise later.

| Concept           | GCP                                                                           | AWS                                                                                                                |
| :---------------- | :---------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------- |
| Web console       | `console.cloud.google.com`                                                    | `console.aws.amazon.com`                                                                                           |
| Organizing unit   | **Project** — everything you create lives in one                              | **Account** — everything lives inside one AWS account (multiple accounts can sit under an "Organization")          |
| Billing           | A billing account linked to your project(s)                                   | A payment method linked directly to the AWS account                                                                |
| Command-line tool | `gcloud`                                                                      | `aws` (the AWS CLI)                                                                                                |
| Free tier         | Trial credit for new accounts + "always free" monthly quotas on many services | 12 months of free-tier quotas on many services + a separate set of "always free" limits — no lump-sum trial credit |

  This is a gentle practical step to complement the theory above.

<Steps>
  <Step>
    ### Create a Google Cloud account

    Go to [cloud.google.com/free](https://cloud.google.com/free) (needs a card for identity verification, but the trial credit means you won't be charged without explicitly upgrading).

  </Step>
  <Step>
    ### Create your first Project

    From the console — name it something like `learning-sandbox`.

  </Step>
  <Step>
    ### Look around the console

    Spend 10 minutes just looking around. Open the navigation menu, find *Compute Engine*, *Cloud Run*, and *IAM & Admin* — don't click into anything yet, just note that they exist. You'll use each of them soon.

  </Step>
  <Step>
    ### (Optional) Install the gcloud CLI

    Install from [cloud.google.com/sdk/docs/install](https://cloud.google.com/sdk/docs/install) and run `gcloud init` to authenticate it.

  </Step>

    ### (Optional) Create a free AWS account

    Go to [aws.amazon.com/free](https://aws.amazon.com/free) and open its console for two minutes, side-by-side with GCP's. You're not doing anything on it yet — just letting the two UIs stop looking alien to each other.

  </Step>
</Steps>
