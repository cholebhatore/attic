## The brief

Deploy a small AI/agent backend — a RAG API, an agent endpoint, anything with a request in, an LLM or retrieval step, and a response out — to both clouds, built so that every earlier concept is genuinely exercised rather than skipped:

- **Compute:** The app containerized and deployed to Cloud Run _and_ its AWS equivalent (App Runner or ECS Fargate) — exercising production container orchestration on both clouds.
- **Storage & data:** Embeddings or documents in Cloud Storage / S3, and/or a Firestore / DynamoDB collection holding retrieval metadata.
- **Networking & IAM:** A least-privilege service account / task role, scoped to only the specific bucket and secret this app actually needs — nothing broader.
- **Secrets:** Your LLM provider's API key stored in Secret Manager / Secrets Manager, referenced at runtime — never hardcoded, never a plain environment variable in your repo.
- **CI/CD:** A push-to-deploy pipeline on at least one cloud (Cloud Build or GitHub Actions with OIDC) so shipping a change is `git push`, not a manual command.
- **Observability:** Structured JSON logs for each request/response, and one real alert — e.g., on elevated error rate or latency.
- **IaC:** The entire infrastructure declared in Terraform, applied with `terraform apply`, not clicked together by hand.
- **Optional stretch:** Run it on GKE Autopilot or EKS with Fargate instead of Cloud Run/App Runner directly, if you want the Kubernetes experience on something real.
- **Cost & architecture:** One written SLO for the app, and a quick pass checking it stays within a sensible free-or-near-free budget for a personal project.

## Suggested build order

Not new theory — just the same sequence you've already practiced, now applied to one project instead of separate throwaway exercises:

<Steps>
  <Step>
    ### Write and containerize the app

    Follow production multi-stage Dockerfile discipline with non-root runtime users.

  </Step>
  <Step>
    ### Deploy manually once to each cloud

    Confirm it works on GCP (Cloud Run), then again on AWS (ECS Fargate or App Runner).

  </Step>
  <Step>
    ### Wire in real storage and least-privilege identity

    Attach Cloud Storage / S3 and scoped least-privilege IAM roles.

  </Step>
  <Step>
    ### Move secret into Secret Manager

    Store LLM keys in Secret Manager / Secrets Manager with runtime injection.

  </Step>
  <Step>
    ### Rewrite into Terraform

    Destroy the manual version, and reapply everything from Terraform IaC.

  </Step>
  <Step>
    ### Add CI/CD pipeline

    Automate builds on push via Cloud Build or GitHub Actions with keyless OIDC.

  </Step>
  <Step>
    ### Add structured logging and alerting

    Emit JSON logs and set up automated CloudWatch / Cloud Monitoring alarms.

  </Step>
  <Step>
    ### Define SLO and sanity-check costs

    Write the service level objective and verify budget guardrails.

  </Step>
</Steps>

## What "done" looks like

- A `git push` deploys the app automatically, on at least one cloud, with no manual step.
- No secret exists anywhere in your repo, environment variables, or Dockerfile.
- The service account / task role could be shown to someone else without embarrassment about over-broad permissions.
- Every resource involved is defined in a Terraform config, not sitting there because you clicked it into existence.
- You could state, in one sentence, this app's SLO.

## Where to go from here

This document stops here, but a few genuinely worthwhile next directions: pursue a recognized cloud certification to formalize what you've built (**Google Associate Cloud Engineer** or **Professional Cloud Architect**; **AWS Certified Cloud Practitioner** or **Solutions Architect – Associate**) — contribute to an open-source infra tool you've now used firsthand (Terraform providers, kubectl plugins) — or specialize further into adjacent tracks like data engineering, MLOps, or platform engineering, all of which build directly on everything in this path rather than replacing it.

> _That's the whole path, start to finish — first principles to a real, observed, automatically-deployed, cost-aware system here. Everything after this is depth, not a different foundation._
