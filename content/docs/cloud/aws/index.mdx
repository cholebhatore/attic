## 1. AWS Global Infrastructure

AWS operates on a globally distributed physical footprint engineered for high availability, fault tolerance, and minimal latency:

<Mermaid
  chart={`

    subgraph Global["AWS Global Network"]
        direction TB
        subgraph Region["AWS Region (e.g. us-east-1 N. Virginia)"]
            AZ1["Availability Zone A (Data Center Cluster)"]

            AZ3["Availability Zone C (Data Center Cluster)"]
            AZ1 <-->|Private Low-Latency Fiber| AZ2
            AZ2 <-->|Private Low-Latency Fiber| AZ3
        end

        Edge -.-> Region
    end

/>

- **Regions:** Physically separated geographic areas (e.g., `us-east-1` in N. Virginia, `eu-west-1` in Ireland). Each region operates completely independently to provide geographic fault tolerance.
- **Availability Zones (AZs):** One or more discrete data centers within a region, each with redundant power, networking, and cooling. Deploying across multiple AZs within a region provides resilience against data center outages without cross-region latency overhead.
- **Edge Locations:** Over 400 Points of Presence (PoPs) globally that cache data via Amazon CloudFront (CDN) and resolve DNS queries via Amazon Route 53 close to end users.

## 2. The Shared Responsibility Model

AWS defines a clear boundary between provider responsibilities and customer duties:

| Responsibility            | Managed By   | Examples                                                                                                                                 |
| :------------------------ | :----------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| **Security OF the Cloud** | **AWS**      | Physical facility security, server hardware, virtualization hypervisors, global network cables, facilities cooling and power.            |
| **Security IN the Cloud** | **Customer** | IAM user permissions, guest operating systems, firewall rules (Security Groups & NACLs), database encryption keys, and application code. |

## 3. Account Hygiene & Cost Guardrails

<Callout type="warn" title="Billing Warning: AWS Charges for Active Resources">
  Unlike platforms that offer a unified trial pool with hard cutoffs, AWS billing starts as soon as
  free-tier limits are crossed. Services such as NAT Gateways, provisioned IOPS disks, and
  relational database instances incur charges continuously once created. Establishing a budget alarm
  is the first mandatory operational task.
</Callout>

### Root Account Protection

The root user email and password possess unrestricted administrative power over all resources and billing.

1. Enable Multi-Factor Authentication (MFA) on the root user immediately.
2. Lock away the root credentials and do not create access keys for root.
3. Use **IAM Identity Center (AWS SSO)** or individual IAM users with least-privilege policies for daily engineering activities.

### Zero-Spend / Low-Threshold Budget Alerts

Using AWS Budgets, configure an automated email alert if estimated monthly charges exceed $1.00:

```bash
aws budgets create-budget \
  --account-id $(aws sts get-caller-identity --query Account --output text) \
  --budget file://budget-config.json \
  --notifications-with-subscribers file://budget-notifications.json
```

## 4. Programmatic Access via AWS CLI

Avoid creating long-lived static API access keys (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`) whenever possible. Instead, configure modern SSO-based authentication:

```bash
# Initiate browser-based SSO login
aws configure sso

# Verify your active identity
aws sts get-caller-identity
```
