## What is a decision model?

Most modern language systems rely on generative large language models (LLMs). Generative models predict the next token in an open-ended sequence, making them suitable for long-form drafting, summarization, and multi-step reasoning.

Decision models target a different layer of software logic. They execute System 1 tasks: immediate, repetitive, schema-bounded evaluations such as content moderation, ticket routing, sentiment scoring, intent detection, and policy verification.

## Why decision models differ from LLMs

A common question is why a dedicated decision model is needed when modern LLMs already support structured output via JSON mode or schema validation.

```
Why is this different from an LLM? I can get structured output from an LLM too.
```

The difference lies in the underlying execution architecture:

### 1. Autoregressive generation versus parallel evaluation

When an LLM produces structured output, it still operates autoregressively. The model samples every punctuation mark, quotation mark, key name, and whitespace character one token at a time:

```json
{ "category": "billing", "urgent": true }
```

Generating this 12-token JSON payload requires 12 sequential forward passes through the model's transformer layers. If the context window is large, each forward pass recomputes attention across past tokens.

Jev is non-autoregressive. It uses a parallel sampler that maps the input state directly to the allowed values in a single forward pass. It never emits `{`, `"`, or `:` characters. It evaluates the representations and populates the schema fields in one step.

### 2. Output space constraints

LLMs sample from a broad vocabulary of roughly 100,000 tokens. Even when constrained by grammar engines, the generative backbone retains the potential to hallucinate field values, drift into syntax errors on edge cases, or exceed token limits.

Jev restricts the output space to developer-defined types (enums, booleans, bounded numeric ranges). Because it lacks an open text generator, it cannot invent imaginary entities or output unparseable syntax.

## Performance and latency

Autoregressive LLM latency scales with the number of generated tokens. Even small JSON payloads take between 1,500 ms and 6,000 ms on frontier models.

Jev eliminates the autoregressive decode loop. Inference is bounded by a single representation pass over the input payload:

| Metric                  | Generative LLMs (e.g. GPT-5)    | Jev Decision Model           |
| :---------------------- | :------------------------------ | :--------------------------- |
| **Inference latency**   | 1,500 ms – 6,000 ms             | 70 ms – 500 ms               |
| **Execution pattern**   | Sequential token-by-token loop  | Single parallel forward pass |
| **Relative speed**      | Baseline (1x)                   | 4x to 200x faster            |
| **Multi-field latency** | Increases with every output key | Constant across all fields   |

Because Jev evaluates schema fields in parallel, adding additional questions to the evaluation schema does not increase response latency.

## Multiple questions in one pass

Production pipelines often need multiple checks on the same piece of data. For example, a customer support ticket requires checking urgency, sentiment, category, policy violations, and language.

Handling this with an LLM presents two inefficient options:

1. **Multiple API requests**: Fire five distinct prompts. This multiplies input token costs fivefold and increases network overhead.
2. **One large prompt**: Combine all questions into a complex prompt. This increases output token length, inflates generation time, and raises the likelihood of malformed JSON.

## Calibrated confidence scoring

Generative LLMs do not produce reliable confidence metrics. When prompted with questions like "How confident are you from 1 to 10?", models output verbalized estimations shaped by conversational tone and reinforcement learning with human feedback (RLHF). These self-reports correlate poorly with actual accuracy.

Similarly, extracting token log probabilities from an autoregressive stream produces scores distorted by sequence length and syntax tokens.

Jev is trained using **Reinforcement Learning for Calibrated Decisions (RLCD)**. Instead of optimizing for conversational preferences, RLCD trains the model's output probabilities to match empirical error rates.

```typescript
interface DecisionResult {
  category: 'refund' | 'technical_support' | 'account_access';
  isEscalationRequired: boolean;
  confidence: number; // Statistically calibrated [0.0 - 1.0]
}

// Calibrated scores enable direct thresholding in code
if (result.confidence >= 0.88 && !result.isEscalationRequired) {
  await dispatchAutoReply(ticket, result.category);
} else {
  await routeToHumanAgent(ticket);
}
```

When Jev outputs a confidence score of 0.85, the judgment is statistically accurate 85% of the time across that probability bucket. This calibration makes the confidence score usable as an automated gate in production logic.

## Hallucination immunity

Hallucination in language models occurs because generation is an open search problem over human vocabulary. Given an ambiguous prompt, a generative model will synthesize plausible words to complete the sentence.

Jev cannot hallucinate because it has no generative vocabulary head:

1. **Closed schema**: The output is bounded by explicit types (enumerations, booleans, floats).
2. **Discriminative evaluation**: Rather than asking what words come next, Jev scores predefined choices against the context vector.
3. **Determinism**: If an input does not match any valid category with high confidence, Jev outputs a low confidence score across all candidates, rather than fabricating a non-existent option.

## Architectural integration

Jev is designed to work alongside generative LLMs rather than replace them entirely. In production systems, Jev operates as the high-throughput decision filter in front of heavier generative models.
