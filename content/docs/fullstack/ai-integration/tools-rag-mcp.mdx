A support assistant answers "where is my order?" with a confident, invented tracking number. The model does not know the order; the app does. Tools let the model ask the app for live data, and retrieval puts the right documents in front of it, so answers come from the app's data instead of the model's memory.

---

## Tool calling

The app describes functions (name, description, JSON schema). The model replies with a `tool_use` block requesting a call; the app runs the function and sends back a `tool_result`; the model continues.

```ts
const tools: Anthropic.Tool[] = [
  {
    name: 'get_order_status',
    description: "Look up the status and tracking number of one of the current user's orders.",
    strict: true,
    input_schema: {
      type: 'object',
      properties: { order_id: { type: 'string', description: 'Order ID such as ord_981' } },
      required: ['order_id'],
      additionalProperties: false,
    },
  },
];

const messages: Anthropic.MessageParam[] = [{ role: 'user', content: userText }];
for (let step = 0; step < 5; step++) {
  // cap the loop
  const response = await client.messages.create({
    model: 'claude-opus-5-5',
    max_tokens: 16000,
    tools,
    messages,
  });
  messages.push({ role: 'assistant', content: response.content });
  if (response.stop_reason !== 'tool_use') return response;

  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const block of response.content) {
    if (block.type !== 'tool_use') continue;
    try {
      const output = await runTool(block.name, block.input, req.user); // authorise as this user
      results.push({ type: 'tool_result', tool_use_id: block.id, content: JSON.stringify(output) });
    } catch (e) {
      results.push({
        type: 'tool_result',
        tool_use_id: block.id,
        content: String(e),
        is_error: true,
      });
    }
  }
  messages.push({ role: 'user', content: results }); // all results in one message
}
```

The SDKs also ship a **tool runner** helper that drives this loop. Rules that matter more than the loop:

- **Tools run with the user's permissions**, never the service's. `get_order_status` must check the order belongs to `req.user`. The model is not an authorization layer.
- Read-only tools are safe to auto-run; tools that change state (refund, delete, send email) need confirmation in the UI or strict limits.
- Cap iterations and total tokens; log every tool call.

```sql
CREATE EXTENSION vector;
CREATE TABLE doc_chunks (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doc_id    bigint NOT NULL REFERENCES docs(id) ON DELETE CASCADE,
  org_id    uuid NOT NULL,                 -- permission filter
  content   text NOT NULL,
  embedding vector(1024) NOT NULL          -- dimension of the chosen embedding model
);
CREATE INDEX ON doc_chunks USING hnsw (embedding vector_cosine_ops);

SELECT content, doc_id FROM doc_chunks
WHERE org_id = $2
ORDER BY embedding <=> $1
LIMIT 8;
```

Practical points:

- **Chunk** by structure (headings, paragraphs), a few hundred tokens with small overlap; keep titles and URLs as metadata.
- **Embedding models** come from a separate API (Voyage AI, OpenAI, Cohere, or open models); re-embed everything if the model changes.
- **Hybrid search** (vector + full-text, merged with reciprocal rank fusion) beats either alone; see [Search](/fullstack/search/search-engines-and-vectors).
- **Filter by permissions in the query**, so retrieval never surfaces another tenant's documents.
- Ask for **citations** and show sources; it lets users verify and exposes hallucinations.
- With million-token context windows, small corpora can be passed whole; retrieval still wins on cost, latency, and freshness for large or changing data.

The full RAG pipeline (parsing, chunking strategies, rerankers, evaluation) is covered in [RAG](/ai/rag).

## MCP

The **Model Context Protocol** standardises how AI clients (Claude, ChatGPT, IDE assistants, agents) discover and call tools and read resources from external servers. Instead of building a custom integration per AI client, an app exposes one MCP server.

| MCP concept | Meaning                                                  |
| :---------- | :------------------------------------------------------- |
| Server      | Exposes tools, resources (readable data), and prompts    |
| Client      | AI application connecting to servers                     |
| Transport   | stdio for local servers; Streamable HTTP for remote ones |
| Auth        | Remote servers use OAuth 2.1 with PKCE                   |

```ts
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { z } from 'zod';

const server = new McpServer({ name: 'shop', version: '1.0.0' });
server.registerTool(
  'get_order_status',
  {
    description: "Status of one of the signed-in user's orders",
    inputSchema: { orderId: z.string() },
  },
  async ({ orderId }, extra) => {
    const order = await orders.getForUser(userFrom(extra), orderId);
    return { content: [{ type: 'text', text: JSON.stringify(order) }] };
  },
);
```

Python servers use the official SDK's `FastMCP` class with decorated functions. The same authorization rules as tool calling apply: an MCP server is a public API whose caller is an AI acting for a user.
