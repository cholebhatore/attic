Accessibility and SEO overlap more than they look: both depend on machines understanding the page. A screen reader and a search crawler both read the same structure, headings, link text, and alt text.

---

## The plain-language version

**Accessibility** (a11y) means people using screen readers, keyboards, voice control, or zoom can use the site. The browser builds an **accessibility tree** from the HTML; assistive tech reads that tree. **SEO** means search engines can crawl, understand, and rank the page.

| Word                | Plain meaning                                                                    |
| :------------------ | :------------------------------------------------------------------------------- |
| **WCAG**            | Web Content Accessibility Guidelines; levels A, AA, AAA. AA is the usual target. |
| **ARIA**            | Attributes that add roles and states for assistive tech.                         |
| **accessible name** | What a screen reader announces for an element.                                   |
| **focus**           | The element receiving keyboard input.                                            |
| **crawl / index**   | A search bot fetching pages / storing them for search.                           |
| **canonical URL**   | The preferred URL when several show the same content.                            |

## Accessibility essentials

WCAG's four principles: perceivable, operable, understandable, robust.

- **Text alternatives**: `alt` on informative images, `alt=""` on decorative ones.
- **Keyboard**: everything clickable reachable with Tab, activated with Enter/Space. Visible focus styles (`:focus-visible`), never `outline: none` without a replacement.
- **Focus management**: move focus into a modal on open, trap it, return it on close. On SPA route changes, move focus to the new heading.
- **Contrast**: at least 4.5:1 for body text, 3:1 for large text.
- **Motion**: honour `prefers-reduced-motion`.
- **Forms**: labels, error messages linked with `aria-describedby`, errors announced (`aria-live`).

### The rules of ARIA

1. Use a native element if one exists. No ARIA is better than bad ARIA.
2. Do not change native semantics (`<h2 role="button">`).
3. Interactive ARIA widgets must be keyboard-operable.
4. Do not hide focusable elements with `aria-hidden`.

Common patterns (tabs, combobox, menu) are specified in the [ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/). Headless libraries such as Radix and React Aria implement them; see [Design Systems](/fullstack/design-systems).

### Testing

axe DevTools or Lighthouse for automated checks (they catch roughly a third of issues), keyboard-only navigation, and a real screen reader (VoiceOver, NVDA). `eslint-plugin-jsx-a11y` and `@axe-core/playwright` in CI.

## SEO essentials

```html
<title>Running Shoes for Flat Feet · Shop</title>
<meta name="description" content="Stability running shoes tested on..." />
<link rel="canonical" href="https://shop.example.com/shoes/flat-feet" />
<meta property="og:title" content="Running Shoes for Flat Feet" />
<meta property="og:image" content="https://shop.example.com/og/flat-feet.png" />
<meta name="twitter:card" content="summary_large_image" />
```

- **Crawlability**: content present in server-rendered HTML ranks more reliably than content only rendered client-side. This is a major reason for [SSR and SSG](/fullstack/rendering).
- **`robots.txt`** controls crawling; `<meta name="robots" content="noindex">` controls indexing.
- **`sitemap.xml`** lists URLs to crawl.
- **Structured data** (JSON-LD with schema.org types like `Product`, `Article`) enables rich results.
- **Performance**: Core Web Vitals are a ranking signal.
- Descriptive link text ("pricing details", not "click here") helps both screen readers and crawlers.

Next.js generates these from the `metadata` export and `sitemap.ts`/`robots.ts` files; see [the App Router](/fullstack/rendering/nextjs-app-router).
