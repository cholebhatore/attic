A team argues for an hour about "JWT vs Bearer auth" and "OAuth2 vs our own login". Both arguments compare things that are not alternatives to each other. Before choosing anything, it helps to know which question each term answers.

---

## The plain-language version

**Authentication** is proving identity, like showing a passport at the border. **Authorization** is deciding what that person may do, like a ticket that only opens certain doors. Login authenticates once; after that, a **session ID** or **token** stands in for the password on every request.

Topics: AuthN vs AuthZ, why tokens exist, the three layers.

| Word           | Plain meaning                                                      |
| :------------- | :----------------------------------------------------------------- |
| **AuthN**      | Authentication: verifying an identity claim.                       |
| **AuthZ**      | Authorization: deciding whether an identity may perform an action. |
| **credential** | Something that proves identity: password, key, token, passkey.     |
| **principal**  | The authenticated entity: a user, service, or device.              |
| **session ID** | Random reference to server-held login state.                       |
| **token**      | A credential issued after login and presented on later requests.   |

## Authentication vs authorization

**Authentication (AuthN)** answers _"who is this?"_: verifying an identity claim (a user, service, or device) against known credentials.

**Authorization (AuthZ)** answers _"what may this identity do?"_: deciding whether an already-authenticated identity can perform an action.

They get confused because the same word, "auth", and often the same request cycle handle both. A login flow authenticates; a scope or role check on a protected endpoint authorizes. OAuth 2.0, despite the name, is primarily an **authorization** framework, not an authentication one. That distinction comes back in [OAuth 2.0 and OIDC](/fullstack/auth/oauth2-and-oidc).

The HTTP status codes follow the same split: `401` means not authenticated, `403` means authenticated but not authorized.

---

## Why not send the password every time?

After a successful login, the browser could in principle send the email and password with every request. Session IDs and tokens exist instead for four reasons:

1. **Security**: sending the password on every request multiplies the chances of exposing it (logs, proxies, a compromised page). A leaked session can be revoked; a leaked password works everywhere the user reused it.
2. **Convenience**: the user logs in once instead of providing credentials repeatedly.
3. **Performance**: verifying a password uses deliberately slow hashing ([Argon2 or bcrypt](/fullstack/auth/password-storage)), often 100 ms or more of CPU. Looking up a session or verifying a token signature is far cheaper.
4. **Password independence**: if the user changes their password, the server can invalidate existing sessions or tokens according to its policy, without the password being resent constantly. Sessions can also carry their own expiry, device info, and scope, which a password cannot.

## The three layers people conflate

Auth concepts live at **three separate layers**. Mixing them up is why terms seem to overlap when they do not.

| Layer                         | Question it answers                                          | Examples                                                      |
| :---------------------------- | :----------------------------------------------------------- | :------------------------------------------------------------ |
| **Framework / protocol**      | What is the overall trust and delegation model?              | OAuth 2.0, OpenID Connect (OIDC), SAML                        |
| **Scheme / method**           | How is the credential transmitted on the wire?               | Basic, Digest, Bearer, API key (header/query), session cookie |
| **Token / credential format** | What does the credential look like, and how is it validated? | Opaque random string, JWT, SAML assertion (XML)               |

A real system usually stacks all three. For example: OAuth 2.0 (framework) issues an access token that is a JWT (format), sent using the Bearer scheme (method) in the `Authorization` header.

Keeping these three questions separate resolves almost every "isn't X the same as Y" confusion. "JWT vs Bearer" compares a format with a scheme; "OAuth2 vs sessions" compares a delegation framework with a state model.

## Interview questions

<Accordions>
  <Accordion title="What is the difference between authentication and authorization?">
    Authentication proves who someone is. Authorization determines what they are allowed to do after
    their identity has been established.
  </Accordion>
  <Accordion title="After login, why doesn't the browser just send the email and password with every request?">
    Security (less exposure of a reusable secret), convenience (log in once), performance (password
    hashing is deliberately slow; session lookup or signature checks are cheap), and control
    (sessions and tokens can expire, be scoped, and be revoked independently of the password).
  </Accordion>
  <Accordion title="Is OAuth 2.0 an authentication protocol?">
    No. It is a delegated authorization framework. OpenID Connect adds authentication on top of it.
  </Accordion>
</Accordions>
