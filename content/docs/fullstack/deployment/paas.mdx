A PaaS turns "push to Git" into a running, HTTPS-enabled app with logs, rollbacks, and preview environments, without managing servers. The trade-off is less control, platform-specific limits, and costs that grow faster than raw compute.

---

## Platforms

| Platform                         | Best at                                                 | Notes                                                                                                               |
| :------------------------------- | :------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------ |
| Vercel                           | Next.js and frontend frameworks                         | Serverless/edge functions, image optimisation, previews per PR; long-running processes and WebSockets not supported |
| Netlify                          | Static and Jamstack sites                               | Functions, forms, edge functions                                                                                    |
| Cloudflare Workers / Pages       | Edge apps, static sites                                 | Very low latency globally; Workers runtime (not full Node); D1, R2, KV, Durable Objects                             |
| Render                           | Web services, workers, cron, managed Postgres and Redis | Heroku-like, Docker or native builds                                                                                |
| Railway                          | Fast setup of services and databases from a canvas      | Usage-based pricing                                                                                                 |
| Fly.io                           | Containers close to users in many regions               | Machines API, volumes, global Anycast                                                                               |
| Heroku                           | Classic buildpack PaaS                                  | Mature, pricier                                                                                                     |
| Google Cloud Run, AWS App Runner | Containers with scale to zero on a hyperscaler          | Fits teams already on that cloud                                                                                    |

Data services: Neon, Supabase, PlanetScale, Turso (databases); Upstash, Redis Cloud (Redis); Cloudflare R2, S3 (storage).

## Configuration

- **Build command** and **start command** (or a Dockerfile).
- **Environment variables** per environment (development, preview, production); frontend-exposed variables (`NEXT_PUBLIC_*`, `VITE_*`) are public.
- **Health check path** so the platform knows when a new version is ready before switching traffic.
- **Custom domain**: add a CNAME (or A record at the apex) and the platform issues certificates.
- **Regions**: put the app in the same region as its database; cross-region queries add tens of milliseconds each.

---

## Preview environments

Every pull request gets its own deployment URL, often with a database branch (Neon, PlanetScale, Supabase branching) so reviewers can test real changes. Protect previews from search indexing and from public access when they contain real data.

## Limits to know

| Limit                                          | Impact                                                                     |
| :--------------------------------------------- | :------------------------------------------------------------------------- |
| Function execution time                        | Long jobs must move to queues or background workers                        |
| Request and response body size                 | Large uploads go direct to object storage                                  |
| No persistent local disk                       | Files go to object storage                                                 |
| Cold starts on scale-to-zero                   | First request slow; keep a minimum instance for latency-sensitive services |
| Connection limits to databases from serverless | Use poolers or HTTP-based drivers                                          |
| Egress and per-seat pricing                    | Bills grow with traffic and team size                                      |

A common progression: start fully on PaaS, then move steady, heavy workloads to containers on a cloud or VPS when the bill or the limits justify the operations work.
