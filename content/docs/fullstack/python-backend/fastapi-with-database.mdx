This page connects the FastAPI app to PostgreSQL with SQLAlchemy 2.0 and versioned migrations with Alembic. The same structure scales from a weekend project to a production service.

---

## The plain-language version

**SQLAlchemy** maps Python classes to tables and builds SQL. An **engine** owns the connection pool; a **session** is a unit of work for one request. **Alembic** records schema changes as migration files that run in order, like Git commits for the database schema.

| Word                  | Plain meaning                                                |
| :-------------------- | :----------------------------------------------------------- |
| **engine**            | Connection pool + dialect for one database.                  |
| **session**           | Tracks loaded objects and changes; commits as a transaction. |
| **declarative model** | Class mapped to a table.                                     |
| **migration**         | Versioned script that changes the schema.                    |
| **eager loading**     | Loading related rows in the same query batch.                |

## Settings and engine

```python title="src/app/settings.py"
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env")
    database_url: str = "postgresql+asyncpg://postgres:postgres@localhost:5432/shop"
    debug: bool = False

settings = Settings()
```

```python title="src/app/db.py"
from collections.abc import AsyncIterator
from typing import Annotated
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
from .settings import settings

engine = create_async_engine(settings.database_url, pool_size=10, max_overflow=5, pool_pre_ping=True)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:
        yield session

DbSession = Annotated[AsyncSession, Depends(get_session)]
```

## Models

```python title="src/app/orders/models.py"
from datetime import datetime
from sqlalchemy import ForeignKey, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase): ...

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(unique=True, index=True)
    orders: Mapped[list["Order"]] = relationship(back_populates="user")

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    status: Mapped[str] = mapped_column(default="pending")
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    user: Mapped[User] = relationship(back_populates="orders")
```

## Service and route

```python title="src/app/orders/service.py"
from sqlalchemy import select
from sqlalchemy.orm import selectinload

async def list_orders_with_users(session: AsyncSession, limit: int) -> list[Order]:
    stmt = select(Order).options(selectinload(Order.user)).order_by(Order.id.desc()).limit(limit)
    return list((await session.scalars(stmt)).all())   # 2 queries total, not 1 + N

async def create_order(session: AsyncSession, user_id: int) -> Order:
    order = Order(user_id=user_id)
    session.add(order)
    await session.commit()
    return order
```

```python title="src/app/orders/router.py"
@router.post("", status_code=201)
async def create(body: OrderIn, session: DbSession, user: CurrentUser) -> OrderOut:
    order = await create_order(session, user.id)
    return OrderOut.model_validate(order, from_attributes=True)
```

In async SQLAlchemy, lazy loading a relationship (accessing `order.user` without loading it) raises an error instead of silently running a query. That forces explicit eager loading, which prevents the [N+1 problem](/fullstack/databases/migrations-and-orms).

## Alembic migrations

```bash
uv add alembic
uv run alembic init -t async migrations
# set target_metadata = Base.metadata in migrations/env.py
uv run alembic revision --autogenerate -m "create users and orders"
uv run alembic upgrade head
uv run alembic downgrade -1
```

Always review autogenerated migrations; renames show up as drop + add, which loses data. Run migrations as a deploy step, not on app startup across many replicas.
