An API is a contract that outlives the code behind it. A sloppy endpoint can be fixed in a day; a sloppy public contract has to be supported for years because clients depend on it.

---

## API styles at a glance

| Style           | Shape                               | Transport      | Strengths                           | Weak at                                   | Typical use                          |
| :-------------- | :---------------------------------- | :------------- | :---------------------------------- | :---------------------------------------- | :----------------------------------- |
| REST            | Resources + HTTP verbs              | HTTP/JSON      | Simple, cacheable, universal        | Over/under-fetching, many round trips     | Public and most internal APIs        |
| GraphQL         | One endpoint, client-shaped queries | HTTP/JSON      | Exact data per screen, typed schema | HTTP caching, query cost control          | Rich frontends, many clients         |
| gRPC            | RPC methods, Protobuf               | HTTP/2, binary | Fast, typed, streaming              | Browsers need a proxy, not human-readable | Service-to-service                   |
| tRPC            | TS functions                        | HTTP/JSON      | End-to-end types, no codegen        | TypeScript-only                           | Full-stack TS apps                   |
| Webhooks        | Server calls client on events       | HTTP POST      | Push instead of polling             | Delivery and security                     | Payments, integrations               |
| WebSocket / SSE | Messages over a long connection     | WS / HTTP      | Real-time                           | Scaling, state                            | See [Real-time](/fullstack/realtime) |
| SOAP            | XML envelopes, WSDL                 | HTTP/XML       | Formal contracts, WS-Security       | Verbose                                   | Legacy enterprise, banking           |
