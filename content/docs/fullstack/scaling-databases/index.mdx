Sharding is the most-discussed and least-needed database scaling technique. Most apps that "need to shard" need an index, a cache, a pooler, or a bigger instance. Scale in order of increasing cost and complexity, and measure before each step.

---

## The ladder

| Step                       | Fixes                                                                            | Cost                        |
| :------------------------- | :------------------------------------------------------------------------------- | :-------------------------- |
| 1. Fix queries and indexes | Slow queries, N+1, missing indexes ([Profiling](/fullstack/databases/profiling)) | Low                         |
| 2. Cache hot reads         | Repeated identical reads ([Caching](/fullstack/caching))                         | Low to medium; invalidation |
| 3. Vertical scaling        | CPU, RAM, IOPS limits; a modern single server handles a lot                      | Money; has a ceiling        |
| 4. Connection pooling      | Too many connections                                                             | Low                         |
| 5. Read replicas           | Read-heavy load                                                                  | Replication lag to handle   |
| 6. Partition big tables    | Huge tables, slow maintenance, time-based data                                   | Medium                      |
| 7. Move workloads out      | Analytics to a warehouse, search to a search engine, queues to a broker          | Medium                      |
| 8. Shard / distributed SQL | Write volume or data size beyond one primary                                     | High                        |
