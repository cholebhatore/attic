Enterprise jobs often involve SQL Server or Oracle, because the systems that run payroll, banking, and ERP were built on them decades ago. NoSQL databases, meanwhile, are a family of very different tools grouped only by not being relational.

---

## Microsoft SQL Server

- T-SQL dialect: `TOP` instead of `LIMIT` (or `OFFSET ... FETCH`), `IDENTITY`, `MERGE`, stored procedures used heavily.
- Default isolation read committed with locking; **read committed snapshot isolation** (RCSI) gives MVCC-like behaviour and is commonly enabled.
- Strong tooling: SQL Server Management Studio, Query Store (plan history and regression detection), integration with Power BI and .NET (Entity Framework).
- High availability with Always On availability groups. Runs on Linux and in containers; Azure SQL Database is the managed version.
- Editions: Express (free, size-limited), Developer (free, non-production), Standard, Enterprise.

---

## Oracle Database

- PL/SQL procedural language; sequences, packages, materialized views, flashback queries.
- **RAC** (Real Application Clusters): several servers sharing one database for availability and scale.
- Data Guard for standby replicas; partitioning and advanced compression are paid options.
- Licensing is per core and complex; cost is a major factor in migrations to PostgreSQL. Oracle Cloud offers Autonomous Database. Free tier: Oracle Database Free.

## NoSQL families

| Family      | Model                                  | Examples                             | Good for                                                      | Watch out for                                                                      |
| :---------- | :------------------------------------- | :----------------------------------- | :------------------------------------------------------------ | :--------------------------------------------------------------------------------- |
| Document    | JSON-like documents                    | MongoDB, Couchbase, Firestore        | Varied, nested records read as a whole                        | Joins and cross-document transactions are limited or costly; schema drift          |
| Key-value   | Key → value                            | Redis, DynamoDB, etcd                | Caching, sessions, simple lookups at huge scale               | Access patterns must be known upfront                                              |
| Wide-column | Rows with dynamic columns, partitioned | Cassandra, ScyllaDB, Bigtable        | Huge write throughput, time-ordered data                      | Query by partition key only; denormalize per query                                 |
| Graph       | Nodes and edges                        | Neo4j, Amazon Neptune                | Deep relationship traversals (social, fraud, recommendations) | Smaller ecosystem                                                                  |
| Time-series | Timestamped measurements               | TimescaleDB, InfluxDB, ClickHouse    | Metrics, IoT, analytics                                       | Updates and point lookups are secondary                                            |
| Vector      | Embeddings + ANN index                 | pgvector, Pinecone, Qdrant, Weaviate | Semantic search, RAG                                          | Approximate results; see [AI integration](/fullstack/ai-integration/tools-rag-mcp) |
| Search      | Inverted index                         | Elasticsearch, OpenSearch            | Full-text search                                              | Not a primary store; see [Search](/fullstack/search)                               |

### DynamoDB-style design

Single-table design models every entity in one table with composite keys (`PK = USER#19`, `SK = ORDER#2026-11-06#981`), shaped around known access patterns. Reads and writes stay fast at any scale, but a new query pattern can require new indexes or a data migration.

---

## When NoSQL fits

- Data is naturally document-shaped and read as a unit (product catalogues with varied attributes, CMS content).
- Scale or write volume beyond one relational primary, with simple access patterns.
- A specialised query type: graph traversal, time-series rollups, similarity search.

Otherwise, PostgreSQL with `jsonb` covers most "we need flexible schema" cases while keeping transactions, joins, and constraints. Choosing between models is covered in depth in [Databases](/db), including [schema on write vs read](/db/foundations/core-concepts/schema-on-write-vs-read) and [OLTP vs OLAP](/db/foundations/core-concepts/oltp-vs-olap).
