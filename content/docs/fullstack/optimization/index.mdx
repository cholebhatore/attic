Optimization without measurement tends to make code more complex without making it faster: memoising components that were never slow, caching queries that were never hot, rewriting a service in another language when the time was spent waiting on the network. The pages here start from the theory that predicts where time goes, then cover techniques for each part of the stack.

---

## The method

1. **Define the goal** in user-facing terms and percentiles: "p75 LCP under 2.5 s on mobile", "p99 checkout API latency under 400 ms at 500 requests per second".
2. **Measure in the field and in the lab.** Field data (real users, production traces) says whether there is a problem and where; lab tools (Lighthouse, profilers, load tests) explain why.
3. **Find the bottleneck**, the single biggest contributor. By [Amdahl's law](/fullstack/optimization/performance-theory), improving anything else has a small ceiling.
4. **Form a hypothesis and change one thing.**
5. **Measure again** under the same conditions; keep the change only if the numbers moved.
6. **Guard it**: performance budgets in CI, alerts on SLOs, regression tests, so the win does not erode.
