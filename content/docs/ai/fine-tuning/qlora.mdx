LoRA removes the optimizer state for the base model but keeps the base weights themselves in BF16. For an 8B model that is still 16 GB before activations, and for a 65B model it is 130 GB, which is more GPUs than most people have.

QLoRA (Dettmers et al., arXiv:2305.14314) quantizes the frozen weights to 4 bits. The headline result: finetune a 65B parameter model on a single 48 GB GPU while preserving full 16-bit finetuning task performance.

---

## The memory wall

Rough weights-only figures at BF16 against 4-bit:

| Model | BF16 weights | 4-bit weights | Fits on one 48 GB GPU at 4-bit |
| :---- | :----------- | :------------ | :----------------------------- |
| 7B    | 14 GB        | 3.5 GB        | Comfortably                    |
| 13B   | 26 GB        | 6.5 GB        | Comfortably                    |
| 33B   | 66 GB        | 17 GB         | Yes                            |
| 65B   | 130 GB       | 33 GB         | Yes                            |

The paper reports Guanaco variants at 7B, 13B, 33B, and 65B using 5 GB, 10 GB, 21 GB, and 41 GB of memory respectively. Those totals include the adapter, its optimizer state, activations, and the quantization constants, which is why the 65B figure sits above the 33 GB weight estimate.

---

## NF4

4 bits gives 16 distinct values. The question is which 16.

Standard 4-bit integer quantization spaces them evenly. That is the wrong choice for neural network weights, which are approximately normally distributed with mean zero: dense near the middle, sparse in the tails. Evenly spaced values put half the representable range in a region almost no weight occupies.

NF4 spaces the 16 values by the _quantiles_ of a standard normal distribution. Each value is placed so that, for normally distributed data, the bins between them have equal expected occupancy. Every representable value carries the same amount of information, which is what the paper means by information-theoretically optimal for zero-mean normal data.

Two implementation details matter:

- **Asymmetric type.** Weight blocks are normalized into `[-1, 1]`, and NF4 has one more negative than positive value, matching the way normal quantiles fall around zero.
- **Blockwise quantization.** The absmax scale is computed per block of 64 weights, not per tensor. Outliers are contained inside their own block instead of stretching the scale for the whole matrix.

```text
For each block of 64 weights:
  c = absmax(block)                       # one FP32 scale per block
  q = round_to_nearest_nf4(block / c)     # 4-bit index into the NF4 table
  store q (4 bits each) and c (32 bits)
```

At inference and during the forward pass, blocks are dequantized back to BF16 on the fly. The 4-bit form is storage; computation still happens in 16-bit.

## Double quantization

Blockwise quantization has an overhead the naive calculation misses. One FP32 scale per 64 weights is `32 / 64 = 0.5` bits per parameter, which on a 65B model is about 4 GB. That is 10% of the weight budget spent on scales.

QLoRA quantizes the scales themselves:

| Level  | What is quantized          | Block size | Precision |
| :----- | :------------------------- | :--------- | :-------- |
| First  | The weights                | 64         | NF4       |
| Second | The first-level scales `c` | 256        | FP8       |

Each second-level block of 256 FP32 scales gets its own FP32 absmax. The arithmetic works out to a saving of 0.37 bits per parameter, which on 65B is roughly 3 GB.

Double quantization is on by default in the `bitsandbytes` QLoRA path and costs a little extra compute per dequantization.

---

## Paged optimizers

The adapter is small, so its optimizer state is small, and neither should overflow memory. But GPU allocation is not smooth: a batch with an unusually long sequence, or a gradient-accumulation spike, can request a large contiguous block and hit `CUDA out of memory` even when total free memory looks sufficient.

Paged optimizers use the NVIDIA unified memory feature to do automatic page-to-page transfers between CPU and GPU. Optimizer state lives in pageable memory and is moved to the device when the update needs it, so a spike evicts pages instead of failing the allocation.

The trade-off is speed. A step that pages state across PCIe is much slower than one that does not. Paged optimizers are insurance against a crash, not a performance feature.

## The full recipe

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, prepare_model_for_kbit_training, get_peft_model

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",           # "fp4" is the evenly spaced alternative
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-70B",
    quantization_config=bnb,
    device_map="auto",
)
model = prepare_model_for_kbit_training(model)   # casts norms to fp32, enables input grads

model = get_peft_model(model, LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
))
model.print_trainable_parameters()
```

`prepare_model_for_kbit_training` is the step people forget. It upcasts the LayerNorm parameters to FP32 and enables gradient computation on inputs, both of which a 4-bit forward pass needs. Skipping it produces a run that either errors or converges badly.

`bnb_4bit_compute_dtype` controls the dtype the weights are dequantized into for the matmul. BF16 on Ampere and newer; FP16 if you must. Keeping it at FP32 defeats most of the speed benefit.

## What QLoRA costs

| Cost                           | Detail                                                     |
| :----------------------------- | :--------------------------------------------------------- |
| Slower forward pass            | Every layer dequantizes its blocks before the matmul       |
| No quantization of the adapter | LoRA weights stay in full precision; they are small anyway |
| bitsandbytes dependency        | CUDA-specific; ROCm and Metal support are partial          |
| Harder debugging               | Numerics differ subtly from a BF16 run                     |
| Serving divergence             | A merged adapter must be re-quantized for 4-bit serving    |

The last one is an operational trap. If you train against 4-bit weights and then merge and serve in BF16, or serve through a different quantization scheme, the deployed model is not the model you evaluated.

---

## Choosing

| Method         | 8B memory, rough | Speed        | When                                |
| :------------- | :--------------- | :----------- | :---------------------------------- |
| Full fine-tune | About 128 GB     | Fastest step | You have the cluster and the data   |
| LoRA           | About 20 GB      | Fast         | The model fits; you want simplicity |
| QLoRA          | About 8 GB       | Slower step  | The model does not fit              |

QLoRA trades wall-clock for reach. If a BF16 LoRA fits on your hardware, use it; the dequantization overhead is pure cost with no quality benefit, since the paper's own claim is that QLoRA matches 16-bit finetuning performance rather than beating it.

## Interview questions

1. What are the three components of QLoRA?

   4-bit NormalFloat quantization of the frozen base weights, double quantization of the per-block scales, and paged optimizers to survive memory spikes. LoRA adapters are trained on top in full precision.

2. Why is NF4 better than evenly spaced 4-bit integers?

   Neural network weights are approximately normally distributed with mean zero, so they cluster near zero and thin out in the tails. Evenly spaced values waste half their range on a region almost no weight occupies. NF4 places its 16 values at the quantiles of a standard normal, so each bin has equal expected occupancy and each value carries the same information.

3. What is double quantization and how much does it save?

   Blockwise quantization stores one FP32 scale per 64 weights, which is 0.5 bits of overhead per parameter. Double quantization quantizes those scales to FP8 in blocks of 256 with their own FP32 absmax, saving 0.37 bits per parameter, roughly 3 GB on a 65B model.

4. What problem do paged optimizers solve?

   Not total memory but allocation spikes. An unusually long sequence or a gradient-accumulation peak can request a large contiguous block and fail even when free memory looks adequate. Paged optimizers use NVIDIA unified memory to move optimizer state between CPU and GPU automatically, so a spike evicts pages instead of crashing.

5. Why does the base weight have to be dequantized during training?

   The 4-bit form is a storage format. The matmul runs in BF16, so each layer dequantizes its blocks on the fly during the forward pass and again during the backward pass. This is the main reason QLoRA has a slower step than a BF16 LoRA run.

6. What does `prepare_model_for_kbit_training` do and why is it needed?

   It upcasts the normalization layer parameters to FP32 and enables gradient computation on the model inputs. Normalization statistics are sensitive to low precision, and gradients must flow through the frozen quantized weights to reach the adapters below them.

7. Guanaco reportedly reaches 99.3% of ChatGPT on the Vicuna benchmark. What was the training budget?

   24 hours of finetuning on a single GPU, for the 65B variant. The paper's broader claim is that QLoRA finetuning matches full 16-bit finetuning performance across the model sizes they tested.

8. When would you choose plain LoRA over QLoRA?

   Whenever the BF16 base model fits in memory. QLoRA's own claim is parity with 16-bit finetuning, not superiority, so the dequantization overhead and the bitsandbytes dependency are pure cost when you do not need the memory saving.

9. You trained with QLoRA and are deploying with vLLM at FP8. What should you check?

   That the served model is the model you evaluated. You trained against NF4-quantized weights and merged an adapter into them; serving applies a different quantization to the merged result. Re-run your evaluation against the actual served artifact rather than the training checkpoint.
