**Transfer learning** is reusing what a model learned on one task as the starting point for another. A network trained on the 1.28 million images of ImageNet has already learned to detect edges, textures, and object parts, and those features are useful for almost any image task. Starting from it instead of from random weights needs far less data and compute. An **ensemble** combines the predictions of several trained models, usually by averaging; because different models make different mistakes, the average is more accurate than any single member.

A vision network is divided into two parts for transfer: the **backbone**, the large stack of layers that turns an image into a feature vector and is reused, and the **head**, the small final layer that maps features to the task's classes and is replaced.

**Builds on:** [CNN Architectures](/ai/classical-deep-learning/vision-architectures) for backbones and `timm`, and [Overfitting and Regularization](/ai/neural-networks/regularization), since both techniques are ultimately about generalizing from limited data.

## Transfer learning

Convolutional features are hierarchical and mostly task-agnostic at the low end. Layer one of an ImageNet network learns oriented edges, layer four learns textures and corners, layer ten learns object parts. None of that is specific to ImageNet's thousand classes, so a model trained to classify dogs has already learned most of what it needs to classify defects in welds.

Three regimes, in increasing cost:

| Regime            | Trainable                        | When to use                           |
| :---------------- | :------------------------------- | :------------------------------------ |
| Linear probe      | Head only                        | Fewer than about 1000 labelled images |
| Partial fine-tune | Head plus last one or two stages | A few thousand images                 |
| Full fine-tune    | Everything                       | Tens of thousands, or a domain shift  |

### Linear probing

Freeze the backbone, replace the classifier, train only the new head.

```python title="probe.py"
import timm
import torch.nn as nn

model = timm.create_model("convnext_base.fb_in22k_ft_in1k", pretrained=True, num_classes=0)
for p in model.parameters():
    p.requires_grad = False
model.eval()

head = nn.Linear(model.num_features, 7)   # 7 target classes
net = nn.Sequential(model, head)
opt = torch.optim.AdamW(head.parameters(), lr=1e-3, weight_decay=0.01)
```

Two details that go wrong often. `requires_grad = False` does not stop BatchNorm from updating its running statistics, so the frozen part must also be put in `model.eval()`, or better, freeze norm layers explicitly:

```python
from timm.layers import BatchNormAct2d

for m in model.modules():
    if isinstance(m, (nn.BatchNorm2d, BatchNormAct2d)):
        m.eval()
```

And `num_classes=0` strips the head and returns pooled features, whose width is on `model.num_features`. Guessing `2048` will be wrong for anything that is not a ResNet.

### Fine-tuning

Unfreezing everything works better when there is enough data, but the early layers should move slowly. A single learning rate for the whole model is the usual mistake: it is either too small for the new head or too large for the pretrained weights.

```python title="finetune.py"
param_groups = [
    {"params": head.parameters(), "lr": 1e-3},
    {"params": model.layer4.parameters(), "lr": 1e-4},
    {"params": [p for n, p in model.named_parameters() if not n.startswith("layer4")], "lr": 1e-5},
]
opt = torch.optim.AdamW(param_groups, weight_decay=0.01)
```

The alternative is staged unfreezing: train the head for a few epochs, unfreeze the last stage, train, unfreeze the next stage, and so on. It is slower to set up and mostly equivalent to discriminative learning rates, so pick one.

<Callout type="warn">
  ### Catastrophic forgetting

Fine-tuning on a narrow dataset overwrites the general features the backbone learned. Accuracy on the new task goes up and the model's behaviour on anything else degrades, sometimes badly. Low learning rates, weight decay, early stopping, and LoRA on the projection weights all slow this down. If the backbone is needed for more than one task afterwards, keep the original checkpoint and train adapters instead of the base weights.

</Callout>

### Domain gap

Pretraining helps in proportion to how similar the target domain is. Natural images to natural images transfers well. Natural images to satellite, medical, or spectrogram data transfers much less, and in those cases a self-supervised pretraining run on unlabelled target-domain images often beats an ImageNet initialization. Check whether the checkpoint's normalization statistics are anywhere near the target data before concluding that the backbone is useless.

## Ensembles

Training `M` models and averaging them is the most reliable accuracy improvement available for free compute. On ImageNet an ensemble of five ResNets typically gains two to three points over the single best member.

### What to average

| Method                | Formula                                 | Notes                                   |
| :-------------------- | :-------------------------------------- | :-------------------------------------- |
| Logit averaging       | `mean(logits_m)` then `argmax`          | Cheapest, works with `CrossEntropyLoss` |
| Probability averaging | `mean(softmax(logits_m))` then `argmax` | Standard, better calibrated             |
| Geometric averaging   | `softmax(mean(log_softmax(logits_m)))`  | Sharper, closer to logit averaging      |
| Label averaging       | Average the predicted class labels      | Loses confidence, rarely used           |

Averaging logits and averaging probabilities give different answers when the members disagree in confidence. Logit averaging lets one very confident member dominate. Probability averaging caps each member's contribution at `1.0`, which is usually the desired behaviour.

```python title="ensemble.py"
import torch
import torch.nn.functional as F

@torch.no_grad()
def predict(models, x, temperature=1.0):
    probs = [F.softmax(m(x) / temperature, dim=-1) for m in models]
    return torch.stack(probs).mean(0)
```

Temperature above `1.0` flattens each member's distribution before averaging, which reduces the influence of overconfident members. It is one of the better single knobs on ensemble accuracy.

### Bagging

Bagging trains members on different bootstrap samples of the training set. In deep learning the members already differ by random initialization, augmentation order, and shuffling, so plain repeated training gets most of the diversity that explicit resampling would. Bagging still helps when the dataset is small enough that all members converge to nearly the same weights.

Related diversity sources:

| Technique          | Diversity comes from                      | Cost     |
| :----------------- | :---------------------------------------- | :------- |
| Repeated training  | Seed, init, data order                    | `M` runs |
| Bagging            | Bootstrap resampling                      | `M` runs |
| Snapshot ensembles | Cyclic LR restarts, saved at each minimum | `1` run  |
| SWA                | Averaging weights along one trajectory    | `1` run  |
| Multi-crop         | Different input resolutions per member    | `M` runs |
| Cross-architecture | Different model families entirely         | `M` runs |

Snapshot ensembles use a cosine schedule with warm restarts and save a checkpoint at every cycle minimum. Each minimum is a different local basin, so one training run produces several usable members. SWA instead averages the weights themselves over the last portion of training, which works because SGD trajectories stay in one broad basin.

Cross-architecture ensembles gain the most, because a ConvNeXt and a Swin transformer make genuinely different mistakes.

### Vectorized evaluation with vmap

Looping over `M` models launches `M` sets of kernels. If the members share an architecture, their parameters can be stacked and evaluate all of them in one batched call.

```python title="vmap_ensemble.py"
from torch.func import vmap, functional_call

models = [build_model(seed=s) for s in range(5)]
params = [dict(m.named_parameters()) for m in models]
buffers = [dict(m.named_buffers()) for m in models]

stacked_p = {k: torch.stack([p[k] for p in params]) for k in params[0]}
stacked_b = {k: torch.stack([b[k] for b in buffers]) for k in buffers[0]}

def predict_one(p, b, x):
    return functional_call(model, (p, b), (x,))

# one model per vmapped dim, batch shared across all of them
logits = vmap(predict_one, in_dims=(0, 0, None))(stacked_p, stacked_b, x)
print(logits.shape)                        # (5, B, num_classes)
probs = logits.softmax(-1).mean(0)         # (B, num_classes)
```

`in_dims=(0, 0, None)` maps over the leading dimension of the parameters and buffers while broadcasting `x` unchanged. The result has a new leading axis of size `5`. This is the same mechanism `torch.func.vmap` provides for per-sample gradients, and it is what makes large ensembles and multi-seed evaluation practical.

The catch is memory: stacking `M` copies of the weights holds `M` models resident at once. For `M = 5` on a ResNet-50 that is about `500 MB`, and on a ConvNeXt-Large it is several GB.

<Callout type="info">
  ### Ensembles at inference time

An ensemble costs `M` times the latency and memory of one model. Production systems usually distil the ensemble into a single student instead of shipping all members. Distillation is covered in [Phase 7](/ai/fine-tuning); the short version is that the student trains against the ensemble's averaged probabilities rather than the hard labels, and recovers most of the gain at single-model cost.

</Callout>

## Key terms

| Term                                        | Meaning                                                                                                                                            |
| :------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| **pretrained model**                        | A model already trained on a large dataset, used as a starting point.                                                                              |
| **backbone / feature extractor**            | The main body of the network, which produces a feature vector for each image.                                                                      |
| **head**                                    | The task-specific final layer(s) on top of the backbone.                                                                                           |
| **freezing**                                | Setting `requires_grad = False` on the backbone so its weights do not change during training.                                                      |
| **linear probing**                          | Freeze the whole backbone and train only a new linear head. Fast, and a measure of how good the features already are.                              |
| **fine-tuning**                             | Also update some or all backbone weights, usually with a small learning rate. Slower, but adapts further.                                          |
| **domain gap**                              | How different the target images are from the pretraining images (for example, X-rays versus everyday photos). A bigger gap needs more fine-tuning. |
| **ImageNet-1k / -22k**                      | The standard pretraining datasets, with about 1,000 and about 22,000 classes.                                                                      |
| **ensemble**                                | Several models whose predictions are combined.                                                                                                     |
| **logit averaging / probability averaging** | Combining raw scores versus combining softmax probabilities. They give different answers when the models disagree in confidence.                   |
| **bagging**                                 | Bootstrap aggregating: train each model on a random resample of the data (drawn with replacement), then average them.                              |
| **`vmap`**                                  | A PyTorch function that runs the same code over a batch of models (or inputs) at once, instead of in a Python loop.                                |

## Interview questions

<Accordions>
  <Accordion title={<>What does <code>requires_grad = False</code> fail to freeze, and how is it fixed?</>}>

    BatchNorm running statistics. Setting `requires_grad = False` stops the weights and biases from receiving updates, but a module still in train mode recomputes and overwrites its running mean and variance on every forward pass, so the frozen backbone slowly drifts. Put the frozen part in `model.eval()`, or freeze the normalization layers explicitly.

  </Accordion>
  <Accordion title="When is a linear probe preferable to full fine-tuning?">

    Below roughly a thousand labelled images, or when the backbone must stay reusable across several tasks. Low and mid features are task-agnostic, so a head trained on frozen pooled features reaches good accuracy in minutes on one GPU, and with 800 images it is hard to beat because full fine-tuning has nothing to learn from and overfits.

  </Accordion>
  <Accordion title="Why use discriminative learning rates instead of one rate for the whole model?">

    Early layers encode edges and textures that transfer as they are and would be damaged by a large step; the new head starts random and needs one. A single rate forces a compromise that is wrong at both ends. The usual setting is the head at, say, `1e-3` and the backbone an order of magnitude lower, with later stages allowed more than earlier ones.

  </Accordion>
  <Accordion title="What is catastrophic forgetting in fine-tuning, and what mitigates it?">

    Fine-tuning on task B overwrites weights tuned for task A, and A's accuracy drops, sharply when B is small or narrow. Mitigations: freeze most of the backbone, keep the learning rate low, train only adapters such as LoRA, interleave a slice of the original data, or regularize the weights toward their pretrained values.

  </Accordion>
  <Accordion title="Does averaging logits or averaging probabilities give better ensemble accuracy, and why?">

    Averaging probabilities, which is what the reference implementation does: softmax each member, then take the mean. Independently trained members have different logit scales, so averaging logits lets whichever member is loudest dominate the vote while the others barely register. Probability averaging puts everyone on the same scale, and temperature above `1.0` flattens each distribution first, which further reduces the influence of overconfident members.

  </Accordion>
  <Accordion title="Where do snapshot ensembles get their diversity from, and what do they cost?">

    A cosine schedule with warm restarts, saving a checkpoint at each cycle minimum. Each minimum is a different local basin reached by a different learning-rate path, so one run yields several usable members. The cost is storage and `M` forward passes at inference; what it avoids is `M` full training runs.

  </Accordion>
  <Accordion title="What is the difference between SWA and an ensemble?">

    SWA averages weights along one SGD trajectory, in parameter space, and yields a single model costing one forward pass; an ensemble averages predictions from several models and costs `M`. SWA works because the trajectory stays inside one broad basin, so averaging the points finds a wider, flatter solution in it rather than combining different solutions.

  </Accordion>
  <Accordion title={<>Explain what <code>vmap(f, in_dims=(0, 0, None))</code> does to a function taking parameters, buffers, and an input batch.</>}>

    It maps over the leading axis of the stacked parameters and buffers (dimension 0 for each) while broadcasting the input batch unchanged, marked `None`. The result gains a leading axis of size `M`: five members become one batched call instead of five separate sets of kernel launches, which is what makes large ensembles and multi-seed evaluation practical.

  </Accordion>
  <Accordion title="How should a classifier for 800 labelled images be built with a strong ImageNet backbone available?">

    Linear probe. Load an ImageNet backbone with `num_classes=0`, set `requires_grad = False` on its parameters and keep it in `eval()` so its BatchNorm statistics do not move, then train a single head on the pooled features with AdamW. At 800 images that lands within a couple of points of fine-tuning with far less overfitting risk. If it falls short, unfreeze only the last stage at a rate ten times smaller than the head's.

  </Accordion>
</Accordions>
