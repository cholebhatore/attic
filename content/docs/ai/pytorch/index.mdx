Phase 1 built the math. This phase puts it on hardware. A PyTorch tensor is the same array you already know, plus three things that change how you reason about it: a device, a dtype, and a stride layout that decides whether an operation copies memory or just relabels it.

Everything after this point in the curriculum, from transformers to distributed training, is these pages applied at larger scale.

If you have never used a deep learning framework, start with [PyTorch Basics](/ai/pytorch/pytorch-basics). It explains what a framework does, the five building blocks every training script uses, why GPUs matter, and walks through a complete 25-line training run before any page goes deep. Every page after it also opens with a **plain-language version**: a short explanation, the page's roadmap, and a table of the words it uses.

## The whole phase, topic by topic

Every heading in this phase, in reading order, with the one detail that makes each worth remembering. Read it first as a preview, or afterwards as a revision sheet.

<Accordions>
  <Accordion title="PyTorch Basics">

    - **What a framework does** — automatic gradients, GPU execution, and ready-made layers on top of an array library
    - **Why PyTorch** — eager, Python-like execution; where TensorFlow, Keras, and JAX fit
    - **The five building blocks** — tensor, autograd, `nn.Module`, optimizer, `DataLoader`
    - **CPU and GPU** — a few strong cores against thousands of simple ones; CUDA, MPS, VRAM, device
    - **Eager versus compiled** — line-by-line execution against `torch.compile`
    - **A complete tiny run** — learning `y = 2x + 1` with every building block once
    - **Where each idea is covered** — which page answers which question

  </Accordion>
  <Accordion title="Tensor Fundamentals">

    - **The plain-language version** — a flat buffer of numbers plus a label saying how to read it; dtype, float bits, device, stride, view
    - **Creating tensors** — from data, constants, and distributions; special tensors like `eye`, `arange`, `linspace`
    - **Data types** — each dtype's bit layout decides its range and precision
    - **Type promotion** — mixing dtypes never errors; any float beats any integer, and the wider type wins within a category
    - **Device placement** — every tensor lives on exactly one device
    - **Strides and contiguity** — a `(3, 4)` tensor has stride `(4, 1)`; contiguous means plain row-by-row order
    - **Views share storage** — writing through a view changes the original
    - **Byte accounting** — memory is `numel() * element_size()`

  </Accordion>
  <Accordion title="Indexing and Shapes">

    - **The plain-language version** — every indexing operation returns a window (view) or a photocopy (copy)
    - **Basic slicing** — `x[start:stop:step]`, stop excluded, always a view
    - **Boolean masking** — `x[x > 0]` returns a packed 1-D copy
    - **Fancy indexing** — indexing by a list of positions copies; token embedding is fancy indexing
    - **Gather and scatter** — read or write one position per row when the index differs per row
    - **Shape manipulation** — `view` refuses when it would need a copy, `reshape` copies silently; `-1` infers a size; `squeeze`, `unsqueeze`, `flatten`
    - **Splitting** — `split` and `chunk` cut one tensor into pieces

  </Accordion>
  <Accordion title="Combining and Permuting">

    - **The plain-language version** — gluing and relabeling axes never changes a number
    - **cat and stack** — `cat` joins along an existing axis, `stack` adds a new one; the KV cache is a `cat` per generated token
    - **transpose and permute** — swap two axes, or reorder all of them
    - **The multi-head reshape** — split `d_model` into `h` heads of width `d`
    - **expand and repeat** — a stride-0 view for free, or a real copy
    - **einops** — reshapes written as named patterns like `"b s (h d) -> b h s d"`
    - **Copying and when it matters** — which operations are free and which copy everything

  </Accordion>
  <Accordion title="Matrix Multiplication">

    - **The plain-language version** — `*` multiplies matching positions, `@` takes dot products and contracts an axis; a 2 by 2 example by hand
    - **Hadamard product versus matmul** — both run on square matrices, only one is what you meant
    - **The matmul family** — `mm`, `bmm`, and `matmul`, which broadcasts batch axes
    - **Linear layers store weights transposed** — `nn.Linear` keeps `W` as `(out, in)` and computes `x @ W.T + b`
    - **einsum** — letters missing from the output are multiplied and summed away
    - **Attention written three ways** — the same scores with `@`, `bmm`, and `einsum`
    - **Counting the cost** — `(M, K) @ (K, N)` is `2 * M * K * N` FLOPs
    - **Why shape and layout matter** — tensor cores work on fixed-size tiles, so shapes that divide evenly run faster

  </Accordion>
  <Accordion title="Autograd Engine">

    - **The plain-language version** — the forward pass writes a receipt; `backward()` reads it in reverse with the chain rule
    - **Leaves and non-leaves** — only tensors you created keep `.grad` by default
    - **The graph is dynamic** — rebuilt every forward pass, so Python control flow just works
    - **backward()** — the graph is freed afterwards; running twice needs `retain_graph`; `create_graph` gives second derivatives
    - **Turning autograd off** — `no_grad` and `inference_mode` for evaluation and serving
    - **Freezing parameters** — `requires_grad=False` keeps weights fixed
    - **Hooks** — callbacks during backward, the basis of clipping and debugging tools
    - **torch.compile** — TorchDynamo captures the graph, TorchInductor emits fused kernels; graph breaks, modes, and dynamic shapes

  </Accordion>
  <Accordion title="Devices and Precision">

    - **The plain-language version** — CPU chefs against GPU line cooks; fewer bits buys speed and costs range or precision
    - **Where a tensor lives** — operations across devices raise instead of copying
    - **Why the GPU wins** — parallel arithmetic plus far higher memory bandwidth
    - **The decode ceiling** — one generated token reads every weight once, so memory bandwidth caps tokens per second
    - **Crossing the PCIe boundary** — host-to-device copies are slow; pinned memory makes them faster and asynchronous
    - **Numerical formats** — FP32, TF32, BF16, FP16, FP8; `65504` is the FP16 ceiling
    - **Why FP16 needs help and BF16 does not** — tiny gradients round to zero in FP16, so the loss is scaled by `2^16`
    - **Automatic mixed precision** — `autocast` runs matmuls in low precision and keeps sensitive ops in FP32
    - **TF32** — FP32 storage with a 10-bit mantissa inside matmuls
    - **Memory accounting** — mixed precision halves activation memory, not parameters
    - **`torch.compile` and the backend** — compilation and precision compose

  </Accordion>
  <Accordion title="Training Loop">

    - **The plain-language version** — the model, the loss, and the optimizer, called in order batch after batch
    - **What `nn.Module` gives you** — `__init__` builds the pieces, `forward` composes them
    - **Registration** — assigning a parameter, buffer, or submodule to `self` registers it
    - **Loss functions** — `CrossEntropyLoss` takes raw logits, never softmax output
    - **Optimizers** — SGD with momentum for vision, AdamW for transformers
    - **The five steps** — `zero_grad`, forward, loss, `backward`, `step`
    - **A complete toy run** — the five steps on a real model
    - **Validation** — `model.eval()` plus `torch.no_grad()`, and why you need both
    - **Learning rate schedules** — changing the step size as training progresses
    - **Gradient clipping and accumulation** — cap the gradient norm; simulate a big batch with several small ones
    - **The full harness** — everything above in one script
    - **Failure modes** — symptom, usual cause, and the check that confirms it

  </Accordion>
  <Accordion title="Data Pipelines">

    - **The plain-language version** — `Dataset` fetches one example, `DataLoader` serves batches from background workers
    - **Two dataset styles** — map-style by index, iterable-style as a stream
    - **A map-style dataset** — `__len__` and `__getitem__`
    - **DataLoader** — batch size, shuffle, `num_workers`, `pin_memory`, `prefetch_factor`
    - **What the workers do** — separate processes preparing batches ahead of the GPU
    - **Sizing `num_workers`** — the smallest count where CPU time per batch divided by workers beats the GPU step
    - **Collation** — merging examples into one batch, with padding for variable lengths
    - **Determinism and worker seeding** — seed every worker so runs repeat
    - **Epoch boundaries** — `persistent_workers` avoids re-spawning workers every epoch
    - **Distributed sampling** — each GPU gets a different slice
    - **Iterable datasets** — streaming data too big to index
    - **WebDataset** — `.tar` shards, three levels of shuffle, shard sizing, and why shards beat millions of small files
    - **Choosing** — which approach fits which situation

  </Accordion>
  <Accordion title="Checkpointing">

    - **The plain-language version** — a full game save to resume, or just the weights to run inference
    - **What `state_dict` is** — a flat mapping from dotted names to tensors
    - **What goes in a resumable checkpoint** — model, optimizer, scheduler, step, and RNG states; Adam state is twice the model
    - **Loading** — restore into an already-built model and optimizer
    - **Why `torch.save(model)` is wrong** — it pickles the object instead of saving plain tensors
    - **Safetensors** — tensors only, no code execution, memory-mapped loading
    - **Format comparison** — `.pt`, safetensors, distributed checkpoints, `.keras`, SavedModel, ONNX, GGUF
    - **Partial loads and architecture changes** — `strict=False`, and always print the missing and unexpected keys
    - **Distributed and sharded checkpoints** — `torch.distributed.checkpoint` writes one shard per rank plus metadata
    - **Exporting for inference** — producing a file a serving runtime can load
    - **Cross-framework: Keras 3 and legacy TensorFlow** — weight layouts differ, so tensors need permuting

  </Accordion>
</Accordions>

## Prerequisites

Phase 1 covers the math these pages assume. Three of them in particular:

- [Vectors and Matrices](/ai/math-foundations/vectors-and-matrices) for rank, SVD, and what a weight matrix does geometrically
- [Tensor Broadcasting](/ai/math-foundations/tensor-broadcasting) for the stride and contiguity model PyTorch inherits
- [Backprop from Scratch](/ai/math-foundations/backprop-from-scratch) for the reverse-mode traversal that `autograd` automates

Install PyTorch with `uv`, matching the CUDA build to your driver:

```bash title="CPU only"
uv add torch torchvision --index-url https://download.pytorch.org/whl/cpu
```

```bash title="CUDA 12.6"
uv add torch torchvision --index-url https://download.pytorch.org/whl/cu126
```

Check what you got:

```python title="check_install.py"
import torch

print(torch.__version__)
print(torch.cuda.is_available())
print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else "cpu only")
```

The companion packages used later in this phase:

```bash
uv add safetensors einops webdataset
```
