## What is an outlier?

A standard definition comes from Douglas Hawkins (_Identification of Outliers_, 1980): **an observation that deviates so much from other observations as to arouse suspicion that it was generated by a different mechanism.** The last part is the important one. An outlier is not just a large number; it is a value that probably came from a different process than the rest.

Outliers have three causes, and the cause decides what to do:

| Cause                 | Example                                                       | What to do                                                            |
| :-------------------- | :------------------------------------------------------------ | :-------------------------------------------------------------------- |
| **Error**             | Age 250, a height typed in mm instead of cm, a sensor glitch  | Fix it if you can, otherwise remove it or treat it as missing         |
| **Natural extreme**   | A genuinely tall person, a billionaire in an income survey    | Keep it; use robust statistics or a transform so it does not dominate |
| **Different process** | A fraudulent purchase, a cyberattack, a machine about to fail | This is the signal: detect it, do not delete it                       |

**Should you remove outliers?** Only when you know they are errors. Deleting real extreme values makes the data look tidier than the world is, and a model trained without them is surprised by them in production. In fraud, security, and fault detection the outliers are the whole point. When in doubt, keep them and use methods that are not dominated by them: medians instead of means, robust scaling, log transforms, or tree models.

## Point, contextual, and collective outliers

The three-way split is from the anomaly detection survey by Chandola, Banerjee, and Kumar (_Anomaly Detection: A Survey_, ACM Computing Surveys, 2009).

| Type           | Unusual because…                                                           | Example                                                        |
| :------------- | :------------------------------------------------------------------------- | :------------------------------------------------------------- |
| **Point**      | The single value is unusual compared with all data                         | A 9,000-dollar purchase on a card that usually spends 40       |
| **Contextual** | The value is unusual **in its context** only                               | 30 °C is normal in July and an anomaly in January in Oslo      |
| **Collective** | A **group** of values is unusual together, though each one alone is normal | 50 small logins from one IP in a minute; a flat line in an ECG |

Contextual outliers need the context as an input: the time, the location, the user. A global rule on the raw value misses them, which is why the time-series section compares each day with the same weekday, not with the whole series. Collective outliers need a window or a sequence, not single rows.

## Outlier, anomaly, novelty, and noise

These words overlap and are used loosely. The useful distinctions:

| Word        | Meaning                                                                                                               |
| :---------- | :-------------------------------------------------------------------------------------------------------------------- |
| **Outlier** | A data point far from the rest. A statistical description: it says nothing about why.                                 |
| **Anomaly** | A data point produced by a different, usually interesting process: fraud, attack, failure. An outlier you care about. |
| **Novelty** | A new kind of point, not present in the clean training data, seen at prediction time.                                 |
| **Noise**   | Random, uninteresting variation or error. Removed or smoothed, not investigated.                                      |

scikit-learn makes the outlier and novelty split concrete, and interviewers use the same terms:

- **Outlier detection** (unsupervised): the training data **contains** outliers, and the method must find them in that same data. Example: clean a dataset before training.
- **Novelty detection** (semi-supervised): the training data is **clean**, all normal. The method learns what normal looks like, then judges new data. Example: train on a month of verified-good transactions, then score today's.

Novelty detection is easier when you can get clean data, because the model never learns that outliers are normal.

## Univariate versus multivariate outliers

- A **univariate** outlier is unusual in one variable on its own: a salary of 250 thousand among salaries near 40. Box plots and z-scores find these.
- A **multivariate** outlier is unusual only in **combination**. A height of 190 cm is fine. A weight of 52 kg is fine. A 190 cm adult who weighs 52 kg is very unusual. Checking each column alone will never find it.

Real anomalies are usually multivariate: a normal amount, at a normal hour, in a normal country, but never all three together for this customer. That is why the methods after the IQR rule all look at every feature at once.

## Statistical detection

Four rules, each a spread measure from the statistics page turned into a threshold.

| Method                   | Score                                            | Usual threshold                       | Assumes                                       | Robust to the outliers themselves?     |
| :----------------------- | :----------------------------------------------- | :------------------------------------ | :-------------------------------------------- | :------------------------------------- |
| **Z-score**              | `(x - mean) / std`                               | `abs(z) > 3`                          | Roughly normal data                           | No                                     |
| **Modified z-score**     | `0.6745 * (x - median) / MAD`                    | `abs(M) > 3.5`                        | Roughly symmetric data                        | Yes                                    |
| **IQR rule**             | Below `Q1 - 1.5 * IQR` or above `Q3 + 1.5 * IQR` | Tukey's fences (1.5; 3 for "far out") | Nothing about shape                           | Yes                                    |
| **Mahalanobis distance** | `sqrt((x - mean)^T * inverse(Cov) * (x - mean))` | Chi-square cutoff                     | Roughly elliptical (multivariate normal) data | No, unless a robust covariance is used |

### Z-score

The z-score counts standard deviations from the mean. By the empirical rule, only about 0.3% of normal data is beyond 3, so `abs(z) > 3` flags a value as suspicious. It is simple and fast, and it fails in two ways:

- **The outlier inflates the statistics used to judge it.** The mean moves toward the outlier and the standard deviation grows, so the outlier's own z-score shrinks.
- **With few points, it cannot fire.** In a sample of size `n`, no z-score (computed with the sample standard deviation) can exceed `(n - 1) / sqrt(n)` (Shiffler, 1988). For `n = 10` that limit is 2.85, so a threshold of 3 can never flag anything, however extreme the value.

### Modified z-score

Iglewicz and Hoaglin (_How to Detect and Handle Outliers_, 1993) replaced the mean with the median and the standard deviation with the MAD, which outliers cannot move. The constant 0.6745 rescales MAD to match the standard deviation on normal data (`1 / 1.4826`). Their recommended cutoff is 3.5.

### IQR rule

Tukey's rule draws **fences** at `Q1 - 1.5 * IQR` and `Q3 + 1.5 * IQR` and flags anything outside. These are the box plot's whiskers. It makes no assumption about the shape of the distribution, and quartiles are robust. On heavily skewed data it flags many values in the long tail; apply it to `log(x)` instead.

### The three univariate rules on the same data

The ten salaries from the statistics page, in thousands:

```python
import numpy as np

x = np.array([32, 35, 38, 40, 40, 43, 45, 48, 52, 250], dtype=float)

z = (x - x.mean()) / x.std(ddof=1)
print("z-scores:", np.round(z, 2).tolist())
print("z > 3 flags:", x[np.abs(z) > 3].tolist())
n = len(x)
print(f"largest possible |z| with n={n}: {(n - 1) / np.sqrt(n):.2f}")

med = np.median(x)
mad = np.median(np.abs(x - med))
mz = 0.6745 * (x - med) / mad
print("modified z:", np.round(mz, 2).tolist())
print("modified z > 3.5 flags:", x[np.abs(mz) > 3.5].tolist())

q1, q3 = np.percentile(x, [25, 75])
iqr = q3 - q1
lo, hi = q1 - 1.5 * iqr, q3 + 1.5 * iqr
print(f"IQR fences: [{lo}, {hi}]  flags: {x[(x < lo) | (x > hi)].tolist()}")

# Masking: two large values hide each other from the z-score
y = np.array([32, 35, 38, 40, 40, 43, 45, 48, 52, 240, 250, 41, 39, 44, 37, 46, 42, 36, 47, 43], dtype=float)
zy = (y - y.mean()) / y.std(ddof=1)
my = 0.6745 * (y - np.median(y)) / np.median(np.abs(y - np.median(y)))
print(f"n=20 with 240 and 250: max |z|={np.abs(zy).max():.2f}  z>3 flags={y[np.abs(zy) > 3].tolist()}  "
      f"modified-z flags={y[np.abs(my) > 3.5].tolist()}")
```

```text
z-scores: [-0.46, -0.41, -0.37, -0.34, -0.34, -0.29, -0.26, -0.22, -0.16, 2.83]
z > 3 flags: []
largest possible |z| with n=10: 2.85
modified z: [-1.28, -0.88, -0.47, -0.2, -0.2, 0.2, 0.47, 0.88, 1.42, 28.13]
modified z > 3.5 flags: [250.0]
IQR fences: [25.375, 60.375]  flags: [250.0]
n=20 with 240 and 250: max |z|=2.99  z>3 flags=[]  modified-z flags=[240.0, 250.0]
```

The salary of 250 is six times the typical salary, yet its z-score is 2.83, just under the 2.85 ceiling, and the z rule flags nothing. The modified z-score scores it 28.13 and the IQR rule flags it. The last line shows **masking**: with twenty values, two large ones inflate the standard deviation together so neither reaches 3, while the modified z-score flags both.

The opposite failure is **swamping**: an outlier drags the mean so far that normal points on the other side start to look extreme and get flagged. Both are reasons to prefer robust statistics, or to remove the most extreme point and re-test one at a time (Grubbs' test does this formally for normal data).

### Mahalanobis distance

The z-score generalized to many correlated features. It measures distance from the mean in units of the data's own spread, **taking correlations into account**: moving along the direction the data naturally stretches costs little, moving across it costs a lot. With `d` features of normal data, the squared distance follows a chi-square distribution with `d` degrees of freedom, which gives a principled cutoff. For 2 features, the 99% cutoff on the squared distance is 9.21, so a distance above about 3.03 is flagged.

```python
rng = np.random.default_rng(0)
height = rng.normal(170, 10, 500)
weight = 0.9 * height - 85 + rng.normal(0, 5, 500)
data = np.column_stack([height, weight])
mu = data.mean(axis=0)
cov_inv = np.linalg.inv(np.cov(data, rowvar=False))


def mahalanobis(p):
    d = p - mu
    return float(np.sqrt(d @ cov_inv @ d))


for name, p in [("tall and heavy", np.array([190.0, 86.0])),
                ("tall and light", np.array([190.0, 52.0]))]:
    zs = (p - mu) / data.std(axis=0, ddof=1)
    print(f"{name}: z per feature={np.round(zs, 2).tolist()}  "
          f"euclidean from mean={np.linalg.norm(p - mu):.1f}  mahalanobis={mahalanobis(p):.2f}")
```

```text
tall and heavy: z per feature=[2.0, 1.81]  euclidean from mean=27.5  mahalanobis=2.00
tall and light: z per feature=[2.0, -1.5]  euclidean from mean=25.5  mahalanobis=7.45
```

Both people look ordinary column by column: every z-score is 2 or less. By plain Euclidean distance, the tall and light person is even **closer** to the average. Mahalanobis distance sees that tall and heavy follows the correlation (2.00, normal) and tall and light breaks it (7.45, far beyond 3.03). This is a multivariate outlier, caught.

Its weakness is the same as the z-score's: the mean and covariance are themselves pulled by outliers. The **Minimum Covariance Determinant** estimator (scikit-learn's `EllipticEnvelope`) fits them on the most central subset of the data instead. It also needs more rows than features to invert the covariance matrix, and assumes one elliptical cloud.

### Isolation Forest

**Idea.** Anomalies are few and different, so they are **easy to isolate**. Build random trees: at each node pick a random feature and a random split value between its min and max, and keep splitting until each point is alone. A point in a dense crowd needs many splits to separate. An anomaly is cut off in a few. The **average path length** over many trees is the score: short path, likely anomaly. (Liu, Ting, and Zhou, _Isolation Forest_, ICDM 2008.)

- **Strengths**: fast (each tree uses a small random subsample, 256 rows by default), scales to large data and many features, needs no distance metric and no scaling.
- **Weaknesses**: weaker on **local** outliers that sit just outside a dense cluster, and on anomalies that only differ in a combination of features that axis-aligned cuts struggle with.
- **The go-to first method** for tabular data.

### Local Outlier Factor (LOF)

**Idea.** Compare each point's **local density** with the density of its `k` nearest neighbours. A point in a sparse spot surrounded by dense neighbours has a LOF well above 1; a point as dense as its neighbours has LOF near 1. (Breunig, Kriegel, Ng, and Sander, _LOF_, SIGMOD 2000.)

- **Strengths**: finds **local** outliers in data whose clusters have different densities, the case where a single global threshold fails.
- **Weaknesses**: needs a distance metric and scaled features, is slow on large data (nearest-neighbour search), and is sensitive to `k`.

### One-Class SVM

**Idea.** Learn a boundary around the normal data in a kernel feature space, so that most training points are inside. Points outside are anomalies. The parameter `nu` is an upper bound on the fraction of training points left outside. (Schölkopf et al., _Estimating the Support of a High-Dimensional Distribution_, Neural Computation 2001.)

- **Strengths**: flexible curved boundaries; a natural fit for **novelty** detection on clean training data.
- **Weaknesses**: very sensitive to the kernel width `gamma` and to `nu`, needs scaled features, and training scales poorly beyond tens of thousands of rows.

### DBSCAN

**Idea.** A clustering algorithm that also labels noise. A **core point** has at least `min_samples` neighbours within distance `eps`. Clusters grow from core points. Points not reachable from any core point are labelled **noise** (`-1`), which serves as the outlier set. (Ester, Kriegel, Sander, and Xu, KDD 1996.)

- **Strengths**: finds clusters of any shape and does not need the number of clusters.
- **Weaknesses**: one `eps` for the whole dataset, so clusters of different densities break it: an `eps` that suits a tight cluster calls the edges of a loose cluster noise. Outputs a label, not a graded score.

### Autoencoders

**Idea.** An [autoencoder](/ai/math-foundations/encoding-and-decoding#encoder-and-decoder-networks) compresses each input into a small code and rebuilds it. Train it on normal data only. It learns to rebuild normal patterns well, and rebuilds anything unlike them badly. The **reconstruction error** is the anomaly score.

- **Strengths**: works on images, sequences, logs, and very high-dimensional data; learns non-linear structure.
- **Weaknesses**: needs mostly clean training data and tuning. If it is too powerful, it learns to rebuild anomalies as well (it learns the identity). Errors are hard to explain.
- **The linear case is PCA.** A linear autoencoder trained with squared error spans the same subspace as the top principal components (Baldi and Hornik, 1989). PCA reconstruction error is therefore a cheap baseline, used in the fraud project below.

### Four detectors on the same data

Two clusters, one tight and one loose, plus three planted outliers: two **global** ones far from everything, and one **local** one just outside the tight cluster. Each method gives every point a score, and the code prints where each planted point ranks among all 303 (rank 1 is the most anomalous).

```python
import numpy as np
from sklearn.cluster import DBSCAN
from sklearn.ensemble import IsolationForest
from sklearn.neighbors import LocalOutlierFactor
from sklearn.svm import OneClassSVM

rng = np.random.default_rng(42)
dense = rng.normal([0, 0], 0.3, size=(150, 2))     # a tight cluster
loose = rng.normal([4, 4], 1.2, size=(150, 2))     # a spread-out cluster
planted = np.array([[-2.0, 3.0], [6.0, -1.0],      # global outliers: far from everything
                    [1.5, 0.0]])                   # local outlier: close, but far for the tight cluster
X = np.vstack([dense, loose, planted])              # both axes share one unit, so no scaling


def rank(scores):
    """Rank of each planted point among all 303, where 1 is the most anomalous."""
    order = np.argsort(-scores)
    return [int(np.flatnonzero(order == i)[0]) + 1 for i in range(len(X) - 3, len(X))]


scores = {
    "Isolation Forest": -IsolationForest(random_state=0).fit(X).score_samples(X),
    "Local Outlier Factor": -LocalOutlierFactor(n_neighbors=20).fit(X).negative_outlier_factor_,
    "One-Class SVM": -OneClassSVM(nu=0.05, gamma=0.1).fit(X).decision_function(X),
}
for name, s in scores.items():
    print(f"{name:21s} ranks of [global, global, local]: {rank(s)}")

labels = DBSCAN(eps=0.6, min_samples=5).fit_predict(X)
print(f"DBSCAN                planted points labelled noise: {(labels[-3:] == -1).tolist()}  "
      f"other noise points: {int((labels[:-3] == -1).sum())}")
```

```text
Isolation Forest      ranks of [global, global, local]: [2, 1, 17]
Local Outlier Factor  ranks of [global, global, local]: [1, 3, 2]
One-Class SVM         ranks of [global, global, local]: [2, 1, 14]
DBSCAN                planted points labelled noise: [True, True, True]  other noise points: 14
```

All four find the global outliers. Only LOF ranks the local outlier near the top (2nd). Isolation Forest and One-Class SVM rank it 17th and 14th, behind ordinary points, mostly at the edge of the loose cluster, because by absolute distance the loose cluster's edges look more isolated. DBSCAN catches all three, but also calls 14 normal points noise: its single `eps` suits the tight cluster and treats the loose cluster's edges as outliers. No method wins everywhere, which is why the comparison table matters more than any single result.

### Choosing a method

| Method                   | Defines an outlier as               | Global or local | Scale needed? | Large data | Typical use                                    |
| :----------------------- | :---------------------------------- | :-------------- | :------------ | :--------- | :--------------------------------------------- |
| **Z / modified z / IQR** | Far from center on one feature      | Global          | No            | Yes        | Quick checks per column, data cleaning         |
| **Mahalanobis**          | Far from center, given correlations | Global          | No            | Yes        | Few correlated numeric features, one cluster   |
| **Isolation Forest**     | Quick to isolate with random cuts   | Mostly global   | No            | Yes        | First choice for tabular data, fraud           |
| **LOF**                  | Less dense than its neighbours      | Local           | Yes           | Slow       | Clusters of different densities                |
| **One-Class SVM**        | Outside a learned boundary          | Global          | Yes           | Slow       | Novelty detection on small, clean data         |
| **DBSCAN**               | Not in any dense cluster            | Global          | Yes           | Medium     | When you also want the clusters                |
| **Autoencoder**          | Hard to reconstruct                 | Either          | Yes           | Yes (GPU)  | Images, sequences, logs, high-dimensional data |

When labels exist, even a few hundred, a **supervised** classifier (gradient-boosted trees) usually beats every unsupervised method, because it learns what the anomalies you care about look like rather than what "unusual" means in general. Unsupervised detectors are for when labels are missing, too few, or the anomalies keep changing. Many production systems use both: an unsupervised score becomes one feature of the supervised model.

## Anomaly scores and thresholds

Most detectors output a **score**, not a yes or no. Turning scores into alerts needs a **threshold**, and choosing it is a business decision as much as a statistical one.

- **Contamination or percentile.** Flag the top `p`% of scores (scikit-learn's `contamination` parameter). Only right if you roughly know the anomaly rate.
- **Statistical cutoff.** A z of 3, a modified z of 3.5, a chi-square quantile for Mahalanobis.
- **Alert budget.** Flag the top `k` per day, where `k` is how many cases the analysts can actually review. Common in fraud and security, and the fraud project below evaluates exactly this.
- **Cost-based.** Choose the threshold that minimizes `cost of a miss * misses + cost of a false alarm * false alarms`.

Scores from different methods live on different scales, so to combine detectors convert each to a rank or a percentile first, then average. Scores are also not probabilities; a probability needs calibration against labelled data.

## Time-series anomaly detection

Time series add trend (a steady rise), **seasonality** (daily and weekly cycles), and order. A value is anomalous **relative to what was expected at that time**, which makes most time-series anomalies contextual.

Approaches, from simple to complex:

1. **Rolling statistics**: a z-score or modified z-score against a moving window of recent values.
2. **Seasonal baseline**: compare with the same hour yesterday or the same weekday last week.
3. **Decompose, then score the residual**: split the series into trend, seasonality, and residual (STL decomposition), and run a robust rule on the residual.
4. **Forecast, then score the error**: predict each point (ARIMA, Prophet, or a neural forecaster) and flag large forecast errors.
5. **Change-point detection**: find the moment the series' level or variance shifts for good (CUSUM, PELT), as opposed to one spike.

A daily sales series with a trend, a weekly cycle, and one real spike on day 90:

```python
import numpy as np

rng = np.random.default_rng(3)
days = np.arange(120)
sales = 200 + 1.5 * days + 30 * np.sin(2 * np.pi * days / 7) + rng.normal(0, 8, 120)
sales[90] += 60

# Naive: one z-score over the whole series
z = (sales - sales.mean()) / sales.std()
print(f"global z at day 90: {z[90]:.2f}   flags: {np.flatnonzero(np.abs(z) > 3).tolist()}")


def seasonal_flags(series, clean_baseline):
    """Compare each day with the same weekday last week, scored robustly."""
    base = series.copy()
    flags = []
    for t in range(63, len(series)):
        diffs = base[t - 56:t] - base[t - 63:t - 7]      # eight weeks of week-over-week changes
        expected = base[t - 7] + np.median(diffs)
        mad = np.median(np.abs(diffs - np.median(diffs)))
        score = 0.6745 * (series[t] - expected) / mad
        if abs(score) > 3.5:
            flags.append(t)
            if clean_baseline:
                base[t] = expected                      # do not let the spike become next week's baseline
    return flags


print("week-over-week flags:            ", seasonal_flags(sales, clean_baseline=False))
print("week-over-week, cleaned baseline:", seasonal_flags(sales, clean_baseline=True))
```

```text
global z at day 90: 1.38   flags: []
week-over-week flags:             [90, 97, 116]
week-over-week, cleaned baseline: [90, 116]
```

Three lessons in three lines:

- **The global z-score misses the spike** (z = 1.38). The trend makes late values large anyway, so the series' overall spread swallows a 60-unit jump.
- **The seasonal baseline finds it** on day 90, but also flags day 97, an **echo**: day 97 is compared with the inflated day 90 and looks too low. Replacing a flagged value with its expected value before it becomes a baseline removes the echo.
- **Day 116 is a false alarm.** Nothing was planted there; comparing with a single day last week doubles the noise, and at a threshold of 3.5 some normal days cross it. Lower thresholds catch more and alarm more. That trade-off never goes away.

## Multivariate and high-dimensional data

- **Scale features first** for any distance or boundary method (LOF, One-Class SVM, DBSCAN, Mahalanobis without a covariance, k-NN). Otherwise the feature with the largest unit decides everything. Use robust scaling when outliers are present, so they do not set the scale.
- **The curse of dimensionality.** In hundreds of dimensions, distances between random points become nearly equal, so "far" loses meaning for distance-based methods. Isolation Forest, PCA or autoencoder reconstruction error, and reducing dimensions first hold up better.
- **Mixed types.** Encode categories (see [Encoding and Decoding](/ai/math-foundations/encoding-and-decoding#encoding-categories)) or use tree-based methods that handle them.
- **Explaining an alert.** Analysts need to know **why** a point was flagged. Report which features contributed most (per-feature z-scores, per-feature reconstruction error, or SHAP values on a tree model).

## Imbalanced datasets

In anomaly problems the interesting class is rare: fraud under 1% of transactions, faults far rarer. That breaks the usual training and evaluation habits.

**The accuracy paradox.** With 1% fraud, a model that always says "normal" is 99% accurate and catches nothing. The fraud project below prints exactly that: accuracy 0.990, recall 0.00.

Fixes, in the order to try them:

1. **Use the right metric** (next section): precision, recall, PR-AUC, precision at k. Never accuracy alone.
2. **Move the threshold.** A model trained on imbalanced data often ranks well but is miscalibrated; lowering the threshold trades precision for recall at no training cost.
3. **Class weights.** Make each mistake on the rare class cost more in the loss (`class_weight="balanced"` in scikit-learn).
4. **Resampling.** **Undersample** the majority class (fast, discards data) or **oversample** the minority class. **SMOTE** (Chawla et al., 2002) creates synthetic minority examples by interpolating between a minority point and its minority neighbours. Resample the **training** split only, never the test set, or the test score no longer reflects reality.
5. **Treat it as anomaly detection** when positives are too few or too varied to learn from: model normal, flag what does not fit.

## Concept drift

A detector learns what normal looks like **at training time**. Normal changes: new products, new customers, seasons, a pandemic, and fraudsters adapting to the detector. **Drift** is the name for that change, and it quietly ruins anomaly detectors, because a shift in normal looks like a flood of anomalies, or hides real ones.

| Kind                             | What changes                                        | Example                                                       |
| :------------------------------- | :-------------------------------------------------- | :------------------------------------------------------------ |
| **Data drift** (covariate shift) | The input distribution `P(x)`                       | Average basket size rises after a price change                |
| **Concept drift**                | The relation between input and label `P(y given x)` | A purchase pattern that used to be safe is now a fraud tactic |
| **Label drift** (prior shift)    | The base rate `P(y)`                                | Fraud rate doubles during the holidays                        |

Drift can be **sudden** (a new policy), **gradual** (slowly changing tastes), **incremental**, or **recurring** (seasons). Detecting it:

- Compare feature distributions between a reference window and the current one: the **population stability index** (PSI), the **Kolmogorov-Smirnov test**, or KL divergence. A common industry rule of thumb reads PSI below 0.1 as stable and above 0.25 as a significant shift.
- Track model **performance** once labels arrive (chargebacks can take weeks).
- Track the **alert rate**: a detector that suddenly flags three times as many cases has usually met drift, not a crime wave.

Responses are retraining on recent data on a schedule or when drift is detected, weighting recent data more, and keeping a human review loop so new labels keep arriving. The production side is covered in [data drift and concept drift](/ai/mlops/telemetry-and-cost#data-drift-and-concept-drift) in the MLOps phase.

## Evaluation metrics

Every metric starts from the **confusion matrix**, with "anomaly" as the positive class:

|                      | Predicted anomaly                  | Predicted normal            |
| :------------------- | :--------------------------------- | :-------------------------- |
| **Actually anomaly** | True positive (TP)                 | False negative (FN): a miss |
| **Actually normal**  | False positive (FP): a false alarm | True negative (TN)          |

| Metric                         | Formula                                            | Question it answers                                             |
| :----------------------------- | :------------------------------------------------- | :-------------------------------------------------------------- |
| **Precision**                  | `TP / (TP + FP)`                                   | Of the alerts, how many were real?                              |
| **Recall** (sensitivity)       | `TP / (TP + FN)`                                   | Of the real anomalies, how many did we catch?                   |
| **F1**                         | `2 * P * R / (P + R)`                              | One number balancing the two (harmonic mean)                    |
| **False positive rate**        | `FP / (FP + TN)`                                   | Of the normal points, how many did we wrongly flag?             |
| **ROC-AUC**                    | Area under recall against FPR, over all thresholds | Probability a random anomaly scores above a random normal point |
| **PR-AUC** (average precision) | Area under precision against recall                | Ranking quality, focused on the rare class                      |
| **Precision at k**             | Precision among the top `k` scores                 | How useful are the alerts analysts actually review?             |

**Why PR-AUC over ROC-AUC for rare anomalies.** The false positive rate divides by the huge number of normal points, so thousands of false alarms barely move it, and ROC-AUC looks excellent. Precision divides by the number of alerts, so those false alarms show up directly. A random ranking scores ROC-AUC 0.5 whatever the imbalance, but PR-AUC equal to the **base rate**, so always compare PR-AUC against the base rate. The fraud project shows the gap: ROC-AUC 0.936, PR-AUC 0.643.

**Precision against recall is a trade-off** set by the threshold. Which matters more depends on the costs: missing fraud costs money, but a false alarm costs an analyst's time and annoys a real customer whose card gets blocked.

## A fraud detection project, end to end

A synthetic credit card dataset, so every step can be checked. Four features per transaction: log of the amount, hour of the day, distance from home in km, and transactions in the last hour. Fraud is 1% of 10,000 rows, and it overlaps with normal behaviour on purpose: larger amounts, odd hours, further from home, more bursts, but none of these alone gives it away.

The steps, which are the same in a real project:

1. **Define the problem and the cost.** What counts as fraud, how quickly it must be caught, how many alerts analysts can review per day.
2. **Explore** each feature (histograms, box plots), and how fraud differs from normal.
3. **Preprocess**: impute, scale where the method needs it, and engineer features (amount compared with the customer's usual amount, counts per time window).
4. **Split by time** in a real project, so the model is tested on the future, not on shuffled past data. Fit preprocessing on training data only.
5. **Train** an unsupervised detector on normal data (novelty detection), and a supervised model if labels exist.
6. **Evaluate** with the base rate, PR-AUC, and precision and recall at the alert budget.
7. **Deploy and monitor** the alert rate, precision on reviewed cases, and drift. Retrain as fraud patterns change.

```python
import numpy as np
from sklearn.ensemble import IsolationForest
from sklearn.metrics import average_precision_score, precision_score, recall_score, roc_auc_score

rng = np.random.default_rng(7)
n_normal, n_fraud = 9_900, 100
# features: log amount, hour of day, km from home, transactions in the last hour
normal = np.column_stack([
    rng.normal(3.5, 0.8, n_normal),
    rng.normal(14, 4, n_normal),
    rng.exponential(5, n_normal),
    rng.poisson(1, n_normal),
])
fraud = np.column_stack([
    rng.normal(4.6, 1.0, n_fraud),
    rng.normal(8, 6, n_fraud),
    rng.exponential(25, n_fraud),
    rng.poisson(2.5, n_fraud),
])
X = np.vstack([normal, fraud])
y = np.r_[np.zeros(n_normal), np.ones(n_fraud)].astype(int)

# The do-nothing model: predict "not fraud" every time
always_zero = np.zeros_like(y)
print(f"always 'normal': accuracy={np.mean(always_zero == y):.3f}  recall={recall_score(y, always_zero):.2f}")

# Train only on transactions believed normal (here: a random 70% of the normal rows)
idx = rng.permutation(n_normal)
train = normal[idx[:6_930]]
test_X = np.vstack([normal[idx[6_930:]], fraud])
test_y = np.r_[np.zeros(n_normal - 6_930), np.ones(n_fraud)].astype(int)

model = IsolationForest(n_estimators=200, random_state=0).fit(train)
score = -model.score_samples(test_X)             # higher means more anomalous
print(f"base rate in test={test_y.mean():.3f}")
print(f"ROC-AUC={roc_auc_score(test_y, score):.3f}  PR-AUC={average_precision_score(test_y, score):.3f}")

for budget in (50, 100, 200):                    # analysts can review this many alerts
    threshold = np.sort(score)[-budget]
    pred = (score >= threshold).astype(int)
    print(f"review top {budget:3d}: precision={precision_score(test_y, pred):.2f}  "
          f"recall={recall_score(test_y, pred):.2f}")

# A linear autoencoder (PCA) flags rows it cannot rebuild
mu, sd = train.mean(axis=0), train.std(axis=0)
Z = (train - mu) / sd
_, _, Vt = np.linalg.svd(Z, full_matrices=False)
W = Vt[:2].T                                       # encode 4 features into 2 numbers


def reconstruction_error(rows):
    z = (rows - mu) / sd
    return np.sum((z - z @ W @ W.T) ** 2, axis=1)


err = reconstruction_error(test_X)
print(f"reconstruction error: median normal={np.median(err[test_y == 0]):.2f}  "
      f"median fraud={np.median(err[test_y == 1]):.2f}  PR-AUC={average_precision_score(test_y, err):.3f}")
```

```text
always 'normal': accuracy=0.990  recall=0.00
base rate in test=0.033
ROC-AUC=0.936  PR-AUC=0.643
review top  50: precision=0.84  recall=0.42
review top 100: precision=0.59  recall=0.59
review top 200: precision=0.36  recall=0.72
reconstruction error: median normal=1.32  median fraud=15.88  PR-AUC=0.687
```

Reading the output:

- **Accuracy is useless here.** Doing nothing scores 0.990.
- **The test set is 3.3% fraud**, because all 100 fraud cases went to the 3,070-row test set. A random ranking would score PR-AUC about 0.033; Isolation Forest scores 0.643, about 19 times better, while ROC-AUC (0.936) makes it look nearly solved.
- **The alert budget is the real decision.** Reviewing the top 50 alerts, 84% are real fraud but only 42% of fraud is caught. Reviewing 200 catches 72%, but almost two in three reviews are wasted.
- **The PCA autoencoder** gives fraud a median reconstruction error 12 times that of normal rows, and a PR-AUC (0.687) close to Isolation Forest's. A cheap baseline worth running alongside.

In a real project, the next step would be a supervised model on the labelled cases, with the anomaly score as one of its features, evaluated on a later time period.

## Outliers in LLM work

"Outlier" means two different things in AI interviews. Make sure you know which one is being asked about.

**1. Activation and weight outliers in quantization.** Large language models develop a few hidden-state channels with values far larger than the rest. When a block of numbers shares one quantization scale, one huge value forces a coarse scale on everything else and destroys their precision. LLM.int8(), SmoothQuant, and AWQ exist to handle this. It is the heavy-tail idea from the statistics page applied to model internals, and it is covered in [the outlier problem](/ai/inference/quantization-math#the-outlier-problem).

**2. Anomaly detection inside AI systems.** The classical methods on this page keep appearing around LLMs:

- **Training data cleaning**: filtering documents with unusual statistics (extreme length, repeated lines, symbol ratios) and near-duplicates before pretraining.
- **Out-of-distribution inputs**: flagging a query whose embedding is far from anything in the RAG corpus or the evaluation set, so the system can refuse or route it.
- **Production monitoring**: spikes in token usage, cost, latency, refusal rate, or error rate per user, which point to abuse, a prompt-injection campaign, or a broken deployment.
- **Training stability**: loss and gradient-norm spikes during a run are outliers in a time series, and are watched exactly like the sales example above.

## Interview questions

<Accordions>
  <Accordion title="What is an outlier, and should you remove it?">

    A point that deviates so much from the rest that it was probably produced by a different mechanism. Remove it only if you know it is an error (a typo, a broken sensor). Natural extremes should stay, handled with robust statistics or transforms. In fraud, security, and fault detection the outliers are the signal, so you detect them rather than delete them.

  </Accordion>
  <Accordion title="Name the three types of outliers with an example of each.">

    Point: one value unusual against all data, like a 9,000-dollar purchase on a card that spends 40. Contextual: unusual only in context, like 30 °C in January. Collective: a group unusual together while each member is normal, like 50 small logins from one IP in a minute.

  </Accordion>
  <Accordion title="What is the difference between outlier detection and novelty detection?">

    In outlier detection the training data contains the outliers, and the method must find them in that data (unsupervised). In novelty detection the training data is clean, the method learns normal, and it judges new points (semi-supervised). Novelty detection is easier when clean data exists, because the model never learns the outliers as normal.

  </Accordion>
  <Accordion title="Why can the z-score fail to detect an obvious outlier?">

    The outlier inflates the mean and standard deviation used to judge it, so its own z-score shrinks (masking). With `n` points no z-score can exceed `(n - 1) / sqrt(n)`, which is 2.85 for ten points, so a threshold of 3 can never fire. The z rule also assumes normal data. Use the modified z-score (median and MAD) or the IQR rule instead.

  </Accordion>
  <Accordion title="Explain the IQR method.">

    Compute Q1 and Q3, then `IQR = Q3 - Q1`. Flag anything below `Q1 - 1.5 * IQR` or above `Q3 + 1.5 * IQR` (Tukey's fences; 3 times IQR for extreme outliers). Quartiles are robust and the rule assumes no distribution shape, which is why box plot whiskers use it. On skewed data it over-flags the long tail; apply it to the log of the data instead.

  </Accordion>
  <Accordion title="What is Mahalanobis distance, and when do you use it instead of Euclidean?">

    Distance from the mean scaled by the inverse covariance matrix, so it accounts for each feature's spread and the correlations between features. Use it when features are correlated: a 190 cm, 52 kg person has ordinary per-feature z-scores and a smaller Euclidean distance than a 190 cm, 86 kg person, but a Mahalanobis distance of 7.45 against 2.00. Squared, it follows a chi-square distribution for normal data, which gives a cutoff.

  </Accordion>
  <Accordion title="How does Isolation Forest work, and why is it fast?">

    It builds random trees that split on a random feature at a random value until points are isolated. Anomalies are few and different, so they are isolated in fewer splits; the average path length across trees is the score. Each tree is built on a small subsample (256 rows by default) and needs no distances, so it is fast and scales to large, high-dimensional data. It is weaker on local outliers.

  </Accordion>
  <Accordion title="When would you use LOF instead of Isolation Forest?">

    When the data has clusters of different densities and the anomalies are local: a point just outside a tight cluster is normal by global distance but sparse relative to its neighbours. LOF compares each point's density with its neighbours' density. In the four-detector example, LOF ranked the local outlier 2nd while Isolation Forest ranked it 17th. LOF needs scaled features and is slower on large data.

  </Accordion>
  <Accordion title="How do you use an autoencoder for anomaly detection?">

    Train it on normal data to compress and reconstruct its input. Normal points are reconstructed well, anomalies poorly, so reconstruction error is the anomaly score; set the threshold on a validation set. Risks: if the training data contains anomalies, or the network is too powerful, it learns to reconstruct them too. PCA reconstruction error is the linear version and a good baseline.

  </Accordion>
  <Accordion title="Your fraud model is 99% accurate. Is it good?">

    Not necessarily. With 1% fraud, always predicting "not fraud" gives 99% accuracy and zero recall. Report precision, recall, PR-AUC compared against the base rate, and precision at the number of alerts analysts can review. Also check how the data was split: a random split can leak future patterns into training, so test on a later time period.

  </Accordion>
  <Accordion title="Why prefer PR-AUC over ROC-AUC for imbalanced problems?">

    ROC-AUC uses the false positive rate, whose denominator is the huge normal class, so many false alarms barely move it. PR-AUC uses precision, which counts every false alarm against the alerts. A random model's PR-AUC equals the base rate rather than 0.5. In the fraud example, ROC-AUC was 0.936 while PR-AUC was 0.643, against a base rate of 0.033.

  </Accordion>
  <Accordion title="How do you handle class imbalance?">

    Pick metrics that respect the rare class, tune the decision threshold, weight the rare class more in the loss, and resample the training split (undersample the majority, oversample the minority, or SMOTE, which interpolates new minority examples). Never resample the test set. When positives are too few or keep changing, model normal data and treat it as anomaly detection.

  </Accordion>
  <Accordion title="What is concept drift, and how does it differ from data drift?">

    Data drift is a change in the input distribution; concept drift is a change in the relation between inputs and the correct label, so the same input now deserves a different answer. Fraudsters changing tactics is concept drift. Detect drift by comparing feature distributions (PSI, KS test), tracking performance as labels arrive, and watching the alert rate. Respond by retraining on recent data.

  </Accordion>
  <Accordion title="How would you detect anomalies in a time series with seasonality?">

    Not with one global threshold: the trend and seasonal cycle hide spikes and create false alarms. Compare each value with an expected value for its time (same weekday last week, an STL decomposition, or a forecast) and score the residual with a robust rule. Stop flagged values from becoming the next baseline, or they cause echo alerts. Use change-point detection for permanent level shifts.

  </Accordion>
  <Accordion title="An interviewer asks about outliers in LLMs. What might they mean?">

    Either activation and weight outliers that make quantization hard (a few huge channels force a coarse scale on all values; LLM.int8(), SmoothQuant, and AWQ handle them), or classical anomaly detection used around LLM systems: cleaning pretraining data, flagging out-of-distribution queries by embedding distance, and spotting spikes in cost, latency, or loss. Ask which one, then answer.

  </Accordion>
</Accordions>
