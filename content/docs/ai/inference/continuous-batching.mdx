title: Continuous Batching
description: 'Iteration-level scheduling against static batching waste, selective batching, preemption, token budgets, and prefix caching with its block-aligned hit rules.'
---

Static batching pads every request in a batch to the length of the longest one and holds the whole batch until the slowest request finishes. Continuous batching reschedules after every forward pass instead, admitting new work and retiring finished work mid-batch. It is the single largest throughput improvement in LLM serving, and it is a scheduler change rather than a kernel change.

---

## What static batching wastes

Output lengths are wildly uneven, so padding cost is proportional to the spread. A realistic batch of eight requests:

```text
output lengths    50   60   80  120  200  400  800  1600
sum of useful     3,310 token slots
padded to 1600    8 x 1,600 = 12,800 token slots
utilization       3,310 / 12,800 = 26 percent
```

Seventy-four percent of the compute goes to positions that produce nothing, and the seven finished requests hold memory and GPU time while the longest one completes. The waste gets worse with tail-heavy length distributions, which is what real traffic looks like.

---

## Iteration-level scheduling

Orca, at OSDI 2022, replaced request-level scheduling with **iteration-level** scheduling. The scheduler runs after every forward pass:

1. Collect the set of requests that need one more token.
2. Admit queued requests whose KV cache fits.
3. Retire requests that emitted a stop token or hit their length limit.
4. Run one forward pass over the resulting batch.
5. Repeat.

A request that finishes at step 60 releases its slot at step 61 instead of step 1,600. Orca reports up to 36.9x higher throughput than FasterTransformer at matched latency.

The obstacle is that attention cannot be batched the ordinary way once sequences in the batch have different lengths. Orca's answer is **selective batching**: batch the operations that are shape-uniform across requests, namely the linear projections, the MLP, and the normalization layers, and run attention per request or with a variable-length kernel. Everything else is a dense matrix multiply over the concatenation of all positions in the batch.

This is why continuous batching needs paged KV cache. Admitting a request mid-batch requires allocating cache for it on the fly, and a contiguous allocator cannot do that without fragmenting until nothing fits. PagedAttention's fixed-size blocks make mid-batch admission a block-table update, which is what turned the idea from a paper into the default. vLLM reports 2 to 4x higher throughput than Orca at the same latency, with the gain coming from memory rather than scheduling (arXiv:2309.06180).

## The token budget

Every engine exposes the same two knobs, because the scheduler has to bound both dimensions of a batch:

| Knob                     | Bounds                               | Effect of raising it                           |
| :----------------------- | :----------------------------------- | :--------------------------------------------- |
| `max_num_seqs`           | Number of concurrent sequences       | More parallelism, more KV memory, higher TPOT  |
| `max_num_batched_tokens` | Positions processed in one iteration | Bigger prefills per step, higher TTFT variance |

The second one is where chunked prefill lives. An iteration has a token budget, and the scheduler fills it with a mix of decode steps, one position each, and prefill chunks. A budget of 8,192 with 200 active decodes leaves 7,992 positions for prefill, so a 32K prompt arrives in five chunks. Tuning the budget is directly trading TTFT against TPOT.

Two further knobs control memory behavior: `gpu_memory_utilization`, the fraction of VRAM the engine is allowed to claim for weights and cache, and the KV block size, which in vLLM defaults to 16 tokens and sets the granularity of both allocation and cache hits.

## Preemption

When every block is in use and a running request needs one more, the scheduler preempts something. Two strategies:

| Strategy  | Mechanism                                                | Cost                                                  |
| :-------- | :------------------------------------------------------- | :---------------------------------------------------- |
| Recompute | Drop the KV cache, requeue the request, re-prefill later | One extra prefill, but no host memory or PCIe traffic |
| Swap      | Copy blocks to host RAM, copy them back on resume        | PCIe transfer on the critical path, needs host memory |

Recompute is the default for short sequences because a re-prefill of 500 tokens is cheaper than two PCIe transfers of the same data. Swap wins for long contexts where re-prefill dominates. Preemption is a throughput-neutral, latency-hostile event, so a healthy server reports a preemption count near zero. A rising preemption rate means the cache is too small for the offered load, and the fix is a lower `max_num_seqs`, a smaller KV precision, or more hardware.

## Prompt and prefix caching

A repeated prefix does not need to be prefilled twice. If the KV state for tokens `1..k` already exists, a new request that shares those tokens starts from position `k + 1`.

**Block-hash caching** in vLLM hashes the token IDs of each 16-token block along with the hash of the preceding block, and looks the result up in a table. A hit means the block's KV is already computed and can be shared by reference, with copy-on-write if a sequence diverges. Enable it with `--enable-prefix-caching`.

**RadixAttention** in SGLang keeps the same information in a radix tree keyed by token sequences, with LRU eviction across the whole tree (arXiv:2312.07104). The tree structure suits agentic and multi-turn workloads better than a flat hash table, because it naturally represents branching: several conversations sharing a system prompt are one prefix node with many children, and a beam search or a tree-of-thoughts expansion is a subtree. SGLang reports up to 6.4x higher throughput than prior systems on workloads with heavy prefix reuse.

The hit conditions are strict, and most cache misses come from violating one of them:

- The match must be an **exact prefix**, not a substring. A shared passage in the middle of two different prompts does not hit.
- The match must be **token-aligned**. The same text with different whitespace can tokenize differently.
- The match must cover **whole blocks**. A prefix shared up to token 20 with a 16-token block size yields one reusable block, and the four leftover tokens are recomputed.
- The blocks must still be **resident**. Eviction under memory pressure removes them.

The design rule that follows is ordering: put stable content first and variable content last. A system prompt, then tool definitions, then a retrieved document corpus that changes daily, then the user's question. Anything variable placed early invalidates every block after it, so a timestamp or a request ID in the system prompt costs the entire cache.

---

## What caching costs

Prefix cache blocks occupy the same memory as live KV cache. Every cached prefix is memory not available for concurrent sequences, so there is a direct trade between hit rate and batch size.

```text
H100, Llama 3 8B BF16, 56 GiB free for cache

458,752 token slots total

held as prefix cache    100,000 slots for shared system prompts
left for live sequences 358,752 slots = 87 requests at 4,096 context
```

Whether that trade pays is a function of hit rate and prefix length. A 2,000-token system prompt shared across 87 requests saves 174,000 token-slots of prefill work per round of admissions, which is worth far more than the 4,000 slots it occupies. A cache of rarely-reused one-off prefixes saves nothing and costs batch size.

Managed APIs sell the same mechanism as a discount on cached input tokens, with explicit cache breakpoints or automatic prefix detection. The engineering constraints are identical: prefix-only, alignment-sensitive, and evicted under pressure. The context engineering section covers the API-level rules.

<Callout type="warn">
  ### Randomized retrieval ordering silently kills the cache

A RAG pipeline that sorts retrieved chunks by a per-request score produces a different token sequence every call, even when the same chunks are retrieved. The shared prefix ends at the last stable token before the chunk list, so the entire retrieval payload is re-prefilled on every request. Sorting retrieved chunks by a stable key such as document ID preserves cache hits at the cost of a fixed presentation order, and the latency difference is usually larger than the quality difference.

</Callout>

  <Accordion title="3. What is selective batching, and why is it necessary?">

    Batch the shape-uniform operations, the projections, MLP, and normalizations, as one dense multiply over all positions in the batch, and handle attention separately because sequences have different lengths. Without it, attention would force rectangular padding.

  </Accordion>
  <Accordion title="4. Why does continuous batching require paged KV cache?">

  </Accordion>
  <Accordion title={<>5. What do <code>max_num_seqs</code> and <code>max_num_batched_tokens</code> bound, respectively?</>}>

    Concurrent sequences, and positions processed in one iteration. The second is the knob that sets how much prefill fits alongside decode, so it trades TTFT against TPOT directly.

  </Accordion>
  <Accordion title="6. A 32K prompt arrives with an 8,192-token iteration budget and 200 active decodes. What happens?">

    It is admitted in chunks. 200 decode positions leave 7,992 for prefill, so the prompt takes five iterations, and other users' TPOT stays flat throughout.

  </Accordion>
  <Accordion title="7. When is recompute the right preemption strategy?">

    For short sequences, where re-prefilling a few hundred tokens costs less than two PCIe transfers of the same KV data. Swap wins for long contexts where re-prefill dominates.

  </Accordion>
  <Accordion title="8. What does a rising preemption count tell you?">

    The cache is too small for the offered load. The fixes are a lower `max_num_seqs`, a lower KV precision, or more memory, not a scheduler change.

  </Accordion>
  <Accordion title="9. Why does a hash chain over blocks rather than a hash per block?">

    Because a block's contents are only reusable if everything before it is identical. Including the predecessor's hash makes the key represent the whole prefix, so a match implies the cached KV is valid at those positions.

  </Accordion>
  <Accordion title="10. Why does a radix tree suit agentic workloads better than a flat hash table?">

    Branching is native to it. Many conversations sharing a system prompt are one prefix node with many children, and a tree-of-thoughts expansion is a subtree, so shared structure is represented once and evicted by LRU across the whole tree.

  </Accordion>
  <Accordion title="11. List the four conditions a prefix cache hit requires.">

    An exact prefix match, token alignment, whole-block coverage, and residency in memory. Most misses come from variable content placed early in the prompt.

  </Accordion>
  <Accordion title="12. What is the ordering rule for cacheable prompts, and why?">

    Stable content first, variable content last. A single varying token early invalidates every block after it, so a request ID in the system prompt costs the entire cache.

  </Accordion>
  <Accordion title="13. Why is prefix caching a trade against batch size?">

    Cached blocks occupy the same memory as live KV cache. Holding 100,000 of 458,752 slots as prefix cache leaves 87 concurrent requests at 4,096 context instead of 112.

  </Accordion>
  <Accordion title="14. When does the trade pay off?">

    When hit rate times prefix length exceeds the memory cost. A 2,000-token prompt shared across 87 requests saves 174,000 token-slots of prefill per admission round for 4,000 slots of memory. Rarely-reused prefixes save nothing.

  </Accordion>
  <Accordion title="15. A RAG pipeline has a 90 percent prefix cache miss rate despite a fixed system prompt. What is the likely cause?">

    Retrieved chunks ordered by a per-request relevance score, which produces a different token sequence each call. Sorting by a stable key such as document ID restores the hits.

  </Accordion>
