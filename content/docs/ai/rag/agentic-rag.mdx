title: Self-RAG and Agentic RAG
description: 'Retrieval as a decision: Self-RAG reflection tokens, Corrective RAG, Adaptive-RAG routing, and the four guardrails an agentic retrieval loop needs.'
---

Naive RAG retrieves on every query, once, with the query as given. That is wrong three ways: some queries need no retrieval, some need a different source, and some need a second attempt after the first came back with nothing useful.

Agentic RAG makes retrieval a decision the model makes inside a loop. It can skip retrieval, choose a source, judge whether what came back is relevant, and rewrite the query and try again. The cost is latency, money, and a new class of failure involving loops that do not terminate.

---

## The plain-language version

**Where this sits:** advanced paradigms. Everything before this page describes a fixed pipeline that runs the same steps for every question. Agentic RAG lets the model decide which steps to run.

Basic RAG always retrieves, exactly once, with the question as typed. That is wrong in three ways: some questions ("thanks!") need no retrieval, some need a different source (a database instead of the documents), and some need a second try because the first search came back with nothing useful. **Agentic RAG** puts retrieval inside a loop where the model decides: should I search, where, did what came back actually help, and should I rephrase and search again?

Think of the difference between a vending machine and a research assistant. The vending machine always does the same thing when you press the button. The assistant decides whether to look something up, where to look, notices when a source is useless, and keeps going until the question is answered, but takes longer and needs rules about when to stop.

This page covers, in order:

1. **The four decisions**: whether to retrieve, where, whether the result is relevant, and whether to try again
2. **Self-RAG**: a model trained to emit reflection tokens that critique its own retrieval and answer
3. **Corrective RAG**: grade the retrieved documents and fall back to other sources when they are poor
4. **Adaptive-RAG**: route each question to no retrieval, single-step, or multi-step retrieval by its complexity
5. **Comparison**: the three side by side
6. **Building the loop**: an agentic retrieval loop in code, and the four guardrails it needs
7. **When it is worth it**: the latency and cost against the accuracy gained

| Word                    | Plain meaning                                                                                                                                                                                           |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **agent**               | An LLM in a loop that chooses actions (such as tool calls) based on what it has seen so far.                                                                                                            |
| **retrieval as a tool** | Search is offered to the model as a tool it may call, rather than a step that always runs.                                                                                                              |
| **reflection token**    | A special output token that Self-RAG uses to judge whether retrieval is needed and whether passages and answers are supported.                                                                          |
| **relevance grading**   | Asking a model whether each retrieved document actually helps answer the question.                                                                                                                      |
| **fallback**            | A second source used when the first fails, such as web search when the internal index has nothing.                                                                                                      |
| **query complexity**    | How many retrieval steps a question needs: none, one, or several chained hops.                                                                                                                          |
| **guardrail**           | A limit that keeps the loop safe. This page's four: a maximum number of attempts, a token budget, a check that the rewritten query actually changed, and a relevance floor for what enters the context. |

## The four decisions

The toc framing is worth stating exactly, because these are the four things an agent controls that a static pipeline does not.

| Decision            | Static RAG      | Agentic RAG                                     |
| :------------------ | :-------------- | :---------------------------------------------- |
| Whether to retrieve | Always          | Skip for greetings, arithmetic, and known facts |
| Which source        | One fixed index | Route among indexes, SQL, tools, and the web    |
| Is this relevant    | Assume yes      | Score each chunk, discard the ones that fail    |
| Rewrite and retry   | Never           | Reformulate from what the first pass returned   |

```text
        +--------------------------------------------------+
        |                                                  |
   query -> decide: retrieve? -> no -> answer directly      |
                 |                                          |
                 yes                                        |
                 v                                          |
            choose source                                   |
                 |                                          |
                 v                                          |
            retrieve + rerank                               |
                 |                                          |
                 v                                          |
            evaluate relevance --- sufficient ---> generate |
                 |                                          |
                 insufficient                               |
                 v                                          |
            rewrite query ----------------------------------+
            (bounded iterations)
```

## Self-RAG

Asai et al., arXiv:2310.11490. Train the model to emit **reflection tokens** that control its own retrieval and critique its own output.

| Token      | Emitted when                 | Values and meaning                                                          |
| :--------- | :--------------------------- | :-------------------------------------------------------------------------- |
| `Retrieve` | Before generation            | `Yes` or `No`: should the model retrieve at all                             |
| `IsRel`    | After each retrieved passage | `Relevant` or `Irrelevant`: does this passage address the query             |
| `IsSup`    | After each generated segment | `Fully supported`, `Partially`, `No support`: is it grounded in the passage |
| `IsUse`    | After the full response      | A 1 to 5 usefulness rating                                                  |

Training is two-stage. A critic model, itself fine-tuned from the base with GPT-4-generated supervision, labels reflection tokens on a corpus. The target model is then fine-tuned to produce both the reflection tokens and the text, so at inference it emits them inline and they are parsed rather than generated by a separate call.

At inference the tokens drive a tree search: the model generates several continuations, each with its own retrieval decision and self-critique, and the reflection token scores select among them. This is where the quality gain comes from, and it is why Self-RAG is slower than a single pass.

The paper reports Self-RAG at 7B and 13B outperforming ChatGPT and Llama2-chat with retrieval on open-domain question answering, reasoning, and fact verification, and it improves citation accuracy for generated passages.

## Corrective RAG

Yan et al., arXiv:2401.15884. A lightweight retrieval evaluator, fine-tuned from T5-large, scores each retrieved document and the result falls into one of three bands.

| Band      | Action                                                                          |
| :-------- | :------------------------------------------------------------------------------ |
| Correct   | Decompose-then-recompose: strip irrelevant parts of the document, keep the rest |
| Incorrect | Discard the retrieved documents entirely and run a web search instead           |
| Ambiguous | Keep the refined documents and merge them with web search results               |

The decompose-then-recompose step is the interesting one. Instead of passing a whole retrieved chunk, CRAG splits it into knowledge strips, scores each strip independently, filters the low-confidence ones, and recombines. That is sentence-level pruning with a learned scorer, and it addresses the common case where a chunk is mostly right but contains one misleading sentence.

CRAG is plug-in: it wraps an existing retriever and generator without retraining either. That makes it the cheapest of the three to adopt.

## Adaptive-RAG

Jeong et al., arXiv:2403.14403. Train a small classifier to predict query complexity and route accordingly.

| Predicted class     | Strategy                                   | Cost      |
| :------------------ | :----------------------------------------- | :-------- |
| No retrieval needed | Answer from parametric knowledge           | One call  |
| Single-step         | One retrieval, one generation              | Two calls |
| Multi-step          | Iterative retrieval, composing across hops | Several   |

The classifier is trained on labels derived from existing QA datasets, using whether a question was answerable by a single-step or multi-step retriever as a weak supervision signal. It is a few-million-parameter model, so routing costs a millisecond and saves seconds on the queries that land in the first two buckets.

Adaptive-RAG and a router in front of your pipeline are the same idea. You do not need the paper's classifier; a structured-output LLM call with four categories works, and a fine-tuned small model works better and cheaper at volume.

## Comparison

| Property            | Naive RAG | Self-RAG        | CRAG               | Adaptive-RAG        | Agentic loop |
| :------------------ | :-------- | :-------------- | :----------------- | :------------------ | :----------- |
| Decides to retrieve | No        | Yes             | No                 | Yes                 | Yes          |
| Judges relevance    | No        | Yes             | Yes                | No                  | Yes          |
| Falls back to web   | No        | No              | Yes                | No                  | Yes          |
| Multi-hop           | No        | Limited         | No                 | Yes                 | Yes          |
| Needs training      | No        | Yes, two stages | Yes, the evaluator | Yes, the classifier | No           |
| Calls per query     | 2         | 2 to 6          | 3 to 4             | 2 to 6              | 3 to 15      |
| Latency             | Low       | Moderate        | Moderate           | Low to moderate     | High         |
| Adoption cost       | None      | High            | Low                | Low                 | Moderate     |

For most production systems the useful subset is: a router (Adaptive-RAG's idea), a relevance gate on the retrieved chunks (CRAG's idea), and a bounded retry with a rewritten query. That is an agentic loop you can build without training anything, and it captures most of the published gain.

## Building the loop

```python
from dataclasses import dataclass, field


@dataclass
class RetrievalState:
    query: str
    original_query: str
    chunks: list = field(default_factory=list)
    attempts: int = 0
    max_attempts: int = 3
    budget_tokens: int = 6000
    spent_tokens: int = 0


def agentic_retrieve(state: RetrievalState) -> RetrievalState:
    while state.attempts < state.max_attempts:
        state.attempts += 1

        plan = plan_step(state)                       # route: skip / vector / sql / web
        if plan.action == "answer_directly":
            return state

        hits = execute(plan)                          # hybrid search, SQL, or web
        scored = rerank(state.query, hits, top_n=8)
        kept = [h for h in scored if h.score > plan.relevance_floor]

        state.chunks.extend(kept)
        state.spent_tokens += sum(token_count(c.text) for c in kept)

        if sufficient(state.chunks, state.query) or state.spent_tokens > state.budget_tokens:
            return state

        state.query = rewrite_from_feedback(state.query, state.chunks, plan.failure_reason)

    return state
```

Four guardrails, all of which are load-bearing:

| Guardrail          | Prevents                                                         |
| :----------------- | :--------------------------------------------------------------- |
| `max_attempts`     | Infinite loops when the corpus genuinely lacks the answer        |
| `budget_tokens`    | Cost blowup from repeated wide retrieval                         |
| Query-change check | Thrashing: rewriting to the same query and retrieving again      |
| Relevance floor    | Stuffing the context with chunks the reranker did not believe in |

The query-change check is the one people omit. An agent that rewrites "what is the retry limit" to "what is the retry limit for the worker" and then to "retry limit configuration" can loop until the attempt cap without ever changing its result set. Compare the new query's embedding or term set against the previous one and stop if the distance is below a threshold.

<Callout type="warn">
  ### Over-retrieval is the common failure, not under-retrieval

Given the option to retrieve again, agents usually do. The measured effect is a context full of marginally relevant chunks, a lost-in-the-middle penalty on the one good chunk, a higher bill, and a lower-quality answer than a single well-tuned retrieval would have produced. Make the sufficiency check conservative and log how often the second attempt adds a chunk that the final answer cites. If it rarely does, cap attempts at one.

</Callout>

## When it is worth it

| Situation                                    | Use                                          |
| :------------------------------------------- | :------------------------------------------- |
| Single corpus, well-formed questions         | Naive RAG plus a reranker                    |
| Chat product with follow-ups                 | Rewriting plus a router                      |
| Multiple corpora with different access rules | Router plus per-source retrieval             |
| Multi-hop questions across documents         | IRCoT or an agentic loop                     |
| The corpus may not contain the answer        | A relevance gate and an explicit "not found" |
| Corpus quality varies by source              | CRAG-style refinement and fallback           |
| Interactive, latency-sensitive               | Route, but cap attempts at one               |
| Batch research or analysis                   | Full agentic loop, latency is free           |

## Interview questions

<Accordions>
  <Accordion title="What makes RAG agentic rather than static?">

    Four decisions move from the pipeline into the model: whether to retrieve at all, which source to query, whether the retrieved chunks are relevant, and whether to rewrite the query and retry. A static pipeline always retrieves once from one index with the query as given.

  </Accordion>
  <Accordion title="What are Self-RAG's reflection tokens?">

    `Retrieve`, emitted before generation to decide whether to retrieve; `IsRel`, scoring each retrieved passage for relevance; `IsSup`, scoring whether a generated segment is supported by the passage; and `IsUse`, a 1 to 5 usefulness rating. The model is trained to emit them inline, so they are parsed rather than requiring a separate call.

  </Accordion>
  <Accordion title="How is Self-RAG trained?">

    Two stages. A critic model, fine-tuned from the base with GPT-4-generated supervision, labels reflection tokens over a corpus. The target model is then fine-tuned to produce both the tokens and the text. At inference the tokens drive a tree search over continuations, which is where the quality gain and the latency both come from.

  </Accordion>
  <Accordion title="What are CRAG's three confidence bands and what does each trigger?">

    Correct: decompose the document into knowledge strips, filter low-confidence strips, and recompose. Incorrect: discard the retrieved documents and run a web search. Ambiguous: keep the refined documents and merge with web results. CRAG is plug-in, wrapping an existing retriever and generator without retraining either.

  </Accordion>
  <Accordion title="What is decompose-then-recompose?">

    Splitting a retrieved chunk into smaller knowledge strips, scoring each independently with the retrieval evaluator, discarding the low-confidence ones, and recombining the rest. It handles the common case where a chunk is mostly right but contains one misleading sentence.

  </Accordion>
  <Accordion title="What does Adaptive-RAG add?">

    A small classifier that predicts query complexity and routes to no retrieval, single-step retrieval, or iterative multi-step retrieval. Trained on weak supervision from whether existing QA datasets were answerable in one step or several. It costs a millisecond and saves seconds on the queries that do not need multi-hop.

  </Accordion>
  <Accordion title="Do you need the published models to get most of this?">

    No. A router, a relevance gate on retrieved chunks, and a bounded retry with a rewritten query give you Adaptive-RAG's routing and CRAG's evaluation without training anything. That combination captures most of the published gain at a fraction of the adoption cost.

  </Accordion>
  <Accordion title="Name the four guardrails an agentic retrieval loop needs.">

    A maximum attempt count, a token budget, a relevance floor below which chunks are discarded, and a query-change check. The last one prevents thrashing, where the agent rewrites the query in ways that do not change the result set and loops to the attempt cap.

  </Accordion>
  <Accordion title="What is the most common failure mode of agentic RAG?">

    Over-retrieval. Given the option to retrieve again, agents usually do, producing a context full of marginally relevant chunks, a lost-in-the-middle penalty on the one good chunk, a higher bill, and a worse answer than a single well-tuned retrieval. Make the sufficiency check conservative and measure how often a second attempt contributes a chunk the answer cites.

  </Accordion>
  <Accordion title="When is a full agentic loop the wrong choice?">

    In an interactive, latency-sensitive product over a single well-formed corpus. Three to fifteen calls per query is seconds of added latency for a gain that a reranker and a router already deliver. Reserve the full loop for batch analysis, multi-hop questions, and heterogeneous sources where latency is not the constraint.

  </Accordion>
