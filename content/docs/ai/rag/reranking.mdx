title: Reranking
description: 'Bi-encoders retrieve for recall, rerankers order for precision: cross-encoders, LLM listwise reranking, and ColBERT late interaction with the MaxSim formula.'
---

First-stage retrieval scores a query against millions of chunks, so it must score them independently. That constraint is what makes it fast and what makes it imprecise: the query and the document never attend to each other.

A reranker scores a query against a hundred chunks, so it can afford to let them interact. That single change, applied after retrieval, is the highest return-per-line-of-code improvement available in a RAG pipeline.

---

## The plain-language version

**Where this sits:** query pipeline, right after retrieval ([Hybrid Search](/ai/rag/hybrid-search)) and before the context is assembled.

Retrieval has to search millions of chunks in milliseconds, so it scores each chunk without ever reading it together with the question: the question and each chunk were embedded separately. That is fast and imprecise. A **reranker** takes the short list retrieval returned (say 50 chunks), reads the question and each chunk **together**, and re-scores them much more accurately. Only the best few go to the model.

Think of hiring. Retrieval is the CV keyword screen that cuts 10,000 applicants to 50 in a second. Reranking is the interview: slower, far more accurate, and only affordable because the list is already short.

This page covers, in order:

1. **Recall against precision**: retrieve wide, then rerank narrow
2. **Bi-encoder against cross-encoder**: separate embeddings versus reading both texts together
3. **LLM-based reranking**: asking an LLM to order the candidates
4. **ColBERT and late interaction**: a middle ground that compares every query word with every document word
5. **Placing the reranker**: how many candidates in, how many out, latency budgets, thresholds, and diversity (MMR)

| Word                      | Plain meaning                                                                                                                      |
| :------------------------ | :--------------------------------------------------------------------------------------------------------------------------------- |
| **first-stage retrieval** | The fast search over the whole index that produces candidates.                                                                     |
| **reranker**              | A slower, more accurate model that re-orders the candidates.                                                                       |
| **bi-encoder**            | Embeds the query and document separately and compares vectors. Fast, because documents are embedded ahead of time.                 |
| **cross-encoder**         | Feeds the query and document into one model together and outputs a relevance score. Accurate, but must run per pair at query time. |
| **pointwise / listwise**  | Score each candidate on its own, or have a model look at the whole list and output an order.                                       |
| **late interaction**      | Keep one vector per token, and compare query tokens with document tokens at search time (ColBERT).                                 |
| **MaxSim**                | ColBERT's score: for each query token, take its best match in the document, then sum.                                              |
| **MMR**                   | Maximal Marginal Relevance: pick results that are relevant but not near-copies of results already picked.                          |

## Recall against precision

| Stage      | Candidate set | Interaction          | Optimizes    | Typical k |
| :--------- | :------------ | :------------------- | :----------- | :-------- |
| Retrieval  | 1M to 1B      | None, dot product    | Recall       | 50 to 200 |
| Rerank     | 50 to 200     | Full cross-attention | Precision    | 4 to 20   |
| Generation | 4 to 20       | In-context           | Faithfulness | —         |

The division of labour is why the pipeline works. Retrieval only has to be good enough that the correct chunk is somewhere in the top 100. Everything after that is a smaller, harder, more expensive problem solved on a much smaller set.

A useful way to see it: recall@100 of 0.98 with a perfect reranker beats recall@100 of 0.99 with no reranker, because the LLM sees five chunks, not a hundred, and the difference between sending the right one first and sending it ninth is the lost-in-the-middle penalty.

## Bi-encoder against cross-encoder

```text
bi-encoder      q -> E_q     d -> E_d     score = E_q . E_d
                document vectors are precomputed and indexed

cross-encoder   [CLS] q [SEP] d [SEP] -> transformer -> score at [CLS]
                nothing is precomputed; every pair is a forward pass
```

| Property                   | Bi-encoder          | Cross-encoder                    |
| :------------------------- | :------------------ | :------------------------------- |
| Document encoding          | Once, at index time | Every query, every candidate     |
| Query-document interaction | None, a dot product | Full attention across all layers |
| Indexable                  | Yes, ANN            | No                               |
| Cost per 100 candidates    | One ANN search      | 100 transformer forwards         |
| Accuracy ceiling           | Lower               | Higher                           |
| Where it belongs           | First stage         | Second stage                     |

The reason cross-encoders are more accurate is that term matching becomes contextual. A bi-encoder must decide what "bank" means before it sees the query. A cross-encoder reads "river bank" and "bankruptcy filing" together with the query and attends across them, so the same word form resolves differently per candidate.

MonoBERT (Nogueira and Cho, arXiv:1901.04085) established the pattern: fine-tune BERT on MS MARCO passage rankings and use the `[CLS]` logit as the relevance score.

### Models and cost

| Reranker                               | Size    | Max tokens | Notes                            |
| :------------------------------------- | :------ | :--------- | :------------------------------- |
| `cross-encoder/ms-marco-MiniLM-L-6-v2` | 22M     | 512        | Fast, weak on long chunks        |
| `BAAI/bge-reranker-v2-m3`              | 568M    | 8,192      | Multilingual, strong default     |
| Cohere Rerank 3.5                      | Hosted  | 4,096      | Per-search-token billing         |
| Voyage `rerank-2.5`                    | Hosted  | 16,000     | Domain variants for code and law |
| Jina `reranker-v2`                     | 137M    | 8,192      | Open weights, good latency       |
| RankGPT-style LLM reranking            | Any LLM | The window | Listwise, see below              |

Latency scales with `candidates * (query_tokens + chunk_tokens)`. Approximate batched numbers on one modern GPU with 512-token chunks:

| Candidates | 6-layer MiniLM | 24-layer bge-reranker | LLM listwise  |
| :--------- | :------------- | :-------------------- | :------------ |
| 20         | under 10 ms    | 30 to 60 ms           | 400 to 800 ms |
| 100        | 20 to 50 ms    | 150 to 400 ms         | 1 to 3 s      |
| 200        | 50 to 100 ms   | 300 to 800 ms         | 2 to 6 s      |

The 100-candidate row is the usual operating point. It adds under half a second and typically moves nDCG@10 by 10 to 20 points.

## LLM-based reranking

Instead of scoring each pair, give the LLM the whole candidate list and ask for a permutation.

RankGPT (Sun et al., arXiv:2304.09542) uses a sliding window over the list: rank positions 1 to 20, slide to 11 to 30, and so on, so the model never sees more than it can attend to well. It reports that GPT-4 reranking exceeds a supervised cross-encoder on TREC-DL and BEIR, and introduces **permutation distillation**, where a GPT-4 ranking is used as the training target for a small specialized model.

| Property                 | Cross-encoder          | LLM listwise                               |
| :----------------------- | :--------------------- | :----------------------------------------- |
| Sees candidates jointly  | No, one pair at a time | Yes, the whole window                      |
| Handles long chunks      | Truncates              | Fits the window                            |
| Latency                  | Tens of milliseconds   | Seconds                                    |
| Cost                     | Low                    | High                                       |
| Zero-shot on new domains | Moderate               | Strong                                     |
| Explanations             | None                   | Can be requested                           |
| Position bias            | None                   | Real; the list order influences the output |

Position bias is the practical catch. LLM rerankers systematically favour candidates near the start of the list they were given, so shuffling the input order and averaging, or permuting and taking a consensus, measurably improves results.

For most production systems the answer is a small supervised cross-encoder for the top 100 and an LLM only for the ambiguous cases a confidence threshold flags.

## ColBERT and late interaction

ColBERT (Khattab and Zaharia, SIGIR 2020, arXiv:2004.12832) sits between the two. Encode the query and the document independently into a **matrix of per-token vectors** rather than a single vector, then score by summing each query token's best match in the document.

$$
S(q, d) = \sum_{i \in |q|} \max_{j \in |d|} \left( \mathbf{E}_{q,i} \cdot \mathbf{E}_{d,j}^\top \right)
$$

where $\mathbf{E}_q \in \mathbb{R}^{|q| \times d}$ has one vector per query token and $\mathbf{E}_d \in \mathbb{R}^{|d| \times d}$ has one vector per document token.

This is **MaxSim**: a maximum over document positions, then a sum over query positions.

| Property             | Bi-encoder      | ColBERT              | Cross-encoder  |
| :------------------- | :-------------- | :------------------- | :------------- |
| Document encoding    | Once            | Once                 | Per query      |
| Token-level matching | No              | Yes                  | Yes            |
| Interaction depth    | One dot product | Max per query token  | Full attention |
| Storage per chunk    | One vector      | One vector per token | None           |
| First-stage capable  | Yes             | Yes                  | No             |

The `max` is what buys the accuracy. "Which port does the API use" matches the token "port" specifically rather than diluting into an averaged sentence vector, so exact-term behaviour improves without giving up the dense representation.

The cost is storage. A 300-token chunk needs 300 vectors instead of one, so a ColBERT index runs one to two orders of magnitude larger than a single-vector index. Two pieces of work make that tractable:

**ColBERTv2** (Santhanam et al., arXiv:2112.01488) compresses each token vector to a centroid id plus a residual quantized to one or two bits per dimension, and trains on denoised supervision where false negatives are filtered out. It reports a large storage reduction over ColBERTv1 with better accuracy.

**PLAID** (Santhanam et al., arXiv:2205.09707) is the engine. It scores candidates against cluster centroids first, prunes aggressively, and only computes full MaxSim on the survivors, reaching hundreds of queries per second on a CPU.

ColBERT can serve as the first-stage retriever or as the reranker. As a reranker over a hundred BM25-plus-dense candidates it is competitive with a cross-encoder at a fraction of the latency, because the document side is already encoded.

## Placing the reranker

```text
hybrid retrieval, 50 dense + 50 sparse
        |
        v
   RRF fusion -> top 40 unique
        |
        v
   cross-encoder rerank -> scores
        |
        v
   threshold and MMR diversify -> top 5
        |
        v
   generation with citations
```

Two things after the reranker that are easy to skip:

**Thresholding.** Reranker scores are not probabilities and are not calibrated across queries, but a relative cutoff still works: if the best score is below a floor, or the top score is not clearly separated from the rest, return "not found" instead of generating. This is the cheapest hallucination gate in the system.

**Diversity.** A reranker optimizes relevance, and the top five can be five near-duplicates from the same section. Maximal Marginal Relevance reorders to balance relevance against novelty:

$$
\text{MMR}(d) = \lambda \cdot \text{rel}(d) - (1 - \lambda) \max_{s \in S} \text{sim}(d, s)
$$

with `lambda` around 0.7. See [Production Debugging](/ai/rag/production-debugging) for the duplicate-chunk failure mode this fixes.

## Interview questions

<Accordions>
  <Accordion title="Why does a pipeline need a reranker if retrieval already scores relevance?">

    Retrieval must score a query against millions of chunks, so it scores them independently with a dot product and the query and document never attend to each other. A reranker scores a hundred candidates jointly with full cross-attention. The division of labour is recall first on a huge set, precision second on a small one.

  </Accordion>
  <Accordion title="What is the difference between a bi-encoder and a cross-encoder?">

    A bi-encoder encodes the query and the document separately and scores with a dot product, so document vectors can be precomputed and indexed. A cross-encoder concatenates query and document and runs one forward pass, producing a score at the `[CLS]` token. Nothing is precomputable, which is why it can only run on a small candidate set.

  </Accordion>
  <Accordion title="Why are cross-encoders more accurate?">

    Term matching becomes contextual. A bi-encoder must fix the meaning of "bank" before it sees the query. A cross-encoder reads the query and the candidate together, so the same surface form resolves differently per candidate.

  </Accordion>
  <Accordion title="What is a reasonable candidate count and what does it cost?">

    About 100. On one modern GPU with 512-token chunks, a 24-layer reranker over 100 candidates takes roughly 150 to 400 ms and typically moves nDCG@10 by 10 to 20 points. Two hundred candidates doubles the latency for a smaller gain.

  </Accordion>
  <Accordion title="How does LLM listwise reranking differ, and what is its main problem?">

    It gives the model the whole candidate list and asks for a permutation rather than scoring pairs independently, so candidates are compared against each other. RankGPT (arXiv:2304.09542) uses a sliding window to keep the list manageable. The main problem is position bias: the model systematically favours candidates near the start of the input list, so you shuffle and average or take a consensus over permutations.

  </Accordion>
  <Accordion title="What is permutation distillation?">

    Training a small specialized reranker to reproduce GPT-4's listwise rankings, from RankGPT. It moves the quality of an LLM reranker into a model cheap enough to run on every query.

  </Accordion>
  <Accordion title="Write the ColBERT scoring function and name it.">

    `S(q, d) = sum over i in |q| of max over j in |d| of (E_q_i . E_d_j^T)`. It is MaxSim, or late interaction: a maximum over document token positions, then a sum over query token positions. Queries and documents are encoded into per-token matrices independently, so the document side is still precomputable.

  </Accordion>
  <Accordion title={<>What does the <code>max</code> in MaxSim buy you?</>}>

    Exact token-level matching inside a dense representation. "Which port does the API use" matches the document token "port" specifically instead of diluting into an averaged sentence vector. It recovers much of what BM25 gives you without leaving the embedding space.

  </Accordion>
  <Accordion title="What is the storage cost of ColBERT and how is it mitigated?">

    A 300-token chunk needs 300 vectors instead of one, so the index runs one to two orders of magnitude larger. ColBERTv2 (arXiv:2112.01488) stores a centroid id plus a one-to-two-bit residual per dimension and trains on denoised supervision. PLAID (arXiv:2205.09707) scores against centroids first and only computes full MaxSim on survivors.

  </Accordion>
  <Accordion title="Can ColBERT be a first-stage retriever?">

    Yes, unlike a cross-encoder, because the document side is precomputed and indexed. In practice it is often used as the reranker over hybrid candidates, where it matches a cross-encoder at much lower latency since encoding already happened at index time.

  </Accordion>
  <Accordion title="Reranker scores are not probabilities. How do you still use them as a gate?">

    With a relative cutoff rather than an absolute one. If the best score is below a floor, or the top score is not clearly separated from the rest of the list, return "not found" instead of generating. It is uncalibrated across queries but reliable within one, which is enough for the decision.

  </Accordion>
  <Accordion title="Why apply MMR after reranking?">

    A reranker optimizes relevance, so the top five can be five near-duplicate chunks from the same section, wasting budget and reinforcing one source. `MMR(d) = lambda * rel(d) - (1 - lambda) * max_s sim(d, s)` with `lambda` around 0.7 penalizes similarity to already-selected chunks and restores diversity.

  </Accordion>
</Accordions>
