A loader hands over bytes. A PDF's bytes are drawing instructions, an HTML page's bytes are mostly menus and scripts, a scanned contract's bytes are a photograph, and a spreadsheet's bytes are a ZIP archive of XML. **Parsing** (also called **extraction**) turns each of those into what the rest of the pipeline needs: clean text, in reading order, with its structure (headings, lists, tables, captions) still visible.

This is where most RAG systems quietly lose. A two-column page read straight across, a table flattened into a stream of numbers, a running header repeated in every chunk: none of these raise an error. They produce an index full of text that looks plausible and retrieves badly, and no later stage can recover what was lost.

## The plain-language version

The loader is the mail clerk who collected the envelopes. The parser is the person who opens each one and types up what is inside. A careless typist copies every word in the order it appears on the paper, so a newspaper page comes out with lines from two columns mixed together, a table comes out as a jumble of numbers, and the page number "Page 3 of 40" appears in the middle of a sentence. A careful typist recognizes columns, headings, tables, and captions, and types it up so it reads the way a person would read it.

Good parsing output is usually **Markdown** (or a list of typed elements): headings as `#` lines, tables as Markdown or HTML tables, lists as lists. Markdown is the common target because LLMs read it well and chunkers can split on its headings.

## Why parsing decides quality

| Parsing failure                   | What lands in the index                             | What it does to retrieval                                                   |
| :-------------------------------- | :-------------------------------------------------- | :-------------------------------------------------------------------------- |
| Two columns read straight across  | Sentences made of half-lines from both columns      | Chunks mean nothing; no query matches them                                  |
| Table flattened to text           | `Region Q3 Q4 EU 4.1 4.6 US 9.8 10.2`               | Numbers detached from their row and column; wrong answers cited confidently |
| Running header and footer kept    | "ACME Confidential Page 3 of 40" inside every chunk | Every chunk shares the same words; similarity becomes noise                 |
| Scanned page with no OCR          | Empty text                                          | The document silently does not exist                                        |
| Headings lost                     | One undifferentiated wall of text                   | Chunker cannot split by section; no section path for metadata               |
| Ligatures and hyphenation left in | `ﬁnancial`, `regu-` newline `lation`                | Keyword search for "financial regulation" misses                            |

None of these produce an error message. The only defence is to **look at the parsed output** for a sample of each document type before indexing anything.

## What good output looks like

The target has three parts:

1. **Clean text in reading order**, with boilerplate removed and words rejoined.
2. **Structure**: heading levels, lists, tables with their header rows, captions attached to their figures and tables.
3. **Location metadata**: source, page number, and ideally a bounding box per element, so a citation can open the right page and highlight the passage.

```text
# 4. Security                                     <- heading level kept
## 4.2 Access tokens
Tokens expire after 24 hours. Refresh tokens ...  <- clean body text

Table 3: Token lifetimes by plan                  <- caption attached to its table
| Plan       | Access token | Refresh token |
| ---------- | ------------ | ------------- |
| Free       | 1 hour       | 7 days        |
| Enterprise | 24 hours     | 90 days       |
```

metadata per element: `page: 12`, `bbox: [72, 410, 540, 520]`, `section_path: "4. Security > 4.2 Access tokens"`, `type: "table"`.

That `section_path` is what [Chunking](/ai/rag/chunking) later prepends to each chunk, and it only exists if parsing kept the headings.

## Born-digital versus scanned

The first decision for every document: is there real text inside it, or a picture of text?

| Kind                       | How to recognize it                                                  | Extraction route                                              | Speed and cost                   |
| :------------------------- | :------------------------------------------------------------------- | :------------------------------------------------------------ | :------------------------------- |
| **Born-digital**           | Text can be selected and copied in a viewer; extraction returns text | Read the text layer, then layout analysis                     | Fast and cheap                   |
| **Scanned**                | Text cannot be selected; extraction returns nothing or very little   | Render to image, then OCR                                     | Slow; may need a GPU or paid API |
| **Mixed**                  | Some pages have text, some are scans (a contract with signed pages)  | Decide per page                                               | Varies                           |
| **Scanned with OCR layer** | Text can be selected, but it came from an earlier OCR run            | Read the text layer, but check quality; old OCR is often poor | Fast                             |

A practical per-page test: extract the text layer and count characters. A page with an image covering it and almost no extracted characters needs OCR. Tools such as Unstructured's `strategy="auto"` and Docling make this decision for you.

## Plain text, Markdown, and code

The easy cases, with three traps:

- **Character encoding.** Decode as UTF-8, and handle files that are not: detect the encoding (the `charset-normalizer` library), and repair mojibake (`cafÃ©` instead of `café`) with `ftfy`. [Encoding and Decoding](/ai/math-foundations/encoding-and-decoding#character-encodings) explains both.
- **Markdown is already structured.** Keep the headings; they are the best possible split points.
- **Code needs structure-aware handling.** Split by function and class (using a parser such as tree-sitter), keep the file path and symbol name in metadata, and skip generated, vendored, and minified files. A function split in half is as useless as a table split in half.

## HTML and web pages

An HTML page is mostly not the article. Navigation menus, sidebars, footers, cookie banners, related-article lists, scripts, and styles often outweigh the content itself. **Main-content extraction** keeps the article and drops the rest.

How it works:

1. **Drop elements that are never content**: `<script>`, `<style>`, `<nav>`, `<header>`, `<footer>`, `<aside>`, forms, and hidden elements.
2. **Score the remaining blocks** by signals of being prose: text length, punctuation density, few links per word. A block of short link text is a menu; a block of long sentences is an article. This is the approach of Mozilla's Readability and of `trafilatura`.
3. **Keep the structure**: convert `<h1>` to `<h3>` into Markdown headings, `<li>` into list items, and `<table>` into a table.
4. **Keep the metadata**: `<title>`, the canonical URL, publication and modified dates from `<meta>` tags.

A minimal version with only the standard library:

```python title="html_main_text.py"
from html.parser import HTMLParser

html = """<html><head><title>Refund policy</title><script>track()</script></head>
<body><nav>Home | Shop | Cart</nav>
<main><h1>Refund policy</h1><p>Refunds are available within 30 days.</p>
<h2>Exceptions</h2><p>Gift cards are final sale.</p></main>
<footer>(c) 2026 Example Ltd</footer></body></html>"""

class MainText(HTMLParser):
    SKIP = {"script", "style", "nav", "footer", "header", "aside"}
    def __init__(self):
        super().__init__()
        self.skip_depth, self.lines, self.prefix = 0, [], ""
    def handle_starttag(self, tag, attrs):
        if tag in self.SKIP:
            self.skip_depth += 1
        elif tag in {"h1", "h2", "h3"}:
            self.prefix = "#" * int(tag[1]) + " "      # keep headings as Markdown
    def handle_endtag(self, tag):
        if tag in self.SKIP:
            self.skip_depth -= 1
    def handle_data(self, data):
        if self.skip_depth == 0 and data.strip() and self.lasttag != "title":
            self.lines.append(self.prefix + data.strip())
            self.prefix = ""

p = MainText()
p.feed(html)
print("\n".join(p.lines))
# # Refund policy
# Refunds are available within 30 days.
# ## Exceptions
# Gift cards are final sale.
```

The menu, the tracking script, and the footer are gone; the two headings survive as Markdown. Real pages need the scoring step too, because many sites do not use `<nav>` and `<main>` tags. In production, use `trafilatura`, `readability-lxml`, or a crawler that returns Markdown directly (Firecrawl, Crawl4AI). For pages rendered by JavaScript, the loader must render first; see [Document Loaders](/ai/rag/document-loaders#loading-the-web).

## PDFs

### How a PDF stores text

A PDF is not a text document. It is a set of **drawing instructions** for a printer: "use this font, move to coordinates (72, 700), draw these glyphs". There are no paragraphs, no columns, no table cells, and often no spaces, only characters placed at positions. Some consequences:

- **Reading order is not stored.** Text is drawn in whatever order the generating software chose, which may jump between columns, headers, and footnotes.
- **Words can be split.** A word may be drawn as several separately positioned pieces, and spaces are often inferred from gaps between glyphs.
- **Characters can be unmappable.** A glyph is a picture in a font. If the font has no table mapping glyphs back to Unicode (a `ToUnicode` map), extraction returns garbage or nothing, even though the page looks perfect.
- **Tables are just lines and text.** A table is some drawn lines plus text placed in a grid; nothing says "this is a cell".

### Three levels of extraction

| Level                        | What it does                                                                                                                                                                | Tools                                                                                   | Good enough for                                   |
| :--------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------- | :------------------------------------------------ |
| **1. Text layer extraction** | Reads the glyphs and their positions, and joins them into lines with simple heuristics                                                                                      | `pypdf`, `pdfminer.six`, PyMuPDF (`fitz`)                                               | Single-column, born-digital prose: reports, books |
| **2. Rule-based layout**     | Uses positions, font sizes, and drawn lines to find columns, headings (larger or bold fonts), and table grids                                                               | `pdfplumber`, PyMuPDF with your own logic, Camelot, Tabula                              | Consistent document templates you can tune for    |
| **3. ML layout analysis**    | Renders each page as an image and runs a model trained to detect regions (title, text, table, figure, header, footer, formula), orders them, and recognizes table structure | Docling, Unstructured `hi_res`, Marker, MinerU, LlamaParse, Azure Document Intelligence | Mixed layouts, multi-column papers, forms, tables |

Level 3 models are trained on datasets of annotated pages, such as DocLayNet (Pfitzmann et al., arXiv:2206.01062), and descend from layout-aware models such as LayoutLM (Xu et al., arXiv:1912.13318), which reads text together with its position on the page. Docling's approach is described in arXiv:2408.09869.

The trade-off is speed and cost for accuracy. Level 1 handles many pages per second on a CPU. Level 3 is far slower per page, and fastest on a GPU. A common production pattern is to **route by document**: level 1 for simple born-digital files, level 3 for anything with columns, tables, or scans.

### Cleaning up after extraction

- **Remove running headers and footers**: lines that repeat at the same position on most pages (a title, "Confidential", page numbers).
- **Rejoin hyphenated words**: `regu-` at a line end plus `lation` becomes `regulation`.
- **Normalize ligatures and odd characters**: Unicode NFKC normalization turns the single character `ﬁ` into `fi`.
- **Merge lines into paragraphs**: line breaks inside a paragraph are layout, not meaning.

Multi-column pages are the classic failure, with a full table of what layout-aware parsing recovers in [Vectorless RAG](/ai/rag/vectorless-rag#complex-multi-column-pdfs).

## OCR

When there is no text layer, the text has to be read from pixels.

**The classic pipeline:**

<Steps>
<Step>

**Render and preprocess.** Render each page at about 300 DPI, convert to grayscale, deskew (straighten a tilted scan), remove noise, and binarize (black text on white).

</Step>
<Step>

**Detect text regions.** Find the boxes that contain lines or words of text.

</Step>
<Step>

**Recognize.** Read the characters in each box with a recognition model, producing text plus a **confidence score** per word.

</Step>
<Step>

**Lay out.** Order the recognized lines into reading order, and feed the result into the same layout analysis as a born-digital page.

</Step>
</Steps>

| Approach                            | Examples                                                                                        | Strengths                                                               | Weaknesses                                                            |
| :---------------------------------- | :---------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------- | :-------------------------------------------------------------------- |
| **Classic open-source OCR engines** | Tesseract, PaddleOCR, EasyOCR                                                                   | Free, local, fast on clean printed text                                 | Struggle with poor scans, handwriting, complex layouts                |
| **Cloud document AI services**      | Azure Document Intelligence, AWS Textract, Google Document AI                                   | OCR plus layout, tables, forms, and key-value pairs in one call         | Per-page cost; data leaves your environment                           |
| **Vision-language models**          | Sending page images to a multimodal LLM, or OCR-specialized VLMs such as olmOCR and Mistral OCR | Handle messy layouts, handwriting, and charts; output Markdown directly | Slower and costlier; can **hallucinate** text that is not on the page |

<Callout type="warn">
  ### Common mistake: trusting VLM transcription blindly

A classic OCR engine that cannot read a word outputs garbage or a low-confidence score, which you can detect. A vision-language model that cannot read a word may output a plausible word instead, with no signal. For documents where exact figures matter (invoices, contracts, medical records), keep confidence checks, compare against a classic engine on a sample, or have the model mark unreadable regions explicitly.

</Callout>

**Skip OCR entirely** is also an option: ColPali (Faysse et al., arXiv:2407.01449) embeds page images directly with a vision-language model and retrieves pages without extracting text at all. It is strong for visually rich documents (slides, brochures, charts), and the retrieved page images are then passed to a multimodal model to answer.

## Tables

Tables carry the densest facts in most business documents: prices, limits, specifications, results. They are also what naive parsing destroys most completely. Table handling has three steps: **find** the table, **recognize its structure**, and **serialize** it into something retrievable.

### Finding and recognizing tables

| Source                        | How the table is found                               | How structure is recognized                                                             | Tools                                                                                                                 |
| :---------------------------- | :--------------------------------------------------- | :-------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| **HTML**                      | The `<table>` tag                                    | Already explicit: `<tr>`, `<th>`, `<td>`, with `rowspan` and `colspan` for merged cells | `pandas.read_html`, any HTML parser                                                                                   |
| **DOCX, PPTX**                | Table objects in the XML                             | Explicit rows and cells                                                                 | `python-docx`, `python-pptx`, Docling                                                                                 |
| **Spreadsheets, CSV**         | The whole sheet is a table (or several)              | Header detection; see the next section                                                  | `pandas`, `openpyxl`                                                                                                  |
| **Born-digital PDF, ruled**   | Drawn lines form a grid                              | Cells are the boxes between the lines (Camelot's **lattice** mode)                      | Camelot, pdfplumber                                                                                                   |
| **Born-digital PDF, unruled** | Text aligned in columns with whitespace between them | Columns inferred from gaps in x positions (Camelot's **stream** mode)                   | Camelot, Tabula, pdfplumber                                                                                           |
| **Scanned or complex**        | A detection model draws a box around each table      | A structure model predicts rows, columns, header cells, and spanning cells              | Table Transformer (trained on PubTables-1M, Smock et al., arXiv:2110.00061), Docling's TableFormer, cloud document AI |

The hard parts are **merged cells** (one header spanning three columns), **multi-row headers**, **tables that continue across pages** (the second half has no header row), and **nested tables**. Check a sample of each against the original.

### Five ways to represent a table for retrieval

Once the structure is known, it must be written as text for embedding and for the prompt. The choice depends on the table's size and on what questions will be asked.

| Representation           | What it looks like                                                                                                    | Best for                                                                           | Weakness                                                                 |
| :----------------------- | :-------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------- | :----------------------------------------------------------------------- |
| **Markdown table**       | `\| region \| revenue \|` rows                                                                                        | Small, simple tables placed directly in a prompt                                   | Cannot express merged cells; the header is far from cells in long tables |
| **HTML table**           | `<table>` with `rowspan` and `colspan`                                                                                | Tables with merged cells or multi-level headers                                    | More tokens                                                              |
| **Row serialization**    | One line per row with every column named: `region: EU; quarter: Q3; revenue_musd: 4.1`                                | Long, narrow tables; each row is a self-contained fact that can be retrieved alone | Repeats column names; loses the at-a-glance comparison                   |
| **Summary plus payload** | Embed an LLM-written or caption-based description of the table; store the full table as payload returned with the hit | Large tables where a query should find "the table about X"                         | Needs an extra LLM call per table at indexing time                       |
| **Load into a database** | Store as a SQL or DuckDB table; answer with text-to-SQL                                                               | Large or numeric tables; questions that filter, sum, or compare                    | A separate retrieval path                                                |

```python title="table_serialization.py"
import io
import pandas as pd

csv = """region,quarter,revenue_musd,growth_pct
EU,Q3,4.1,12
US,Q3,9.8,7
APAC,Q3,2.6,21
"""
df = pd.read_csv(io.StringIO(csv))
print(df.shape)                                    # (3, 4)

# 1. Markdown table: good for small tables placed straight into a prompt
header = "| " + " | ".join(df.columns) + " |"
rule = "|" + "|".join(" --- " for _ in df.columns) + "|"
rows = ["| " + " | ".join(str(v) for v in r) + " |" for r in df.itertuples(index=False)]
print("\n".join([header, rule, *rows]))
# | region | quarter | revenue_musd | growth_pct |
# | --- | --- | --- | --- |
# | EU | Q3 | 4.1 | 12 |
# | US | Q3 | 9.8 | 7 |
# | APAC | Q3 | 2.6 | 21 |

# 2. Row serialization: one self-contained line per record, header repeated in every line
for r in df.to_dict("records"):
    print("; ".join(f"{k}: {v}" for k, v in r.items()))
# region: EU; quarter: Q3; revenue_musd: 4.1; growth_pct: 12
# region: US; quarter: Q3; revenue_musd: 9.8; growth_pct: 7
# region: APAC; quarter: Q3; revenue_musd: 2.6; growth_pct: 21

# 3. Row groups that each carry the caption and header, so any chunk can be read alone
def row_chunks(frame, rows_per_chunk=2, caption="Revenue by region, Q3"):
    for start in range(0, len(frame), rows_per_chunk):
        part = frame.iloc[start:start + rows_per_chunk]
        yield caption + "\n" + part.to_csv(index=False).strip()

for c in row_chunks(df):
    print("----\n" + c)
# ----
# Revenue by region, Q3
# region,quarter,revenue_musd,growth_pct
# EU,Q3,4.1,12
# US,Q3,9.8,7
# ----
# Revenue by region, Q3
# region,quarter,revenue_musd,growth_pct
# APAC,Q3,2.6,21
```

The third form is the one to use when a table is too big for one chunk: every chunk repeats the caption and header row, so the second chunk is still readable on its own. Splitting the table without repeating the header leaves `APAC,Q3,2.6,21` as an unretrievable string of values.

<Callout type="warn">
  ### Three table rules

**Never split a table without repeating its header.** A table chunk with no header is a list of numbers with no meaning.

**Keep the caption and section heading with the table.** "Table 4" retrieves nothing; "Table 4: Latency by region, Q3 performance review" retrieves well.

**Do not answer arithmetic from embeddings.** "Which region grew fastest?" needs a comparison across rows. Put the whole table in the context, or send the question to SQL. Similarity search only finds the table; it cannot compute over it.

</Callout>

[Vectorless RAG](/ai/rag/vectorless-rag#markdown-tables) covers the prompt-side handling of large tables (column selection, row serialization, and DuckDB).

## Spreadsheets and CSV

A spreadsheet looks like one table and is often several, with notes, blank rows, and totals mixed in.

- **Read every sheet.** An Excel workbook (`.xlsx`) is a ZIP of XML files, one per sheet. `pandas.read_excel(path, sheet_name=None)` returns all sheets as a dictionary.
- **Find the real header.** Titles and notes often sit above the header row. Detect the first row whose cells are all non-empty text, or let a person configure it per template.
- **Formulas versus values.** A cell may hold `=SUM(B2:B9)`. With `openpyxl`, `load_workbook(path, data_only=True)` returns the value Excel last calculated and saved, not the formula; without it you get the formula string.
- **Merged cells** span several cells but store their value only in the top-left one. Forward-fill them so every row knows its group.
- **Totals and subtotals** rows look like data. Mark or drop them so a sum is not counted twice.
- **Decide the unit**: per row (row serialization, for lookup questions), per sheet (for small sheets), or into SQL (for analysis questions).

## Images, charts, and diagrams

Text inside a figure (labels, chart values, a screenshot of an error message) is invisible to a text-only parser.

| Option                       | How                                                                                         | Good for                                    |
| :--------------------------- | :------------------------------------------------------------------------------------------ | :------------------------------------------ |
| **OCR the image**            | Run OCR on the figure region                                                                | Screenshots, scanned figures with text      |
| **Caption with a VLM**       | Ask a vision-language model to describe the figure, or to extract a chart's data as a table | Charts and diagrams whose meaning is visual |
| **Use the existing caption** | Attach the document's own caption and surrounding paragraph to the figure                   | Papers and reports with good captions       |
| **Multimodal embedding**     | Embed the image itself with an image-text model (CLIP-style) or the whole page (ColPali)    | Image search; visually rich pages           |

Store the image path with the generated text, so the answer can show the original figure.

## Email and chat

- **Parse the MIME structure.** An email is a tree of parts: plain text, HTML, attachments. Python's `email` package parses it. Prefer the plain-text part, or extract text from the HTML part.
- **Strip quoted replies and signatures.** Each reply repeats the whole thread below it. Without stripping, one sentence appears in the index twenty times.
- **Group into threads.** The `Message-ID`, `In-Reply-To`, and `References` headers link replies. A thread is usually a better document than a single message.
- **Recurse into attachments.** Each attachment goes back through file-type detection and its own parser.
- **Expect personal data** everywhere; see PII handling in [Ingestion Pipeline](/ai/rag/ingestion-pipeline#personal-and-sensitive-data).

## Audio and video

Speech has to become text first. **Automatic speech recognition (ASR)** with a model such as Whisper (Radford et al., arXiv:2212.04356) produces a transcript with timestamps. Two additions make it retrievable:

- **Timestamps in metadata**, so a citation can jump to the moment in the recording.
- **Speaker diarization** (who spoke when), so "what did the CFO say about hiring" can be answered. Libraries such as pyannote do this.

For video, sample frames and caption or OCR the slides shown on screen, and merge them with the transcript by timestamp.

## Choosing a parser

| Tool                                                              | How it works                                                                                                                     | Best at                                                            |
| :---------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------- |
| **pypdf, pdfminer.six**                                           | Pure Python; read the text layer and positions                                                                                   | Simple born-digital PDFs, no dependencies                          |
| **PyMuPDF**                                                       | Bindings to the MuPDF C library; fast text, words with coordinates, page rendering. AGPL licensed (commercial license available) | Speed; building your own layout logic                              |
| **pdfplumber**                                                    | Built on pdfminer.six; exposes characters, lines, and rectangles                                                                 | Rule-based table extraction and debugging layouts visually         |
| **Camelot, Tabula**                                               | Table extraction from born-digital PDFs, with lattice (ruled) and stream (whitespace) modes                                      | Tables in consistent born-digital reports                          |
| **Docling** (IBM)                                                 | Layout model plus TableFormer table structure model; outputs Markdown, HTML, or JSON with full structure                         | Open-source, local, structure-rich parsing of PDF and Office files |
| **Unstructured**                                                  | `partition()` routes by file type; PDF strategies `fast` (text layer), `hi_res` (layout model), `ocr_only`, `auto`               | One interface for many formats; typed elements                     |
| **Marker, MinerU**                                                | Pipelines of layout, OCR, and table models producing Markdown                                                                    | Books and papers, including equations                              |
| **Nougat** (arXiv:2308.13418)                                     | A model that transcribes academic pages straight to Markdown with LaTeX                                                          | Scientific papers                                                  |
| **LlamaParse**                                                    | Hosted parsing service from LlamaIndex                                                                                           | Complex documents without running models yourself                  |
| **MarkItDown** (Microsoft)                                        | Converts many formats (PDF, Office, HTML, images, audio) to Markdown                                                             | Quick conversion for LLM input                                     |
| **Apache Tika**                                                   | Java server; detection and extraction for a very wide range of formats                                                           | Legacy and unusual formats                                         |
| **Tesseract, PaddleOCR, EasyOCR**                                 | OCR engines                                                                                                                      | Local OCR                                                          |
| **Azure Document Intelligence, AWS Textract, Google Document AI** | Cloud OCR plus layout, tables, forms, and key-value extraction                                                                   | Scans and forms at scale, without running models                   |
| **trafilatura, readability-lxml**                                 | Main-content extraction for HTML                                                                                                 | Web pages                                                          |

A reasonable default: route by type. HTML through trafilatura; Office files and PDFs through Docling or Unstructured; simple born-digital PDFs through PyMuPDF for speed; scans through a cloud document AI service or a local OCR model; tables kept as HTML or Markdown with their captions.

## Checking parse quality

Parsing fails silently, so measure it:

- **Eyeball a sample** of every document type and every template, side by side with the original. Nothing replaces this.
- **Characters per page**: near zero means a scan that skipped OCR or a font with no Unicode map.
- **Garbage ratio**: the share of replacement characters (`�`), unusual symbols, or non-dictionary words. A spike means a broken font map or bad OCR.
- **Repeated lines across pages**: headers and footers that were not removed.
- **Table checks**: the number of tables found, and whether each has a header row.
- **OCR confidence**: the average word confidence per page, with low pages queued for review or a stronger parser.
- **Downstream check**: questions whose answers are known to be in a document, run through retrieval. If the answer never comes back, look at the parsed text before touching the retriever.

## Interview questions

<Accordions>
  <Accordion title="Why is PDF text extraction hard?">

    A PDF stores drawing instructions: glyphs placed at coordinates. It has no paragraphs, reading order, columns, or table cells, and fonts may lack a Unicode mapping. Extraction must infer words, lines, columns, and tables from positions, which fails on multi-column layouts, tables, and headers and footers.

  </Accordion>
  <Accordion title="How do you extract tables from documents for RAG?">

    Detect the table (explicit in HTML and Office, line or whitespace analysis in born-digital PDFs, a detection model for scans), recognize its structure (rows, columns, headers, merged cells), then serialize it: Markdown for small tables, HTML for merged cells, row serialization for long tables, a summary embedding with the table as payload, or a SQL table for numeric questions. Keep the caption and header with every piece.

  </Accordion>
  <Accordion title="How do you handle scanned documents?">

    Detect pages without a usable text layer, render them to images, preprocess (deskew, denoise), run OCR with layout analysis, and keep confidence scores. Options range from Tesseract and PaddleOCR to cloud document AI services and vision-language models, which handle messy pages better but can hallucinate. ColPali-style retrieval can skip text extraction entirely.

  </Accordion>
  <Accordion title="What is layout analysis?">

    Detecting the regions on a page (titles, paragraphs, columns, tables, figures, headers, footers, formulas) and their reading order. Rule-based approaches use fonts and positions; ML approaches render the page and run a model trained on annotated layouts such as DocLayNet.

  </Accordion>
  <Accordion title="What would you do with a 10,000-row spreadsheet in a RAG system?">

    Not embed it whole. Load it into a SQL engine such as DuckDB and answer analytic questions with text-to-SQL; optionally index a description of the table and its columns so retrieval can find it, and serialize rows individually only if the questions are row lookups.

  </Accordion>
  <Accordion title="Why remove headers and footers?">

    They repeat on every page, so they end up in every chunk. Shared boilerplate pulls every chunk's embedding toward the same point and adds the same keywords everywhere, making both dense and keyword retrieval noisier.

  </Accordion>
  <Accordion title="Why is Markdown a common parsing target?">

    It keeps structure (heading levels, lists, tables) in plain text that LLMs read well and that chunkers can split on, and it is compact compared with HTML or JSON.

  </Accordion>
  <Accordion title="Where do vision-language models fit in document parsing?">

    They can transcribe whole pages to Markdown, describe charts, and read handwriting where classic OCR fails. The costs are speed, price, and the risk of hallucinated text with no confidence signal, so they are usually used for the hard pages, with checks on documents where exact figures matter.

  </Accordion>
</Accordions>
