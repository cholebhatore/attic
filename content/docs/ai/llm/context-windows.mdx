title: Context Windows
description: The quadratic attention compute and linear KV-cache growth that bound a context window, real per-token memory numbers, and how RoPE scaling extends them.
---

A context window is not a free design choice. Four separate limits push back on it, and an interviewer who asks "why can't we just make the context bigger?" wants all four.

1. **Attention compute** grows as `O(N^2)` in sequence length.
2. **KV-cache memory** grows as `O(N)` per request, per layer.
3. **Positional encodings** are trained on a finite range and degrade outside it.
4. **Attention quality** falls off well before the hard limit, so the effective window is smaller than the advertised one.

---

## The plain-language version

**Where this sits:** the limit on how much a model can read at once, and why it cannot simply be made bigger.

The **context window** is the maximum number of tokens the model can take in one go: the prompt, any documents, the conversation so far, and the answer. Four separate things limit it. Attention compares every token with every other, so the work grows with the square of the length. The KV cache stores information for every token, so memory grows with the length. Position information was only trained up to some length, and beyond it the model is lost. And even within the limit, models use the middle of a long context less reliably than the start and end.

Think of a desk. A bigger desk holds more papers (context), but the time to cross-reference every paper with every other grows fast, every paper needs filing space (memory), the page numbers stop at some point (positions), and the papers in the middle of a huge pile get skimmed.

This page covers, in order:

1. **Quadratic attention compute**: why doubling the length quadruples attention work
2. **Linear KV-cache growth**: real bytes per token, and why decode is limited by memory bandwidth
3. **Positional encodings outside the trained range**: Position Interpolation, NTK-aware scaling, YaRN, and others
4. **Advertised versus effective context**: what benchmarks show about usable length
5. **Sizing a context window**: working out what a given length costs

| Word                                    | Plain meaning                                                                                    |
| :-------------------------------------- | :----------------------------------------------------------------------------------------------- |
| **context window**                      | The maximum number of tokens the model processes at once, input and output together.             |
| **`O(N^2)`**                            | Work that grows with the square of the length `N`.                                               |
| **KV cache**                            | Stored keys and values per token per layer, reused during generation.                            |
| **memory-bandwidth bound**              | Limited by how fast data moves from memory, not by how fast the chip computes.                   |
| **RoPE scaling**                        | Adjusting rotary position frequencies so a model handles longer contexts than it was trained on. |
| **Position Interpolation / NTK / YaRN** | Three ways of doing that rescaling, each preserving more of the short-range detail.              |
| **effective context**                   | The length over which the model actually performs well, often well below the advertised maximum. |
| **needle in a haystack**                | A test that hides one fact in a long context. Passing it is necessary but not sufficient.        |

## Quadratic attention compute

Self-attention builds an `N x N` score matrix per head. Two matmuls produce it and consume it: `Q K^T` and `A V`.

Per layer, per token, forward FLOPs:

| Component                                 | FLOPs    |
| :---------------------------------------- | :------- |
| Q, K, V, O projections (multi-head)       | `8 d^2`  |
| SwiGLU feed-forward with `d_ff = (8/3) d` | `16 d^2` |
| Attention score matmuls                   | `4 N d`  |

The dense parts are constant in `N`. The score matmuls grow linearly per token, so the total grows as `N^2` across the sequence. Setting them equal gives the crossover:

```
4 N d = 24 d^2
N = 6 d
```

At `d_model = 4096` that is roughly 24,576 tokens. Past that point the score matmuls cost more than every weight matrix in the layer combined. Grouped-query attention shrinks the K and V projections and a wider feed-forward raises the dense constant, so the exact crossover moves, but the shape of the curve does not.

<Callout type="info">
  ### Materializing the score matrix is not an option at long context

A single 128,256-token prompt with 32 heads at bf16 needs `32 * 128256^2 * 2 bytes = 1,052,774,498,304 bytes`, about 980 GiB, for one attention matrix. FlashAttention (Dao et al., arXiv:2205.14135) never builds it. It tiles the computation so only `O(N)` of intermediate state is ever resident, using the online-softmax trick to accumulate the weighted values block by block. The `O(N^2)` FLOP cost remains; the `O(N^2)` memory cost does not.

</Callout>

## Linear KV-cache growth

During decoding, every generated token attends to every previous one. Recomputing K and V for the whole prefix each step would be quadratic, so they are cached.

```
kv_bytes = 2 * n_layers * n_kv_heads * d_head * seq_len * batch * bytes_per_param
```

The leading `2` is K and V. Per token, per layer, the cache holds `2 * n_kv_heads * d_head` values.

| Model             | Layers | KV heads      | `d_head` | Bytes per token (bf16) | At 8,192 tokens | At 128K tokens |
| :---------------- | :----- | :------------ | :------- | :--------------------- | :-------------- | :------------- |
| GPT-3 175B (MHA)  | 96     | 96            | 128      | 4,718,592 (4.5 MiB)    | 36 GiB          | 576 GiB        |
| Llama 3 70B (GQA) | 80     | 8             | 128      | 327,680 (320 KiB)      | 2.5 GiB         | 40 GiB         |
| Llama 3 8B (GQA)  | 32     | 8             | 128      | 131,072 (128 KiB)      | 1.0 GiB         | 16 GiB         |
| DeepSeek-V3 (MLA) | 61     | shared latent | —        | 70,272 (68.6 KiB)      | 0.55 GiB        | 8.6 GiB        |

GPT-3's row is the whole motivation for multi-query and grouped-query attention. Nine GiB of cache for a 2,048-token batch of one is unworkable; dropping the KV head count by 12x removes it almost entirely. DeepSeek-V3's MLA compresses further, to 576 elements per layer per token instead of 32,768. See [Attention Variants](/ai/llm/attention-variants).

The cache is what makes long context expensive at serving time rather than at build time. Weights are fixed; the cache multiplies by concurrent requests.

### Decode is memory-bandwidth bound

Each decode step reads every weight to emit one token. For an 8B model at bf16 that is 16 GB of reads per token. On a GPU with 1 TB/s of bandwidth the floor is about 16 ms per token, roughly 60 tokens per second, before any compute. Batching amortizes those reads across requests, which is why continuous batching raises throughput without raising per-request latency much.

## Positional encodings outside the trained range

RoPE rotates query and key vectors by an angle proportional to position:

```
theta_i = base^(-2i / d_head)
```

A model trained on 4,096 positions has never seen rotation angles beyond that range. Feed it position 8,000 and the dot products land in a region the attention weights were never optimized for. Output degrades before it collapses, and perplexity spikes sharply past the boundary.

Three families of fixes, all cheap relative to retraining.

### Position Interpolation

Chen et al., arXiv:2306.15595. Scale every position by `L / L'` so a 32K prompt occupies the same angle range as the original 4K training range:

```
m' = m * (L / L')
```

Downside: adjacent tokens that used to differ by a full angular step now differ by `1/8` of one, so high-frequency dimensions lose resolution. The paper shows 1,000 fine-tuning steps recover most of the loss.

### NTK-aware scaling

Instead of scaling positions, scale the base so different frequency bands stretch by different amounts:

```
base' = base * s^(d_head / (d_head - 2))
```

High-frequency dimensions, which encode local order, are barely changed. Low-frequency dimensions, which encode long-range position, absorb the extension. No fine-tuning needed for moderate factors.

### YaRN

Peng et al., arXiv:2309.00071. NTK-by-parts plus an attention temperature correction `1/t = 0.1 ln(s) + 1`, which compensates for the fact that longer contexts produce flatter attention distributions.

DeepSeek-V3's published config uses it directly:

```json
{
  "rope_theta": 10000,
  "rope_scaling": {
    "type": "yarn",
    "factor": 40,
    "original_max_position_embeddings": 4096,
    "beta_fast": 32,
    "beta_slow": 1,
    "mscale": 1.0,
    "mscale_all_dim": 1.0
  },
  "max_position_embeddings": 163840
}
```

`4096 * 40 = 163,840`, which is the advertised window. `beta_fast` and `beta_slow` are the ramp boundaries that decide which frequency dimensions get NTK treatment and which get interpolation.

### Other approaches

| Method                      | Idea                                                                                                    | Source                                 |
| :-------------------------- | :------------------------------------------------------------------------------------------------------ | :------------------------------------- |
| **Sliding window**          | Each token attends to the previous `w` tokens only; older information reaches it through stacked layers | Mistral 7B, arXiv:2310.06825           |
| **Chunked local attention** | Interleave local chunked attention with a few global layers                                             | Llama 4, `attention_chunk_size = 8192` |
| **LongRoPE**                | Search per-dimension rescale factors non-uniformly                                                      | Ding et al., arXiv:2402.13753          |
| **Dual Chunk Attention**    | Separate intra-chunk, inter-chunk, and successive-chunk offsets                                         | DeepSeek-V2                            |
| **Sparse patterns**         | Dilated and strided attention over the full sequence                                                    | Longformer, BigBird                    |

## Advertised versus effective context

Extending the window is necessary but not sufficient. RULER (Hsieh et al., arXiv:2404.06654) tests retrieval, multi-hop tracing, aggregation, and question answering at increasing lengths and finds most models degrade well before their stated limit. "Lost in the Middle" (Liu et al., arXiv:2307.03172) shows a U-shaped accuracy curve: information at the very start and very end of the context is found reliably, and information in the middle is missed.

Two causes. The positional distribution during training is skewed toward shorter sequences, so long positions are under-trained. And softmax over more candidates flattens the distribution, reducing the peak weight any single relevant token receives.

<Callout type="warn">
  ### What an interviewer is testing

"This model has a 1M token context" and "this model works at 1M tokens" are different claims. If you state a context length in an interview, say what benchmark it was measured on and at what length the accuracy started falling. Naming RULER or NoLiMa signals you have deployed long-context workloads rather than read a spec sheet.

</Callout>

## Sizing a context window

The practical constraint is usually VRAM, not FLOPs.

```
total_vram = weights + (kv_bytes_per_token * context_length * concurrent_requests) + activations
```

For Llama 3 8B at bf16 serving 32 concurrent requests with a 32K window:

```
weights   =  8B * 2 bytes               = 16 GiB
kv_cache  =  131,072 * 32,768 * 32      = 128 GiB
```

The cache is eight times the model. Quantizing the KV cache to fp8 or int4 halves or quarters that term and is usually the first optimization applied in production. PagedAttention, from vLLM (Kwon et al., arXiv:2309.06180), removes the second problem: without it, memory is preallocated per request in contiguous blocks, and internal fragmentation wastes a large fraction of it. Paging allocates in small non-contiguous blocks instead.

## Interview questions

<Accordions>
  <Accordion title="Name the four limits that bound a context window.">

    Attention compute, which grows as `O(N^2)`. KV-cache memory, which grows as `O(N)` per request per layer. Positional encodings, which were trained over a finite range and degrade outside it. And attention quality, which falls off long before any of the three becomes a hard wall, so the effective window is smaller than the advertised one.

  </Accordion>
  <Accordion title={<>Derive the crossover length at which attention score matmuls cost more FLOPs than the weight matrices in a layer, for <code>d_model = 4096</code> with a SwiGLU feed-forward.</>}>

    Per token per layer the dense projections cost `8 d^2` and a SwiGLU feed-forward with `d_ff = (8/3) d` costs `16 d^2`, so `24 d^2` independent of `N`. The score matmuls cost `4 N d` per token. Setting `4 N d = 24 d^2` gives `N = 6 d`, about 24,576 tokens at `d_model = 4096`. Past that the two attention matmuls outweigh every weight matrix in the layer together.

  </Accordion>
  <Accordion title={<>Why is the score matrix <code>O(N^2)</code> in memory but FlashAttention makes it <code>O(N)</code>, and which of the two costs does it remove?</>}>

    The `N x N` score matrix is the memory term: materialized for every head and every layer it grows quadratically. FlashAttention tiles the computation and keeps a running maximum and running sum, so it never writes that matrix and needs only `O(N)` scratch space. It removes the memory cost. The `O(N^2)` FLOPs are still there, which is why linear and sparse attention exist as a separate line of work.

  </Accordion>
  <Accordion title={<>Write the KV-cache size formula and compute bytes per token for a 32-layer model with 8 KV heads and <code>d_head = 128</code> at bf16.</>}>

    `bytes = 2 * n_layers * n_kv_heads * d_head * bytes_per_element`, the leading 2 being one key and one value per position. For 32 layers, 8 KV heads, `d_head = 128` at bf16: `2 * 32 * 8 * 128 * 2 = 131,072`, so 128 KiB per token.

  </Accordion>
  <Accordion title="Why does GPT-3 need 4.5 MiB of KV cache per token while Llama 3 8B needs 128 KiB?">

    Both use `d_head = 128`, but GPT-3 has 96 layers with full multi-head attention, so all 96 heads keep their own KV. Llama 3 8B has 32 layers and grouped-query attention with 8 KV heads shared across the query heads. The two reductions multiply: 3x fewer layers and 12x fewer KV heads, which is the 36x gap between 4.5 MiB and 128 KiB.

  </Accordion>
  <Accordion title="Why is decoding memory-bandwidth bound rather than compute bound, and what does batching do about it?">

    One decode step reads every weight and the whole KV cache to produce a handful of tokens for one sequence, so arithmetic intensity is low and the GPU waits on memory rather than on the multiply units. Continuous batching amortizes that same weight read across many sequences, which turns a bandwidth-bound step into a compute-bound one and is why throughput per GPU rises almost linearly with batch size until the cache runs out of room.

  </Accordion>
  <Accordion title="Explain position interpolation and its failure mode at high frequencies.">

    Position interpolation divides positions by the extension factor so the trained range maps onto the longer one. Every frequency is squashed by the same amount, so the high-frequency dimensions, which resolve nearby tokens, lose that resolution: adjacent positions differ by a fraction of the angle they had before. The model then cannot tell neighbours apart the way it used to, and quality drops unless it is fine-tuned to recover it.

  </Accordion>
  <Accordion title="Why does NTK-aware scaling modify the RoPE base instead of the positions?">

    Because uniform compression of positions damages exactly the fast-rotating dimensions that carry local structure. Changing the base stretches each dimension by a different amount, high frequencies barely moving and low frequencies moving most, so long-range resolution is bought without destroying adjacency information. It approximates a per-frequency interpolation for free, and needs no retraining pass to stay usable.

  </Accordion>
  <Accordion title={<>Read DeepSeek-V3's <code>rope_scaling</code> block and explain what <code>factor</code> and <code>original_max_position_embeddings</code> do together.</>}>

    `factor` is the extension ratio and `original_max_position_embeddings` is the length the weights were actually trained at, so their product is the advertised window: `4096 * 40 = 163,840`. The pair also marks the boundary for the ramp: `beta_fast` and `beta_slow` decide which frequency bands get NTK-style rescaling and which get interpolated, so the scaling is not applied uniformly across dimensions.

  </Accordion>
  <Accordion title="What is the difference between advertised and effective context length, and which benchmarks measure the second one?">

    Advertised length is the maximum the positional scheme and config permit. Effective length is the length over which accuracy actually holds, and it is always shorter. RULER, LongBench-style aggregates, and the needle-in-a-haystack family measure the second, along with multi-hop benchmarks such as NoLiMa that check whether a model can use a fact rather than merely retrieve it.

  </Accordion>
  <Accordion title={'Why does "lost in the middle" happen?'}>

    Retrieval over a long context is a ranking problem, and the ranking distribution is trained unevenly: recency and first-position content dominate typical training sequences, while a middle document must compete with everything else for attention mass. The result is the U-shaped curve from Liu et al. (arXiv:2307.03172), where accuracy is highest at the start and the end of the window and drops in between.

  </Accordion>
  <Accordion title="A 70B model at bf16 has to serve 64 concurrent 16K-token requests. Which term dominates the VRAM budget, and name two ways to shrink it.">

    The KV cache dominates. At 320 KiB per token, one 16K-token request holds about 5 GiB, and 64 concurrent requests about 340 GiB, against 140 GB of weights. Two levers: shrink the cache per token with grouped-query or latent attention, and store it at lower precision or reuse it across requests with prefix caching and paging.

  </Accordion>
</Accordions>
