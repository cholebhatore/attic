Running an LLM, usually called inference, is executing code with inputs. You need two files: `model.py` for the architecture and `parameters.bin` for the weights. See [What is an LLM](/ai/llm/what-is-an-llm).

Give the model `"he is a good"` and it does not think in words. It runs a deterministic pipeline: characters to integers, integers to vectors, vectors through matrix multiplications, one integer back out, and a repeat.

---

## The plain-language version

**Where this sits:** the request path. What actually happens between pressing Enter and seeing the last word of the answer.

When you send a prompt, the model does not read words. The text is cut into tokens and turned into integers, the integers become vectors, the vectors pass through every layer, and the last layer outputs a score for every possible next token. One token is chosen, turned back into text, appended to the input, and the whole thing runs again, once per output token, until a stop token appears.

Two phases have very different costs. **Prefill** processes the whole prompt in one parallel pass, like reading a question in one glance. **Decode** writes the answer one token at a time, like writing it out by hand, and each step must re-read stored information about every earlier token. The **KV cache** is that stored information: it saves recomputing the past, but it costs memory.

This page covers, in order:

1. **The end-to-end pipeline**: the five steps at a glance
2. **Tokenization**: text to integers
3. **Embedding lookup**: integers to vectors
4. **Forward pass**: vectors through the layers
5. **Logits and probabilities**: one score per vocabulary token
6. **Detokenization and sampling**: choosing a token and turning it back into text
7. **Prefill and decode**: the two phases and their costs
8. **The KV cache**: what is stored and why
9. **Streaming back to the client**: sending tokens as they are produced
10. **The full request lifecycle**: queues, batching, and caching around the model
11. **Running models locally**

| Word                    | Plain meaning                                                                                               |
| :---------------------- | :---------------------------------------------------------------------------------------------------------- |
| **inference**           | Running a trained model to produce output.                                                                  |
| **forward pass**        | One run of the input through every layer of the model.                                                      |

The loop back from step 5 to step 3 is what makes generation autoregressive. Everything else runs once per token.

## Step 1: Tokenization

Text is split into tokens and mapped to integer IDs through a fixed vocabulary. The table below uses GPT-2's 50,257-entry byte-level BPE.

| Slice     | ID    | Note                               |
| :-------- | :---- | :--------------------------------- |
| `"he"`    | `633` | Lowercase word                     |
| `" is"`   | `318` | Leading space is part of the token |
| `" a"`    | `257` | Common word with space             |
| `" good"` | `922` | Adjective with space               |

```python
input_ids = [633, 318, 257, 922]
```

Token count is what you are billed for and what the context window is measured in. [Tokenization](/ai/llm/tokenization) covers how the vocabulary is built and why rare words fragment.

---

## Step 2: Embedding lookup

An ID like `633` is an index with no mathematical meaning. Token `634` is not "one more" than `633`. The embedding matrix, stored in the checkpoint, converts each ID into a vector of `d_model` floats.

```python
# lookup into the embedding table, shape (vocab_size, 4096)
emb = embed_tokens(torch.tensor([633, 318, 257, 922]))   # (4, 4096)
```

RoPE then encodes position. Unlike learned or sinusoidal encodings it does not add a vector; it rotates the query and key vectors inside each attention layer by an angle proportional to position, so the relative offset between two tokens is recoverable from their dot product.

---

## Step 3: Forward pass

The vectors pass through every transformer block. Each block does two things.

Self-attention lets tokens communicate. The vector at `"good"` looks back at `"he"` and `" is"` to establish what is being described. Feed-forward layers then apply large weight matrices that store the model's associations.

By the final block, the vector at the last position encodes what should come next.

---

## Step 4: Logits and probabilities

The last hidden vector is multiplied by the unembedding matrix, producing one score per vocabulary entry. Those raw scores are logits. Softmax normalizes them.

| Candidate   | Logit  | Probability |
| :---------- | :----- | :---------- |
| `" person"` | `14.2` | 38.4%       |
| `" boy"`    | `13.8` | 26.1%       |
| `" man"`    | `13.3` | 16.2%       |
| `" friend"` | `12.5` | 7.3%        |
| `" guy"`    | `12.1` | 5.0%        |
| `" apple"`  | `-2.4` | 0.0001%     |

At a 128,256-entry vocabulary the logits tensor for a batch of 8 sequences of length 2048 is `8 * 2048 * 128256 * 4 bytes`, about 8.4 GB in FP32. Production code computes logits only for the final position during decode, which cuts that to a single row.

---

## Step 5: Detokenization and sampling

The sampler picks a token. Greedy takes the argmax; temperature and top-p sampling draw from the distribution. The chosen ID is looked up in the vocabulary and appended.

```text
Round 1: "he is a good"            -> " person"
Round 2: "he is a good person"     -> " who"
Round 3: "he is a good person who" -> " loves"
```

The loop ends on a stop token, a stop sequence, or `max_tokens`. [Decoding Strategies](/ai/llm/decoding) covers every sampler and the difference between a stop token and a stop sequence.

## Prefill and decode

The two phases of a request have different performance profiles, and the difference explains most of what serving engines do.

| Property         | Prefill                       | Decode                |
| :--------------- | :---------------------------- | :-------------------- |
| Tokens processed | The whole prompt at once      | One per forward pass  |
| Parallelism      | Across the sequence dimension | Across the batch only |
| Bottleneck       | Compute (FLOPs)               | Memory bandwidth      |
| Matrix shape     | Tall and wide                 | A single row          |
| GPU utilization  | High                          | Low without batching  |

Prefill runs the prompt through the model in one pass and writes a KV cache entry for every position. Decode then reads that cache and the full weight matrices to emit one token.

Decode is memory-bound because the arithmetic intensity is terrible: reading 16 GB of weights to produce one token. A GPU with 1 TB/s of bandwidth has a hard floor around 16 ms per token, roughly 60 tokens per second, no matter how fast its tensor cores are.

This asymmetry is why API providers charge more per output token than per input token, and why prompt caching — reusing the prefill result for a repeated system prompt — is worth so much.

---

## The KV cache

Recomputing keys and values for the whole prefix at every step would make generation quadratic. Instead each layer caches them.

```text
kv_bytes = 2 * n_layers * n_kv_heads * d_head * seq_len * batch * bytes_per_param
```

The leading `2` is K and V. For an 8B model with 32 layers, 8 KV heads, `d_head = 128`, at BF16, that is 131,072 bytes per token. At a 32K context and 32 concurrent requests the cache is 128 GB against 16 GB of weights.

The cache is why grouped-query and latent attention exist, and why long context is a serving problem rather than a training problem. [Context Windows](/ai/llm/context-windows) works through the arithmetic.

## Streaming back to the client

Tokens are returned as they are produced rather than buffered to the end. The transport is Server-Sent Events over HTTP, one JSON chunk per token:

```text
data: {"choices":[{"delta":{"content":" person"},"index":0}]}

data: {"choices":[{"delta":{"content":" who"},"index":0}]}

data: [DONE]
```

Streaming changes the metrics that matter. **Time to first token** is prefill latency plus queueing. **Inter-token latency** is one decode step. **Total latency** is time to first token plus output length times inter-token latency. Optimizing one rarely optimizes the others, and a long prompt hurts only the first.

The stop-string check runs against the decoded buffer on the serving side, before each chunk is flushed, which is why a stop sequence can truncate mid-token while a stop token cannot.

## The full request lifecycle

<Mermaid
  chart={`
flowchart TD
    A["User presses Enter"] --> B["Client sends HTTP POST<br/>messages + sampling params"]
    B --> C["Gateway: auth, rate limit,<br/>model routing, prompt caching"]
    C --> D["Apply chat template"]
    D --> E["Tokenize -> input_ids"]
    E --> F["Scheduler admits the request<br/>into a running batch"]
    F --> G["Prefill: one parallel forward pass,<br/>write KV cache"]
    G --> H["Emit first token -> stream starts"]
    H --> I["Decode step: read weights + KV cache"]
    I --> J["Sample, check stop conditions"]
    J -->|continue| K["Append token, stream chunk"]
    K --> I
    J -->|stop token, stop sequence,<br/>or max_tokens| L["Flush final chunk, free cache blocks"]
    L --> M["Log token counts for billing"]
`}
/>

Three things happen in this pipeline that are easy to miss.

**Continuous batching.** A single request underuses a GPU. Rather than waiting for a whole batch to finish, the scheduler admits new requests into free slots at every decode step. The unit of scheduling is a step, not a request, which is what makes throughput scale without wrecking latency.

**Paged KV allocation.** Without paging, each request reserves a contiguous block sized for its maximum length, and most of it goes unused. vLLM's PagedAttention (Kwon et al., arXiv:2309.06180) allocates the cache in small non-contiguous blocks, like virtual memory, which removes most of that waste.

**Prefix caching.** When many requests share a system prompt, its prefill result is identical every time. Caching the KV blocks for that prefix skips the compute entirely, which is the single largest latency win available for chat deployments.

## Running models locally

Inference needs only the architecture and the weights, so no API is required.

`llama.cpp` compiles the forward pass to optimized C++ and reads weights in the `.gguf` format. Ollama wraps it with a server and a model registry. Both load the weights into RAM or VRAM and run exactly the pipeline above.

```bash
ollama pull llama3.1:8b
ollama run llama3.1:8b "he is a good"
```

The constraints are the ones from the tables above: the weight footprint at your chosen quantization, plus the KV cache at your chosen context length. A 4 GB INT4 model with a 32K context still needs several GB for the cache.

## Interview questions

<Accordions>
  <Accordion title="Name the five stages a prompt passes through before the first output token appears.">

    Tokenization, embedding lookup, forward pass through every block, logits and softmax, then sample and detokenize. The sampled token is appended and the loop returns to the forward pass.

  </Accordion>
  <Accordion title="Why is an embedding lookup necessary, and what would break if token IDs were fed to the model directly?">

    An ID like `633` is an index, not a magnitude: `634` is not "one more than" `633` in any sense the network could use. The embedding table maps each ID to a `d_model` vector that layers can do arithmetic on. Feeding raw IDs would inject ordering and distance that the vocabulary does not carry.

  </Accordion>
  <Accordion title="How does RoPE encode position differently from a sinusoidal or learned encoding?">

    RoPE rotates the query and key vectors inside each attention layer by an angle proportional to position, so the relative offset between two tokens falls out of their dot product. Sinusoidal and learned encodings add a position vector to the token representation instead; RoPE adds nothing and leaves no positional term in the cache.

  </Accordion>
  <Accordion title="What is the shape of the logits tensor for a batch of 8 sequences of length 2048 at a 128,256-entry vocabulary in FP32, and how does decode avoid materializing it?">

    `8 * 2048 * 128256 * 4` bytes, about 8.4 GB in FP32. Decode computes only the last position of each sequence, so the logits become one row per sequence: `8 * 1 * 128256`, and the unembedding multiply is that same shape.

  </Accordion>
  <Accordion title="Contrast prefill and decode on parallelism, bottleneck, and GPU utilization.">

    Prefill processes the whole prompt at once, parallel across the sequence dimension, compute-bound, and keeps the GPU busy. Decode processes one token per forward pass, parallelizes only across the batch, is memory-bandwidth-bound, and idles the compute units unless the batch is deep.

  </Accordion>
  <Accordion title="Why is decode memory-bandwidth bound, and what does that imply about the maximum tokens per second on a given GPU?">

    One decode step is a single row of activations multiplied against every weight matrix and every cached KV entry, so bytes moved per operation is enormous and the flop count is trivial. Tokens per second is capped near bandwidth divided by bytes read per step, which is why batching, quantization and a smaller KV cache raise throughput more than a faster clock does.

  </Accordion>
  <Accordion title={<>Write the KV-cache size formula and compute bytes per token for a 32-layer model with 8 KV heads and <code>d_head = 128</code> at BF16.</>}>

    `bytes per token = 2 * n_layers * n_kv_heads * d_head * bytes_per_element`, the 2 for keys and values. Here `2 * 32 * 8 * 128 * 2 = 131072` bytes, 128 KiB per token, so a 4096-token sequence holds 512 MiB.

  </Accordion>
  <Accordion title="Which latency metric does a long prompt hurt, and which does a long output hurt?">

    A long prompt hurts time to first token, because prefill scales with prompt length even though it runs in parallel. A long output hurts inter-token latency and total wall clock, because decode steps are strictly sequential.

  </Accordion>
  <Accordion title="What does continuous batching change about the scheduler's unit of work?">

    It changes the unit of work from a batch lifetime to a single decode step. Sequences join and leave the running batch between steps, so no slot sits idle waiting for the slowest request to finish.

  </Accordion>
  <Accordion title="Why does paged KV allocation matter, and what does it borrow from operating systems?">

    Reserving one contiguous block per request at maximum length wastes most of HBM and evicts live requests when a long one arrives. Paged KV splits the cache into fixed-size blocks and maps a sequence's logical positions onto non-contiguous physical blocks through a block table, which is virtual memory paging from an operating system applied to attention state.

  </Accordion>
  <Accordion title="What does prefix caching skip, and in which deployment pattern does it pay off most?">

    It skips recomputing the KV entries for tokens whose prefix is byte-identical to a prefix already prefilled, so those tokens never re-enter the model. It pays off where a long static prefix is resent every call: agent loops, multi-turn chat, RAG systems with a large instruction block, few-shot prompting.

  </Accordion>
  <Accordion title="Why can a stop sequence truncate mid-token while a stop token cannot?">

    A stop token is a vocabulary entry, so it always arrives at a token boundary and truncation is exact. A stop sequence is a string matched against decoded text, and the token that completes it can carry extra characters beyond the match, so output is cut mid-token unless the engine checks before emitting.

  </Accordion>
</Accordions>
