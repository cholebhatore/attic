A dense transformer spends the same FLOPs on every token. A mixture of experts replaces the feed-forward block with `E` parallel copies and a router that activates `k` of them per token. Total parameters grow by roughly `E`, active parameters grow by roughly `k`, and the two numbers diverge.

That divergence is the entire point. Compute cost per token tracks active parameters. Memory cost tracks total parameters.

| Model            | Total params | Active per token | Routed experts | Shared | `k` | Layers |
| :--------------- | :----------- | :--------------- | :------------- | :----- | :-- | :----- |
| Mixtral 8x7B     | 46.7B        | 12.9B            | 8              | 0      | 2   | 32     |
| Qwen3-30B-A3B    | 30.5B        | 3.3B             | 128            | 0      | 8   | 48     |
| DeepSeek-V3      | 671B         | 37B              | 256            | 1      | 8   | 61     |
| Llama 4 Scout    | ~109B        | 17B              | 16             | 0      | 1   | 48     |
| Llama 4 Maverick | ~400B        | 17B              | 128            | 0      | 1   | 48     |

Sources: Mixtral (Jiang et al., arXiv:2401.04088), DeepSeek-V3 (arXiv:2412.19437), Qwen3-30B-A3B's published `config.json`, Meta's Llama 4 release notes.

## The plain-language version

**Where this sits:** the second efficiency change. It targets compute: how to make a model know more without making each token more expensive to process.

In a normal (dense) model every parameter is used for every token. A **mixture of experts (MoE)** replaces each feed-forward network with many smaller ones, the **experts**, plus a **router** that picks a few experts for each token. The model can have a huge total parameter count (more knowledge) while each token only uses a small part of it (less compute). The catch: all the experts must still sit in memory, and the router must spread tokens evenly, or a few experts do all the work while the rest learn nothing.

Think of a hospital. A dense model is one doctor who must handle every case alone. An MoE is a hospital of specialists with a triage nurse (the router) who sends each patient to two or three relevant specialists. The hospital knows far more, each patient takes about the same time, but the building has to hold everyone, and triage must not send every patient to the same doctor.

This page covers, in order:

1. **Routing**: top-k gating, and sigmoid versus softmax scoring
2. **Load balancing**: the auxiliary loss, DeepSeek's aux-loss-free bias, and capacity factor
3. **DeepSeek's group-limited routing**: shared experts, dense first layers, and fine-grained experts
4. **What MoE costs you**: memory, communication, and training instability

| Word                          | Plain meaning                                                                                      |
| :---------------------------- | :------------------------------------------------------------------------------------------------- |
| **dense model**               | Every parameter is used for every token.                                                           |
| **expert**                    | One of many parallel feed-forward networks in an MoE layer.                                        |
| **router / gate**             | A small layer that scores the experts for each token and picks the top `k`.                        |
| **total / active parameters** | All parameters in the model, versus those actually used for one token.                             |
| **load balancing**            | Keeping tokens spread across experts so none is overloaded or idle.                                |
| **auxiliary loss**            | An extra training penalty that pushes the router toward balanced use.                              |
| **capacity factor**           | The maximum number of tokens an expert accepts per batch; overflow tokens are dropped or rerouted. |
| **shared expert**             | An expert every token always uses, alongside the routed ones.                                      |
| **expert parallelism**        | Placing different experts on different GPUs.                                                       |

## Routing

Two directions, and the difference matters for load balance.

**Token-choice**: each token scores all experts and picks its top `k`. Every token is guaranteed a path. Every expert competes for tokens, and can starve.

**Expert-choice** (Zhou et al., arXiv:2202.09368): each expert picks its top `n` tokens. Load is perfectly balanced by construction, but a token can receive zero experts, which is awkward for autoregressive decoding.

Nearly every deployed model uses token-choice.

```python
scores = router(x)                                     # (T, E)
topk_vals, topk_idx = torch.topk(scores, k, dim=-1)    # (T, k)
weights = topk_vals / topk_vals.sum(-1, keepdim=True)  # renormalize
out = sum(weights[:, i:i+1] * experts[topk_idx[:, i]](x) for i in range(k))
```

That last line is notation, not runnable code, because the experts are indexed per token. A working version gathers tokens by expert, runs one batched matmul per expert, and scatters the results back:

```python
import torch
import torch.nn as nn


class MoEFFN(nn.Module):
    def __init__(self, d_model, n_experts, top_k, moe_ffn_dim, shared_ffn_dim=None):
        super().__init__()
        self.top_k = top_k
        self.gate = nn.Linear(d_model, n_experts, bias=False)
        self.experts = nn.ModuleList(
            [SwiGLU(d_model, moe_ffn_dim) for _ in range(n_experts)]
        )
        self.shared = SwiGLU(d_model, shared_ffn_dim) if shared_ffn_dim else None

    def forward(self, x):
        B, T, D = x.shape
        flat = x.reshape(B * T, D)                            # (BT, D)
        scores = torch.sigmoid(self.gate(flat))               # (BT, E)
        vals, idx = torch.topk(scores, self.top_k, dim=-1)    # (BT, k)
        vals = vals / vals.sum(-1, keepdim=True)              # (BT, k)

        out = torch.zeros_like(flat)
        for slot in range(self.top_k):
            e_idx, w = idx[:, slot], vals[:, slot].unsqueeze(-1)
            for e in range(len(self.experts)):
                mask = e_idx == e                             # (BT,)
                if mask.any():
                    out[mask] += w[mask] * self.experts[e](flat[mask])

        if self.shared is not None:
            out = out + self.shared(flat)
        return out.reshape(B, T, D)
```

The double loop is the readable form. Production kernels replace it with a sort by expert ID plus a segmented gather, so each expert runs one large batched matmul instead of many small ones.

### Sigmoid versus softmax scoring

Softmax over experts forces the scores to sum to one across the whole vocabulary of experts, which couples every expert's score to every other. Sigmoid scores each expert independently and renormalizes only across the selected `k`. DeepSeek-V3 sets `"scoring_func": "sigmoid"` with `"norm_topk_prob": true`, and reports that this decoupling stabilizes training.

## Load balancing

Without an explicit constraint, routing collapses. A randomly initialized router sends slightly more tokens to some experts; those experts get more gradient updates; they get better at attracting tokens; the gap compounds. Half the parameters end up dead.

### Auxiliary loss

Switch Transformer (Fedus et al., arXiv:2101.03961) adds a differentiable penalty that is minimized at uniform routing:

```
L_aux = alpha * E * sum_e ( f_e * P_e )
```

`f_e` is the fraction of tokens dispatched to expert `e`, `P_e` is the mean router probability assigned to `e`, and `E` is the expert count. The product is minimized when both are `1/E`. Qwen3-MoE publishes `router_aux_loss_coef = 0.001`, which is Switch Transformer's recommended value.

The downside: the aux loss is a proxy. Optimizing it can pull tokens toward experts that are wrong for them, trading quality for balance.

### Aux-loss-free balancing

DeepSeek-V3 (arXiv:2412.19437) removes the loss entirely and adjusts the router directly. Each expert gets a learnable bias `b_e` added to its router logit before the top-k selection:

```
b_e <- b_e + gamma   if expert e is under-loaded
b_e <- b_e - gamma   if expert e is over-loaded
```

The update is gradient-free, so it never interferes with the main objective. A separate mechanism periodically revives experts whose load has fallen to zero for many consecutive steps, by resetting their bias upward. The paper reports that this reaches the same balance as an aux loss without the quality penalty.

### Capacity factor

Training frameworks also impose a hard cap:

```
capacity = capacity_factor * (tokens_in_batch / num_experts)
```

Tokens routed to an expert beyond its capacity are dropped during training. A factor of 1.0 means exactly proportional allocation; 1.25 gives some slack. Dropping tokens is fine in training and unacceptable in inference, so inference engines drop the capacity limit and let load be ragged, which is what makes MoE serving throughput bursty.

## DeepSeek's group-limited routing

DeepSeek-V3's config sets `n_routed_experts = 256`, `n_group = 8`, `topk_group = 4`, `num_experts_per_tok = 8`, `topk_method = "noaux_tc"`.

Selecting 8 experts independently from 256 tends to scatter them across many groups, which fragments the tokens each expert sees and makes the per-expert batches too small to run efficiently. So the selection happens in two stages:

1. Split the 256 experts into 8 groups of 32.
2. Score each group by the sum of its top-2 expert scores. Keep the top 4 groups.
3. Within those 128 candidates, take the global top 8 experts.

The `noaux_tc` name encodes both design choices: no auxiliary loss, token-choice routing.

### Shared experts

`n_shared_experts = 1` means one expert runs for every token, unconditionally. DeepSeekMoE (Dai et al., arXiv:2401.06066) introduced this: common linguistic knowledge lives in the shared expert, and the routed experts specialize. Without it, every expert must redundantly learn the basics.

`routed_scaling_factor = 2.5` multiplies the summed routed output so its magnitude matches the shared expert's contribution after the top-k renormalization shrinks it.

### Dense layers first

`first_k_dense_replace = 3` makes the first 3 of 61 layers ordinary dense feed-forward blocks (`intermediate_size = 18432`) rather than MoE (`moe_intermediate_size = 2048`). Early-layer representations are still forming, and sparse routing on them is unstable. The remaining 58 layers use 256 routed experts plus 1 shared.

### Fine-grained experts

DeepSeek-V3 uses many small experts (`moe_intermediate_size = 2048`) rather than few large ones. Dai et al. show that at matched FLOPs, finer granularity plus a shared expert beats the coarse Mixtral-style design, because more experts means more distinct specialization patterns available to the router.

## What MoE costs you

**Memory.** All 671B of DeepSeek-V3's parameters must be resident, or sharded across devices with expert parallelism. At bf16 that is 1,342 GB. The 37B active subset is what determines FLOPs per token, not what determines VRAM.

**All-to-all communication.** With experts spread across GPUs, every token that routes to a remote expert needs a dispatch and a combine. This is the dominant communication cost in MoE training and is why expert parallelism degree is usually capped well below the expert count.

**Batch-size sensitivity.** Sparse routing needs enough tokens per batch that every expert gets a reasonable share. Small batches produce ragged expert loads and poor GPU utilization, which makes MoE a worse fit for low-latency single-request serving than for high-throughput batch serving.

**Quantization interactions.** Routed experts are individually small, so per-tensor quantization calibrates poorly on them. DeepSeek-V3 ships with FP8 block quantization at `weight_block_size = [128, 128]`, which keeps the calibration granularity local.

<Callout type="info">
  ### Llama 4's `num_experts_per_tok = 1`

Top-1 routing is the most aggressive choice in the table. Each token activates exactly one of 16 (Scout) or 128 (Maverick) experts, which is how both models hold active parameters at 17B while total parameters differ by nearly 4x. Top-1 makes the router's decision load-bearing: a wrong pick is not averaged away by a second expert.

</Callout>

## Interview questions

<Accordions>
  <Accordion title="Which number, total or active parameters, determines FLOPs per token, and which determines VRAM?">

    Active parameters determine FLOPs per token, because only the `k` experts the router selects run on that token. Total parameters determine VRAM, because every expert's weights must be resident or sharded even when they sit idle — DeepSeek-V3 is 37B of compute per token against 671B of memory.

  </Accordion>
  <Accordion title="What is the difference between token-choice and expert-choice routing, and why does expert-choice struggle with autoregressive decoding?">

    Token-choice has each token score all experts and take its top `k`, guaranteeing every token a path while leaving experts to compete for tokens and starve. Expert-choice has each expert pick its top `n` tokens, which balances load by construction but can leave a token with zero experts. Autoregressive decoding needs a value for every position at every step, so an unassigned token has nothing to add.

  </Accordion>
  <Accordion title="Write the top-k gating computation including renormalization.">

    `scores = softmax(W_g x)` over `E` experts, `topk_vals, topk_idx = topk(scores, k)`, then `weights = topk_vals / topk_vals.sum(-1, keepdim=True)` to renormalize so the `k` contributions sum to one, and the output is the weighted sum of the `k` expert feed-forwards.

  </Accordion>
  <Accordion title="Why does routing collapse without a load-balancing term, and what is the positive feedback loop that causes it?">

    The router is trained by gradient through its own selections, so experts that win early receive more gradient and win more often. With no counter-pressure the loop drives most tokens onto a handful of experts, the rest get no gradient and freeze at random initialization, and effective capacity collapses to a few experts plus a large memory bill.

  </Accordion>
  <Accordion title={<>State the Switch Transformer auxiliary loss and explain why the product <code>f_e * P_e</code> is minimized at uniform routing.</>}>

    `L_aux = E * sum_e f_e * P_e`, where `f_e` is the fraction of tokens dispatched to expert `e` and `P_e` is the router's mean probability for it. Both factors are non-negative and sum to one over the experts, so their inner product is smallest when the two vectors are aligned and flat — a uniform load of `1/E` each — and grows as either term concentrates on a few experts.

  </Accordion>
  <Accordion title="What does DeepSeek-V3's aux-loss-free balancing do instead, and why is being gradient-free an advantage?">

    It adds a bias `b_e` to each expert's router logit before top-k selection and updates it gradient-free: `b_e += gamma` when the expert is under-loaded, `b_e -= gamma` when over-loaded, plus periodic reset of the bias for experts starved for many steps. Because the correction never enters the loss, it cannot trade off against the main objective or distort the representation — DeepSeek-V3 (arXiv:2412.19437) reports the same balance without the aux loss's quality penalty.

  </Accordion>
  <Accordion title="What is a capacity factor, and why is it acceptable in training but not in inference?">

    `capacity = capacity_factor * (tokens_in_batch / num_experts)`: the hard per-expert token budget in training, where 1.0 is exactly proportional and 1.25 leaves slack. Tokens above it are dropped and never reach that expert. In training a dropped token costs one gradient contribution; at inference it would silently omit part of the user's output, so serving engines remove the cap and run ragged expert loads instead.

  </Accordion>
  <Accordion title="Walk through DeepSeek-V3's group-limited top-k: 256 experts, 8 groups, top 4 groups, top 8 experts.">

    Split 256 routed experts into 8 groups of 32. Score each group by the sum of its top-2 expert scores and keep the top 4 groups, i.e. 128 candidates. Take the global top 8 experts inside those candidates, renormalize their weights, and add the single shared expert that runs for every token. Picking 8 from 256 independently scatters them across groups, which fragments each expert's token batch; confining them to 4 groups keeps the per-expert batches large enough to compute efficiently.

  </Accordion>
  <Accordion title="What problem does a shared expert solve that routed experts cannot?">

    Routed experts only see the tokens sent to them, so each must redundantly learn the language basics before it can specialize, and rarely-selected experts learn them badly. A shared expert runs unconditionally on every token and carries that common linguistic knowledge, which lets the routed experts spend their capacity on specialization — the finding behind DeepSeekMoE (Dai et al., arXiv:2401.06066).

  </Accordion>
  <Accordion title="Why does DeepSeek-V3 make its first three layers dense?">

    Routing decisions in the first layers are unreliable because the representations that feed the router are still forming, so sparse routing early is unstable and its gradient noise propagates through everything downstream. DeepSeek-V3 keeps 3 of 61 layers as ordinary dense feed-forwards at `intermediate_size = 18432` and only then switches to 256 routed experts of `moe_intermediate_size = 2048` plus one shared.

  </Accordion>
  <Accordion title="Name three costs MoE adds that a dense model of the same active size does not have.">

    All parameters must be resident: 671B at bf16 is about 1,342 GB, or sharded across devices with expert parallelism. All-to-all dispatch and combine traffic between GPUs, which dominates and caps the practical parallelism degree. Batch-size sensitivity — sparse routing needs enough tokens per step that every expert gets work, so small batches leave GPUs ragged.

  </Accordion>
  <Accordion title="Why does top-1 routing make the router's decision more consequential than top-2?">

    With top-1 the whole token output is that one expert's, weighted by a single gate value. There is no second expert to average out a mistake, so a wrong routing decision drops the token's contribution entirely, and load balancing rests on one pick per token instead of two. That is why Llama 4's `k = 1` designs need a shared expert and careful balancing, while top-2 models get a hedge for free.

  </Accordion>
</Accordions>
