An LLM is often described as an artificial brain. On disk it is two files.

1. `model.py` — a few hundred lines of Python or C++ defining the architecture: the attention loops, the matrix multiplications, the normalization layers.
2. `parameters.bin` — a binary file of billions of floating-point numbers produced by training on trabytes of text. Modern checkpoints use `.safetensors` instead, which adds a header describing each tensor's name, shape, and dtype.

`model.py` on its own is an empty shell. It defines how numbers should be multiplied and knows nothing about language. Everything the model knows lives in the weights.

## Weights and biases

Every connection between neurons carries a number called a **weight**. The calculation at each connection is

```text
output = (input * weight) + bias
```

- `input` — the incoming value
- `weight` — how strongly that input influences the output
- `bias` — a constant offset that shifts the result regardless of the input

<Mermaid
  chart={`
flowchart LR
    A["Input Tokens"] --> B["Layer 1"]
    W1["weights"] -.-> B
    B --> C["Layer 2"]
    W2["weights"] -.-> C
    C --> D["Layer N"]
    WN["weights"] -.-> D
    D --> E["Output Probabilities"]
`}
/>

At initialization every weight is random and the model emits gibberish. Training reads text, predicts the next token, measures the error, and nudges each weight in the direction that reduces it. That nudge is backpropagation. After trillions of tokens the weights settle into values that predict well.

## The house price analogy

Predicting a house price from bedrooms, square feet, and balconies uses the same arithmetic as an LLM, at a scale you can hold in your head.

### The training data

| Bedrooms | Square feet | Balconies | Sale price |
| :------- | :---------- | :-------- | :--------- |
| 2        | 1,100       | 1         | $215,000   |
| 3        | 1,500       | 2         | $305,000   |
| 4        | 2,200       | 3         | $440,000   |
| 2        | 950         | 1         | $198,000   |

### Finding the weights

Before training the model has no idea what a bedroom is worth. The optimizer searches until the weights reproduce the prices in the table:

| Parameter          | Value  |
| :----------------- | :----- |
| `w1` (bedrooms)    | 27,000 |
| `w2` (square feet) | 94     |
| `w3` (balconies)   | 21,000 |
| `b` (bias)         | 45,000 |

Those four numbers are the model's `parameters.bin`.

```text
price = (w1 * bedrooms) + (w2 * square_feet) + (w3 * balconies) + b
```

### Making a prediction

A new listing: 3 bedrooms, 1,625 square feet, 2 balconies.

```text
price = (27,000 * 3) + (94 * 1,625) + (21,000 * 2) + 45,000
price = 81,000 + 152,750 + 42,000 + 45,000
price = $320,750
```

The model never saw this house. It applied learned weights to new inputs.

An LLM does the same thing with three changes. The input is a few thousand numbers representing tokens rather than three features. The weights number in the billions rather than four. And the function is not linear — each layer applies a normalization, a matrix product, and a nonlinear activation before passing the result on.

## What lives inside parameters.bin

| Parameter type        | What it stores                                                       |
| :-------------------- | :------------------------------------------------------------------- |
| Token embeddings      | A lookup table mapping every token ID to a vector                    |
| Attention weights     | `W_q`, `W_k`, `W_v`, `W_o` — which prior tokens to attend to         |
| Feed-forward weights  | `W_gate`, `W_up`, `W_down` — stored associations and patterns        |
| Normalization weights | Per-channel scale factors for RMSNorm or LayerNorm                   |
| Biases                | Constant offsets. Most modern models set `attention_bias = false`    |
| Language model head   | Projects the final hidden state back to a score per vocabulary token |

Inspect the real list without downloading the weights: [Reading Model Code](/ai/llm/reading-model-code).

## Model size and precision

```text
size_bytes = num_parameters * bytes_per_parameter
```

`bytes_per_parameter` is set by the numerical precision.

| Format       | Bits | Bytes | Where it is used                                      |
| :----------- | :--- | :---- | :---------------------------------------------------- |
| FP32         | 32   | 4     | Scientific computing; too large for frontier training |
| BF16 / FP16  | 16   | 2     | The standard for training and serving                 |
| FP8 (`e4m3`) | 8    | 1     | DeepSeek-V3's shipped quantization                    |
| INT8         | 8    | 1     | Weight-only quantization                              |
| INT4 / NF4   | 4    | 0.5   | Consumer GPUs; QLoRA fine-tuning                      |

BF16 and FP16 both use 16 bits but split them differently. BF16 keeps FP32's 8-bit exponent, so it has the same range with less precision. FP16 keeps 10 mantissa bits, so it is more precise but overflows above 65,504. Training uses BF16 because gradient magnitudes span a wide range; inference often uses FP16 or lower because the weights are fixed.

### Footprint by precision

| Model        | Parameters | FP32     | BF16     | INT8   | INT4     |
| :----------- | :--------- | :------- | :------- | :----- | :------- |
| Qwen3-8B     | 8.19B      | 32.8 GB  | 16.4 GB  | 8.2 GB | 4.1 GB   |
| Llama 3 70B  | 70B        | 280 GB   | 140 GB   | 70 GB  | 35 GB    |
| DeepSeek-V3  | 671B       | 2,684 GB | 1,342 GB | 671 GB | 336 GB   |
| Llama 3 405B | 405B       | 1,620 GB | 810 GB   | 405 GB | 202.5 GB |

DeepSeek-V3's row is total parameters. Its active count per token is 37B, so the compute per token resembles an 8B model while the memory resembles a 671B one. That gap is the whole point of a mixture of experts.

<Callout type="warn">
  ### Weights on disk are not the serving budget

These numbers are the checkpoint size. Serving needs the weights plus the KV cache, plus activation memory, plus CUDA context buffers. The cache grows with context length and with concurrent requests, and at long context it is usually the largest term. Llama 3 70B at BF16 needs 140 GB to load and typically 160 GB or more to serve a long prompt. See [Context Windows](/ai/llm/context-windows) for the formula.

</Callout>

## Interview questions

<Accordions>
  <Accordion title="1. Name the two files that make up a deployed LLM and say what each one contains.">

    The weights and the code. Weights are the trained tensors plus a config saying how to assemble them; the code is the modeling file that reads that config and builds the graph, or a recipe for an engine like vLLM. A checkpoint without its architecture definition is not a model, which is why the config and the modeling file ship together.

  </Accordion>
  <Accordion title={<>2. What is the difference between <code>parameters.bin</code> and a <code>.safetensors</code> checkpoint?</>}>

    `parameters.bin` is a pickle: it stores Python objects, so loading it executes arbitrary code from whoever produced the file. `.safetensors` is a header of names, dtypes and shapes followed by raw bytes, so it loads by memory mapping, cannot execute anything, and allows lazy per-tensor access. The format exists because model files became an attack surface.

  </Accordion>
  <Accordion title="3. Write the per-connection formula and explain what the bias term contributes that the weight does not.">

    `y = w . x + b`. The weight scales how much an input contributes; the bias shifts the output regardless of input, so the layer need not pass through the origin. Without it every hyperplane is pinned through zero, and no stack of such layers can represent a constant.

  </Accordion>
  <Accordion title={<>4. A house model has <code>w1 = 27000</code> for bedrooms, <code>w2 = 94</code> for square feet, <code>w3 = 21000</code> for balconies, and <code>b = 45000</code>. Price a 3-bedroom, 1,625 square foot house with 2 balconies.</>}>

    `27000 * 3 = 81,000`, `94 * 1,625 = 152,750`, `21000 * 2 = 42,000`, plus the bias 45,000, giving 320,750. The arithmetic is the transformer's: multiply, sum, use the result to decide the next value.

  </Accordion>
  <Accordion title="5. Name three ways an LLM differs from that linear model beyond parameter count.">

    The inputs are learned distributed representations rather than hand-declared columns. The output is a distribution over a vocabulary that is sampled and fed back in. The function is deep, so features are composed across layers instead of read off once. Attention makes each position's inputs depend on the other positions. And it is trained by next-token prediction on raw text, not by regression on labelled rows.

  </Accordion>
  <Accordion title="6. Which six kinds of tensor live in a transformer checkpoint?">

    Token and positional embeddings, the attention projections (`W_Q`, `W_K`, `W_V`, `W_O`), the feed-forward or expert matrices, normalization scales and shifts, and the output head. MoE adds a router matrix per layer, and tied embeddings remove the output head.

  </Accordion>
  <Accordion title="7. Compute the BF16 and INT4 footprint of a 671B-parameter model.">

    BF16 is 2 bytes, so 671B parameters is about 1.34 TB. INT4 is 0.5 bytes, so about 336 GB. Neither is the serving number; the second one is the point, because it is what puts a model that size within reach of a single node.

  </Accordion>
  <Accordion title="8. Why does training use BF16 rather than FP16?">

    BF16 keeps float32's 8-bit exponent, so its dynamic range reaches tiny gradients without rescaling and overflows only near 1e38. FP16 has a 5-bit exponent and a ceiling of 65,504, so an activation or gradient above it becomes inf. That is why FP16 training needs a loss scaler and BF16 does not.

  </Accordion>
  <Accordion title="9. Why can DeepSeek-V3 need 1.3 TB of memory while its per-token compute resembles an 8B model?">

    Every expert's weights must stay resident, because any token may route to any subset, so memory tracks the full 671B. Compute per token only touches the routed subset, which is why the FLOPs resemble a far smaller dense model. MoE buys capacity by trading it for memory and cross-GPU expert dispatch.

  </Accordion>
  <Accordion title="10. A 70B model at BF16 loads in 140 GB. What three additional terms push the serving requirement past 160 GB?">

    The KV cache, which multiplies by concurrent requests and context length. Activations and the prefill workspace, whose peak sits above steady state. Then framework and CUDA context overhead, allocator fragmentation, and the logits buffer, which is `(B, T, V)` against a vocabulary over 100,000.

  </Accordion>
</Accordions>
