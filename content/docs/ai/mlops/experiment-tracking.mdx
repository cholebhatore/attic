A training run produces a model. Without a tracker it produces nothing you can find again. The one question a tracker has to answer is "which run produced the model serving traffic right now, and what exactly did that run do". Every other feature is convenience on top of that.

For LLM work the same machinery covers a narrower object: a fine-tune, a distillation run, a prompt-and-eval combination. The record format barely changes, which is why the older MLOps tools survived the shift to foundation models.

---

## The plain-language version

**Where this sits:** the first MLOps habit. Before anything is deployed, every experiment that produced it must be reproducible.

Training and evaluation produce dozens of runs with different data, code, and settings. Without a record, nobody can say which run produced the model in production or why one version beat another. An **experiment tracker** (Weights & Biases, MLflow) records each run: its parameters, code version, data version, metrics over time, and output files. A **model registry** then catalogues the models worth keeping and promotes them through stages, from candidate to staging to production, only when they pass checks.

Think of a laboratory notebook. Every experiment is written down with its exact conditions and results, so any finding can be repeated and checked, and only results that pass review go into the published paper.

| Word               | Plain meaning                                                                    |
| :----------------- | :------------------------------------------------------------------------------- |
| **run**            | One execution of training or evaluation, with its settings and results.          |
| **artifact**       | A file produced or used by a run: a dataset, a checkpoint, an evaluation report. |
| **lineage**        | The chain linking a model to the data, code, and run that produced it.           |
| **sweep**          | An automated search over hyperparameter values.                                  |
| **model registry** | A catalogue of model versions with metadata and lifecycle stages.                |
| **promotion**      | Moving a model version to the next stage after it passes defined checks.         |

## What a run record has to answer

| Question                      | Field                                             | Where it comes from            |
| :---------------------------- | :------------------------------------------------ | :----------------------------- |
| Which model is live?          | Model URI plus registry alias                     | Registry, not the training job |
| Which code produced it?       | Git commit SHA, entrypoint path, image digest     | CI environment                 |
| What config?                  | Resolved params, defaults included                | Config loader, logged at start |
| What data?                    | Dataset version, split hash, row count            | DVC revision or a content hash |
| What happened during the run? | Metrics per step, gradients, system metrics, logs | In-loop `log` calls            |
| What did the run make?        | Artifacts: weights, tokenizer, eval report        | End-of-run upload              |
| What environment?             | Lockfile, CUDA driver, GPU SKU and count, seed    | Auto-collected                 |
| Who ran it, and from where?   | User, host, job type (train, eval, ci)            | Auth plus explicit `job_type`  |
| What did it cost?             | GPU-hours, wall time, money estimate              | Derived from system metrics    |

Seed and lockfile are the two most commonly dropped, and they are the two that make a run unreproducible. A missing seed costs you an afternoon of "it worked last week". A missing lockfile costs you a production incident when the base image upgrades `transformers` underneath you.

<Callout type="info">
  ### Log the resolved config, not the file

If a run reads `config.yaml` and merges three environment overrides into it, the file alone does not describe the run. Log the merged dictionary. Otherwise your tracker shows two runs with identical params that behave differently, and you spend the debugging time discovering that `WANDB_` or `MLFLOW_` environment variables were the difference.

</Callout>

## The two trackers you will be asked about

| Dimension    | Weights & Biases                                | MLflow                                             |
| :----------- | :---------------------------------------------- | :------------------------------------------------- |
| Hosting      | SaaS, or self-hosted Server                     | Self-hosted tracking server, first-class           |
| Metadata     | Their Postgres                                  | Your backend store: SQLite, Postgres, MySQL        |
| Artifacts    | Object store behind the W&B bucket              | Your artifact store: S3, GCS, Azure Blob, NFS      |
| Core objects | Run, Project, Sweep, Artifact, Report, Job      | Experiment, Run, LoggedModel, Registered Model     |
| Registry     | W&B Registry (a permissions layer on artifacts) | Model Registry built into the server               |
| Sweeps       | Managed, with TPE, random, grid, HyperBand      | Not built in; pair with Optuna or Ray Tune         |
| LLM features | Prompts, traces, evals in Weave                 | Tracing, evaluation, and prompt registry since 2.x |
| Strength     | Least setup, best UI for comparing runs         | Runs inside your VPC, no per-seat dependency       |
| Weak point   | Data leaves your network unless self-hosted     | You own the Postgres, the blob store, and upgrades |

Both log the same triple: params, metrics, artifacts. Switching costs are mostly about sweep integration and dashboard muscle memory.

## Weights & Biases

The API is a run object plus a `log` call. Everything else is decoration.

```python
import wandb

run = wandb.init(
    project="support-copilot",
    job_type="train",
    group="lora-r16-sweep",
    tags=["rlhf-prep", "prod-model"],
    config={
        "model": "mistral-7b",
        "lora_r": 16,
        "lr": 2e-4,
        "epochs": 3,
        "seed": 1337,
    },
)

for epoch in range(run.config.epochs):
    for step, batch in enumerate(train_loader):
        loss = training_step(batch)
        wandb.log({"epoch": epoch, "train/loss": loss})

art = wandb.Artifact("copilot-weights", type="model")
art.add_file("best.pt", name="weights.pt")
art.add_file("tokenizer.json")
run.log_artifact(art, aliases=["candidate"])
run.finish()
```

Consuming an artifact is the mirror image, and the line between producer and consumer is what builds lineage.

```python
run = wandb.init(project="support-copilot", job_type="evaluate")

model_art = run.use_artifact("copilot-weights:v14")
data_art = run.use_artifact("golden-set:v3")
dirpath = model_art.download()

report = wandb.Table(columns=["case", "prompt", "expected", "actual", "judge_score"])
for case in golden_cases:
    report.add_data(case.id, case.prompt, case.expected, generate(case.prompt), score(case))
wandb.log({"eval/errors": report})

run.log_artifact(wandb.Artifact("eval-report", type="report").add("table.json", report))
```

`use_artifact` records the dependency. `log_artifact` records the output. Ask the server for `used_by` on a dataset artifact and you get the list of every model built from it, which is the blast-radius query you need the day a label bug is found.

Concepts worth knowing by name:

| Concept             | What it is                                                 |
| :------------------ | :--------------------------------------------------------- |
| Run                 | One logged process, identified by an 8-character id        |
| Project             | Namespace for runs; API keys and access are per project    |
| Sweep               | Parent object over many runs sharing a search space        |
| Artifact collection | Named, versioned set of artifacts; versions are immutable  |
| Alias               | Mutable pointer to one version, e.g. `champion`, `staging` |
| Lineage             | The graph built by `use` and `log` edges across runs       |
| Job                 | An executable captured from a run's code plus environment  |
| Report              | A document mixing live panels, tables and prose            |

Offline mode matters on a cluster with no egress: set `WANDB_MODE=offline`, train, then `wandb sync` the local directory afterwards.

## MLflow

MLflow splits storage in two, and understanding the split explains every deployment guide.

| Layer          | Holds                                           | Backends                                 |
| :------------- | :---------------------------------------------- | :--------------------------------------- |
| Backend store  | Experiment and run metadata, params, metrics    | SQLite for a laptop, Postgres for a team |
| Artifact store | Run artifacts and model binaries                | Local path, S3, GCS, Azure Blob, NFS     |
| Model Registry | Registered model names, versions, aliases, tags | Same database as the backend store       |

The tracking server is the only process that touches either store, so clients point at it with a URI and never see credentials.

```python
import mlflow
import mlflow.pytorch

mlflow.set_tracking_uri("http://mlflow.internal:5000")
mlflow.set_experiment("support-copilot/training")

with mlflow.start_run(run_name="lora-r16-v3"):
    mlflow.log_params({"lr": 2e-4, "lora_r": 16, "seed": 1337})
    mlflow.log_param("dataset", "golden-train:v3")
    for step, batch in enumerate(train_loader):
        mlflow.log_metric("train/loss", training_step(batch), step=step)

    mlflow.pytorch.log_model(
        model,
        name="model",
        signature=mlflow.models.infer_signature(sample_in, sample_out),
        extra_pip_requirements=["torch==2.4.0", "transformers==4.44.0"],
    )
```

`name` for the artifact path is the 3.x spelling; pre-3.0 code writes `artifact_path` instead, and 3.x also folds `conda_env` and `extra_pip_requirements` into a single `env` argument. The signature is the part that pays for itself: it records input and output types, so serving-side schema drift becomes an error at load time rather than a wrong answer at request time.

`autolog` covers the common frameworks in one line, which is the fastest way to get a team logging anything at all.

```python
mlflow.pytorch.autolog()  # or mlflow.transformers.autolog(), mlflow.sklearn.autolog()
```

Evaluation has its own entrypoint, and `model_type` selects which metrics run.

```python
result = mlflow.evaluate(
    model="models:/copilot@candidate",
    data=eval_df,
    targets="expected",
    predictions="actual",
    model_type="question-answering",
    extra_metrics=[rouge_l, exact_match],
)
result.metrics  # {'rouge_l': ..., 'exact_match': ...}
```

## Sweeps and search budget

A sweep is a search over a config space, and it is the most expensive thing in this phase.

| Method         | How it picks next          | Works when                   | Wastes money when            |
| :------------- | :------------------------- | :--------------------------- | :--------------------------- |
| Grid           | Cartesian product          | Two or three params          | Dimensions multiply          |
| Random         | Uniform sample             | Any space                    | Budget under about 30 trials |
| Manual         | You pick                   | You have a hypothesis        | You do not                   |
| Bayesian (TPE) | Model of promising regions | Smooth metric, modest budget | Noisy or multimodal metric   |
| HyperBand/ASHA | Successive halving         | Budget per trial is unknown  | Runs are tiny                |
| PBT            | Mutate best, kill worst    | Long training, online metric | Short runs                   |

The reason random beats grid in high dimensions is precision. With 5 parameters at 10 values each, grid needs 100,000 runs to cover the space, and 100 runs only sample the extremes of every axis. Random's 100 runs spread across all five dimensions and find a good value for each to roughly one significant figure, which is all continuous hyperparameters like learning rate need.

```yaml
# wandb sweep config
program: train.py
method: bayes
metric:
  name: eval/hallucination_rate
  goal: minimize
early_terminate:
  type: hyperband
  min_iter: 9
command:
  - ${python}
  - ${program}
  - ${args}
parameters:
  lr: { distribution: log_uniform, min: 0.00001, max: 0.003 }
  lora_r: { values: [8, 16, 32, 64] }
  warmup_ratio: { distribution: uniform, min: 0.0, max: 0.2 }
```

Run the arithmetic before you start. A 40-trial sweep on a 7B LoRA taking 25 minutes per trial is about 17 GPU-hours; on 8×A100 with one trial per node, it is 2.1 wall-clock hours of a reservation someone else wanted.

## Model Registry

The registry exists because a filename is not a deployment contract. `model_final.pt` tells the deployer nothing about whether the file passed review.

A registered model has a name, immutable versions, and mutable aliases that point at one version each. Deployers resolve an alias. Trains write a new version. Promotion moves the alias, and that move is the auditable event.

```python
from mlflow.tracking import MlflowClient

client = MlflowClient(tracking_uri="http://mlflow.internal:5000")
client.create_registered_model("copilot")

mv = mlflow.register_model("runs:/8f2c1ad4/model", "copilot")
client.set_registered_model_version_tag("copilot", mv.version, "eval_gate", "passed")
client.set_registered_model_alias("copilot", "candidate", mv.version)

# promotion, only after the CI eval suite is green
client.set_registered_model_alias("copilot", "champion", mv.version)

model = mlflow.pytorch.load_model("models:/copilot@champion")
```

MLflow's `None`/`Staging`/`Production`/`Archived` stages are deprecated as of 2.9, and aliases replaced them. Stages were a fixed four-state ladder, which could not express "this tenant's model" or "the rollback target" without inventing tags on top. Aliases are arbitrary, and a model can hold several at once.

| Alias        | Who reads it           | Changes when                    |
| :----------- | :--------------------- | :------------------------------ |
| `candidate`  | CI evaluation job      | A new version clears the gate   |
| `champion`   | Production traffic     | Promotion, or a rollback        |
| `challenger` | Shadow and canary pool | While an experiment is running  |
| `rollback`   | The deployer           | Immediately after a bad promote |

What a registry gives you over an artifact bucket:

| Capability        | Bucket alone | Registry                         |
| :---------------- | :----------- | :------------------------------- |
| Immutable version | Yes          | Yes, plus ordered lineage        |
| Approval workflow | No           | Gate status, tags, audit trail   |
| Deployer contract | Path string  | `models:/name@alias`             |
| Access control    | IAM policy   | Per-model permissions and owners |
| Stage comparison  | Manual       | Side-by-side versions and runs   |

## Reading a comparison honestly

Trackers make two runs easy to place on one chart. That ease is the source of most bad promotion decisions.

- **One seed is noise.** LLM fine-tuning run-to-run spread on a small eval set is routinely a full point. Three seeds, report mean and standard deviation.
- **Best checkpoint on validation is selection bias.** The peak of a noisy curve is biased upward. If you promote on the peak, promote on the same statistic in both arms.
- **Sampling swamps the model.** A generation temperature of 0.7 on a 200-case suite adds variance larger than most adapter differences. Pin decoding parameters in the record and log them.
- **The eval set is an artifact.** If the golden set changed, the runs are not comparable. Version it and put the version in the record.
- **Wall time is not throughput.** A run on an H100 and one on an A100 have different step times for reasons unrelated to the config.
- **Pre-register the decision metric.** Pick the one number that promotes a model before the sweep starts. A tracker with 40 metrics guarantees you find the one where your config wins.

## When not to run a tracker

A tracker is infrastructure, and infrastructure has a bill. Below a team of three, or for a pipeline that runs weekly, a plain-text record beats a server you have to upgrade.

```bash
# a runs.tsv is enough until it is not
printf '%s\t%s\t%s\t%s\n' "$(git rev-parse --short HEAD)" "$SEED" "$LR" "$VAL_METRIC" >> runs.tsv
```

The pieces worth keeping in any setup: the resolved config dumped next to the weights, a content hash for the dataset, a git SHA, the lockfile, and the seed. Those five let you rebuild a model by hand, which is the actual requirement. TensorBoard's `--logdir` covers curves without a server, and an eval platform like Langfuse or Phoenix covers the prompt-and-trace half of the problem.

## Failure modes

| Symptom                                     | Cause                                      | Fix                                                    |
| :------------------------------------------ | :----------------------------------------- | :----------------------------------------------------- |
| Two runs, same config, different results    | Seed or library version not logged         | Log both; pin with a lockfile                          |
| Tracker shows 500 runs, none reproducible   | Code changed without a commit              | CI refuses to run on a dirty tree                      |
| Model in prod matches no version            | Deployed from a local path                 | Serve only from a registry alias                       |
| Dashboard fills up, nobody reads it         | Logged every metric at every step          | Log validation curves sparsely, system metrics in bulk |
| Sweep found a great config, cannot rerun it | Sweep id not recorded with the winner      | Log the sweep and trial id into the model artifact     |
| Artifact storage bill exploded              | Every trial saved full weights             | Save checkpoints only for top-k trials                 |
| Retired dataset version still in new models | Lineage not queried                        | Gate CI on dataset alias allowlists                    |
| Tracker downtime stopped training           | `log` calls on the critical path, blocking | Offline mode, or a spooling writer                     |
| Eval numbers drift with no model change     | Golden set silently edited                 | Make the eval set an immutable artifact                |

## Interview questions

<Accordions>
  <Accordion title="What are the minimum fields in a run record?">

    Resolved config, git SHA, dataset version, metrics, artifacts, environment lockfile, seed, and who ran it. Missing seed or lockfile is what makes a run irreproducible.

  </Accordion>
  <Accordion title="Why log the resolved config rather than a path to a config file?">

    Because environment overrides and defaults merge into the effective config. The file alone can describe two runs that behaved differently.

  </Accordion>
  <Accordion title="What is the difference between an artifact and a registered model?">

    An artifact is an immutable blob with a version. A registered model is a named registry entry with versions, aliases, permissions, and audit metadata that deployers resolve by alias.

  </Accordion>
  <Accordion title="Name the two stores behind an MLflow server and what each holds.">

    The backend store holds run metadata, params and metrics in a database. The artifact store holds blobs like weights and logs in object storage.

  </Accordion>
  <Accordion title="Why did MLflow deprecate registry stages?">

    The fixed four-stage ladder could not express several concurrent deployment targets. Aliases are arbitrary names pointing at one version, and a model can carry several at once.

  </Accordion>
  <Accordion title="How do you record the rollback target?">

    Keep an alias pointing at the previously live version and move it only on promotion, so the deployer always has a named version to switch back to.

  </Accordion>
  <Accordion title="Why does random search beat grid search in high dimensions?">

    Grid at 5 params and 10 values needs 100,000 runs and only samples axis extremes. Random spreads the same budget across all dimensions and locates continuous values to a significant figure, which is all a learning rate needs.

  </Accordion>
  <Accordion title="What does successive halving, as in HyperBand or ASHA, actually do?">

    It runs many configs briefly, kills the worst performers early, and spends the freed budget on the survivors. It pays off when per-trial cost is uncertain and runs are long.

  </Accordion>
  <Accordion title="How do you compute a sweep's GPU-hour cost before starting it?">

    Trials multiplied by GPU count per trial multiplied by wall time per trial. 40 trials, one 8-GPU node, 25 minutes each is about 17 GPU-hours of work and 2.1 hours of reservation.

  </Accordion>
  <Accordion title="How does artifact lineage answer a data-quality incident?">

    Query which runs and models consumed the poisoned dataset version. That is the blast radius, and it comes from `use` edges recorded at training time, not from memory.

  </Accordion>
  <Accordion title="Why is a single-seed comparison on a small eval set unreliable?">

    Run-to-run spread on small suites is often a full point, and generation sampling adds more variance on top. Use three seeds and report mean with standard deviation.

  </Accordion>
  <Accordion title="What breaks the claim that two runs are comparable?">

    A different eval set version, different decoding parameters, or a different GPU class. Pin all three in the record.

  </Accordion>
  <Accordion title="What is the cheapest reproducible setup with no tracker?">

    Config dump, dataset content hash, git SHA, lockfile and seed written next to the weights, plus a `runs.tsv` for the curves. It rebuilds the model by hand, which is the requirement.

  </Accordion>
  <Accordion title="When should tracker logging be off the critical path?">

    On clusters without egress or where a tracker outage would kill a running job. Use offline mode with a later sync, or a spooling writer.

  </Accordion>
  <Accordion title={'Why is "promoted on the peak validation checkpoint" a biased statistic?'}>

    The maximum of a noisy curve is biased upward. If you promote on it, both arms of the comparison must use the same selection rule.

  </Accordion>
</Accordions>
