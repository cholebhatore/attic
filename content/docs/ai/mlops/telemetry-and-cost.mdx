An LLM endpoint is a function whose output quality is not visible in its status code. A request that returns 200 in 400 ms can be wrong, expensive, or unsafe, and none of that shows up in conventional service metrics. Production observability therefore has four axes: quality, latency, cost, and safety, each with its own signals and its own alert thresholds.

The five metric families named in the title cover about 80 percent of what a weekly review needs. Each has a definition precise enough to be worth memorizing, because the sloppy version causes arguments about whether an outage was real.

---

## The plain-language version

**Where this sits:** watching the system once it is live: is it fast, is it affordable, is it still good?

Production telemetry tracks a handful of numbers continuously. **Latency**: time to first token and inter-token latency, especially the slow tail (p95, p99), which is what users complain about. **Cost**: tokens and dollars per request, per user, and per feature. **Cache hit rates**: how often answers or prompt prefixes are reused. **GPU saturation**: whether expensive hardware is busy or idle. And **drift**: whether the inputs or the right answers have shifted since the system was evaluated.

Think of a car's dashboard. Speed, fuel, engine temperature, and warning lights each tell you something different, and a good driver glances at all of them, not just the speedometer.

This page covers, in order:

1. **Latency**: TTFT, ITL, and what users actually feel
2. **Token accounting and spend per user**
3. **Semantic cache hit rate**
4. **GPU saturation**
5. **Data drift and concept drift**
6. **The morning dashboard**: what to check every day
7. **Failure modes**

| Word                  | Plain meaning                                                                       |
| :-------------------- | :---------------------------------------------------------------------------------- |
| **telemetry**         | Measurements sent continuously from a running system.                               |
| **p95 / p99 latency** | The latency that 95% or 99% of requests stay under.                                 |
| **token accounting**  | Counting input and output tokens per request, user, and feature, to attribute cost. |
| **semantic cache**    | Reusing a stored answer when a new query is very similar to a previous one.         |
| **GPU saturation**    | How fully the GPUs are used; low saturation means paying for idle hardware.         |
| **data drift**        | The distribution of inputs changing over time.                                      |
| **concept drift**     | The correct output for the same input changing over time.                           |

## Latency: TTFT, ITL, and what users actually feel

| Metric   | Definition                                                     | Use it for                    |
| :------- | :------------------------------------------------------------- | :---------------------------- |
| TTFT     | Time from request received to the first token emitted          | Streaming UX, perceived speed |
| ITL      | Mean gap between consecutive tokens after the first            | Smoothness of the stream      |
| TPOT     | Same idea, per output token, often measured engine-side        | Decode throughput comparison  |
| E2E      | Time from request received to the final token or full response | SLOs, timeout budgets, cost   |
| Gen-only | `E2E - TTFT`, the pure generation window                       | Isolating decode from prefill |

Inter-token latency is computed per token and averaged, which is why it is normalized by length:

```text
ITL  = (E2E - TTFT) / (output_tokens - 1)
E2E  = TTFT + ITL * (output_tokens - 1)
```

Worked example. A completion with `TTFT = 800 ms`, 240 output tokens, and `E2E = 4400 ms` gives `ITL = 3600 / 239`, about 15 ms per token, which is roughly 66 tokens per second. Quote it as tokens per second when comparing engines and as milliseconds when comparing user experience, since the two framings hide different things.

Why each metric exists separately: TTFT is dominated by queueing plus prefill, both of which scale with prompt length, while ITL is dominated by weight and KV-cache reads per step, which barely depend on the prompt. A single "latency" number averages two mechanisms with different causes, so it moves for reasons you cannot diagnose.

| Symptom               | Cause to check                                           | Lever                                                    |
| :-------------------- | :------------------------------------------------------- | :------------------------------------------------------- |
| TTFT high, ITL normal | Queue depth, long prompt, no prefix cache                | Continuous batching, prompt caching, chunked prefill     |
| TTFT normal, ITL high | Bandwidth-bound decode, oversized batch, no quantization | Quantize, speculative decoding, right-size batch         |
| Both high             | Saturation, preemption, cross-region network             | Scale out, disaggregate prefill and decode               |
| E2E high, both normal | Output length grew                                       | Cap `max_tokens`, shorten the prompt, route harder cases |
| p99 far above p50     | Head-of-line blocking behind a long prefill              | Chunked prefill, separate prefill pool                   |

Percentiles, always. A mean latency of 900 ms can coexist with 8 percent of requests taking nine seconds, and those eight percent are the complaints. p99 is the honest number for streaming UI, and the SLO should read `p95 TTFT < 1.5 s and p95 ITL < 40 ms`, not an average.

<Callout type="info">
  ### Streaming changes what the SLO should measure

For a streamed answer, the user's sense of speed is TTFT plus whether the text keeps moving. A model that starts in 300 ms and trickles at 8 tokens per second feels slower than one that starts in 900 ms and streams at 90, even though the second may finish first. Alert on stalls, not only on averages. A gap above about 100 ms means the stream fell below 10 tokens per second, and that reads as hesitation.

</Callout>

## Token accounting and spend per user

Cost is a two-term sum, and the asymmetry between the terms is the whole game.

```text
cost = in_tokens * p_in + out_tokens * p_out + cached_in_tokens * (p_in * r)
```

`p_out` is several times `p_in` at every frontier vendor, and `r`, the cache-read multiplier, is around a tenth. Those ratios change, so pull them from the pricing page rather than memory, but the shape is stable: output tokens cost more than input tokens, and cached input costs far less than either.

A concrete request at an assumed 1.25 per million input and 5 per million output:

| Line                     | Tokens | Cost       |
| :----------------------- | :----- | :--------- |
| Input, uncached          | 12,000 | 0.0150     |
| Output                   | 600    | 0.0030     |
| **Total per request**    |        | **0.0180** |
| At 50,000 requests a day |        | 900 a day  |
| Monthly                  |        | 27,000     |

Now add a prompt cache covering the 10,000 stable system-and-retrieval tokens at a tenth of the input price. Input becomes `2000 * 1.25 + 10000 * 0.125` per million, or 0.0025 plus 0.00125, and the request drops from 0.0180 to about 0.00675. That is a 62 percent reduction from one structural change, which is where the "cut API spend by 70 percent" number in a design interview comes from.

Slice spend by every dimension that has a budget owner.

| Dimension     | Why it matters                                            |
| :------------ | :-------------------------------------------------------- |
| Per user      | Finds the loop, the scraper, and the power user           |
| Per tenant    | Margin per account, and whether a plan tier is underwater |
| Per feature   | A copilot button can cost more than the whole product     |
| Per model     | Routing drift is invisible at the aggregate level         |
| Per route     | Escalations to the frontier model are the usual leak      |
| Per direction | Input versus output share tells you which lever to pull   |

The recurring cost surprises, in order of how often they show up: conversation history re-sent in full every turn, so spend per turn grows linearly with session length; retrieval returning 20 chunks because nobody capped `top_k`; retries that re-bill a partially streamed generation; judge-based evaluation running continuously on production traffic; an unbounded `max_tokens`; and a router whose classification threshold drifted so everything escalated.

| Control                 | Mechanism                                                          |
| :---------------------- | :----------------------------------------------------------------- |
| Hard cap                | Per-user and per-tenant daily token ceilings, enforced server-side |
| Rate limit              | Requests per minute per key, plus concurrency limits               |
| Budget alarm            | Alert at 50, 80, and 100 percent of the monthly envelope           |
| Anomaly alert           | Yesterday's spend per user, z-score against a 14-day window        |
| Kill switch             | Feature flag that stops a route without a deploy                   |
| Trace-level attribution | Cost written onto every span, so a bad trace is also a bill        |
| Card reporting          | Per-tenant cost exported to the billing system nightly             |

Do not label Prometheus metrics by user id. Per-user spend belongs in a trace store or a warehouse query, because high-cardinality labels will bring down the metrics backend long before they answer a finance question.

## Semantic cache hit rate

A semantic cache answers a new query from a stored response when its embedding is close enough to a previous one.

```text
hit_rate     = hits / (hits + misses)
useful_rate  = hits that were not flagged stale or wrong / hits
coverage     = fraction of live traffic eligible for caching at all
```

| Threshold   | Hit rate | False-hit risk | Typical outcome                  |
| :---------- | :------- | :------------- | :------------------------------- |
| cosine 0.85 | Low      | Negligible     | Only near-paraphrase matches     |
| cosine 0.92 | Medium   | Low            | The usual starting point         |
| cosine 0.96 | High     | Material       | Different questions, same answer |

The hit rate is the number people report and the false-hit rate is the number that matters. At 0.96 the cache answers "what is our refund window" with the stored reply to "what is our warranty window", and a single grader will not notice because both responses read fluently. Track them together, and sample hits for human review at a fixed rate.

Three properties a semantic cache must have to survive production:

| Property           | Without it                                                |
| :----------------- | :-------------------------------------------------------- |
| Tenant namespacing | One customer's answer served to another, a data breach    |
| Version keying     | Answers generated by an old prompt or model never expire  |
| Invalidation hooks | A policy change leaves cached text contradicting the docs |

The key is a composite of tenant, feature, prompt version, model id, and the embedding of the normalized query. The TTL is short for anything derived from mutable state and long for timeless facts. This is why semantic caching on a support copilot works better than on a coding agent: the answer depends on the retrieved documents, and if retrieval is part of the key, the cache becomes a memo of resolved questions rather than a memo of stale facts.

Prompt caching is a different mechanism and the two are frequently confused. Vendor prompt caching reuses prefill work for a shared token prefix, billed at a discount, and requires the stable part of the prompt to come first. A semantic cache skips the call entirely. The arithmetic in the section above is prompt caching. Semantic caching multiplies its effect by the hit rate.

## GPU saturation

`nvidia-smi` utilization is not a saturation measure. It is the percentage of sampled time in which some kernel was executing, with no information about how many streaming multiprocessors that kernel used. A batch of one decode step reads every weight and reports near-100 percent utilization while delivering a few dozen tokens per second.

The DCGM profiling counters tell the truth.

| Metric                  | Source field                      | Meaning                                      |
| :---------------------- | :-------------------------------- | :------------------------------------------- |
| Time-active utilization | `DCGM_FI_DEV_GPU_UTIL`            | A kernel ran during the sample, nothing more |
| Framebuffer used        | `DCGM_FI_DEV_FB_USED`             | Weight plus KV pool plus activations         |
| SM activity             | `DCGM_FI_PROF_SM_ACTIVE`          | Fraction of SMs with any warp resident       |
| Occupancy               | `DCGM_FI_PROF_SM_OCCUPANCY`       | Warps resident relative to the maximum       |
| Tensor pipe active      | `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | Real matmul work, the honest compute proxy   |
| DRAM active             | `DCGM_FI_PROF_DRAM_ACTIVE`        | Bandwidth pressure, the decode bottleneck    |
| Power draw              | `DCGM_FI_DEV_POWER_USAGE`         | Watts against TDP, a cheap sanity signal     |
| NVLink and PCIe bytes   | `DCGM_FI_PROF_NVLINK_TX_BYTES`    | Cross-GPU chatter, KV transfer cost          |
| XID and ECC errors      | `DCGM_FI_DEV_XID_ERRORS`          | Hardware faults before they become outages   |

For an inference service the alerting set is smaller than the metric set.

| Alert                      | Threshold intuition             | Action                                  |
| :------------------------- | :------------------------------ | :-------------------------------------- |
| KV cache block utilization | Sustained above 90 percent      | Batch ceiling reached, scale out        |
| Waiting queue depth        | Growing for more than 2 minutes | Add replicas or shed with 429s          |
| Preempted request rate     | Above zero for long             | Token budget too small, or overloaded   |
| Tensor pipe active         | Below 20 percent at full load   | Bandwidth-bound, quantize or batch more |
| Power draw                 | Flat-lined at TDP               | Thermal, check clocks and airflow       |
| ECC or XID events          | Any                             | Drain the node, open a hardware ticket  |

Engine exporters already expose the derived numbers. In vLLM, `vllm:num_requests_waiting`, `vllm:gpu_cache_usage_perc`, `vllm:time_to_first_token_seconds`, and `vllm:e2e_request_latency_seconds` are the four to alert on, with `vllm:request_prefill_time_seconds` and `vllm:request_decode_time_seconds` for the decomposition. Exact names shift between releases, so re-read the metrics documentation when upgrading rather than trusting a dashboard from six months ago.

Saturation is not goodput. A GPU at full tilt that is spending half its cycles recomputing preempted prefills, or serving batches that are mostly padding, is busy and unproductive. Measure tokens per dollar and per watt against queue depth, and let the curve find the knee.

## Data drift and concept drift

They are different failures with different detection methods, and conflating them wastes the response.

**Data drift** means the input distribution moved. The model is unchanged; the world it is being asked about is not.

| Detector                     | Formula or method                                       | Convention                                       |
| :--------------------------- | :------------------------------------------------------ | :----------------------------------------------- |
| Population stability index   | `psi = sum( (a_i - b_i) * ln(a_i / b_i) )` over bins    | below 0.1 fine, 0.1-0.25 watch, above 0.25 drift |
| Kolmogorov-Smirnov           | Max vertical distance between two CDFs                  | p-value against a reference window               |
| Embedding centroid shift     | Mean cosine between today's and baseline embeddings     | A slow downward trend                            |
| Schema and shape checks      | Field presence, token-length distribution, language mix | Binary, alerts immediately                       |
| Retrieval score distribution | Median top-k similarity                                 | Falls when the corpus changed                    |

**Concept drift** means the input-to-correct-output relationship moved. The question is the same and the answer is no longer. No unsupervised statistic finds this, because there is no label. Detection requires a proxy signal that correlates with being wrong.

| Signal                        | What it catches                                     |
| :---------------------------- | :-------------------------------------------------- |
| Async judge score on a sample | Direct quality estimate, hours to days late         |
| Deflection or adoption rate   | Users stopped believing the answer                  |
| Escalation and edit rate      | The human disagreed enough to intervene             |
| Regeneration and re-ask       | The first attempt failed, unstated                  |
| Periodic human re-review      | Ground truth against a fresh labeled slice          |
| Guardrail hit rate            | Input category shift, or a rail that over-triggered |

The failure mode nobody plans for is drift caused by someone else. A vendor deprecates a model and repoints an alias. An embedding model gets swapped and every similarity threshold silently changes. A policy document is edited and the index rebuilds with different content. Record the identity of every upstream dependency and alert when it changes, which is the cheapest drift detector in this list.

## The morning dashboard

Four rows, in the order a reviewer reads them.

```text
row 1  quality   judge score by route, guardrail hits, escalation rate
row 2  latency   p50/p95/p99 TTFT and ITL, E2E, queue depth
row 3  cost      spend per 1k requests, tokens per request, cache hit rate,
                 top five tenants by spend
row 4  hardware  KV utilization, waiting requests, preempted, tensor pipe, ECC
```

Split SLO-bound numbers from diagnostic ones. An SLO is a target on one metric with a window and an error budget, and the budget is what makes the conversation sane: at 99 percent TTFT compliance over a rolling 30-day window, the allowance is 1 percent of 30 days, about 7 hours of non-compliant five-minute buckets, and burning half of it in a week means stopping feature work until it recovers. Dashboards without budgets become arguments about whether a spike was "really" an incident.

```text
SLO      p95 TTFT < 1.5 s, 99 percent of 5-minute windows, rolling 30 days
alert    burn rate: error budget consumed 2 percent in 1 hour, page
dashboard everything else, reviewed weekly, no pager
```

The pipeline that fills all of this in is the same one that feeds the golden set.

That last edge matters more than the dashboard. Telemetry that only produces charts is a report. Telemetry that produces labeled failures is a training and evaluation input, and it is the loop that makes the next release measurably better.

## Failure modes

| Symptom                                      | Cause                                            | Fix                                                |
| :------------------------------------------- | :----------------------------------------------- | :------------------------------------------------- |
| "GPU is at 100 percent, why is it slow?"     | Utilization is time-active, not occupancy        | Read tensor pipe active and DRAM active            |
| Latency SLO met, complaints rising           | SLO on mean, or on E2E for non-streaming UI      | p95 TTFT and ITL with stall detection              |
| Cost doubles with no traffic change          | History re-send, or router escalation drift      | Per-request token accounting split by direction    |
| Cache hit rate 40 percent, satisfaction down | Threshold too loose, or tenant keys missing      | Tighten cosine, namespace by tenant and version    |
| Judge scores flat, escalations climbing      | Concept drift with no label to see               | Treat escalation rate as a primary quality signal  |
| PSI alarm after every corpus update          | Reference window older than the corpus change    | Re-baseline on purpose, not by accident            |
| Metrics backend falls over                   | User id or prompt text used as a label           | Keep high-cardinality data in the trace store      |
| Alert fires at 3 a.m. for a spike            | Alert on a raw metric instead of burn rate       | Multi-window burn rates, page only on budget speed |
| Dashboards disagree with vendor invoices     | Cost counted at the router, not the API response | Read usage fields off the response body            |
| Regression shipped despite dashboards        | Nothing compared against a baseline window       | Week-over-week series on every quality metric      |

## Interview questions

<Accordions>
  <Accordion title="Define TTFT, ITL, and E2E, and give the relation between them.">

    TTFT is request arrival to first token. ITL is the mean gap between later tokens, `(E2E - TTFT) / (output_tokens - 1)`. E2E is request arrival to final token, so `E2E = TTFT + ITL * (output_tokens - 1)`.

  </Accordion>
  <Accordion title="A completion takes 4.4 s end to end with TTFT 800 ms and 240 output tokens. What is the decode rate?">

    `3600 / 239` is about 15 ms per token, roughly 66 tokens per second.

  </Accordion>
  <Accordion title="Why do TTFT and ITL need separate causes?">

    TTFT is queueing plus prefill, which scales with prompt length. ITL is per-step weight and KV reads, which barely do. A combined latency number mixes two mechanisms with different fixes.

  </Accordion>
  <Accordion title="What does a streaming interface change about the SLO?">

    Perceived speed becomes TTFT plus stream smoothness, so the SLO needs a p95 TTFT, a p95 ITL, and a stall threshold around 100 ms between tokens.

  </Accordion>
  <Accordion title={<>Why is <code>nvidia-smi</code> utilization a misleading saturation signal?</>}>

    It reports the fraction of sampled intervals with any kernel running. A batch-of-one decode reads every weight and shows near 100 percent while producing few tokens.

  </Accordion>
  <Accordion title="Which DCGM counters do you use instead?">

    `DCGM_FI_PROF_SM_ACTIVE`, `SM_OCCUPANCY`, `PIPE_TENSOR_ACTIVE`, and `DRAM_ACTIVE`. Tensor pipe activity is the honest compute proxy; DRAM active is the decode bottleneck.

  </Accordion>
  <Accordion title="What does sustained 90-plus percent KV block utilization tell you?">

    The engine has reached its concurrency ceiling. New requests wait or get preempted, and the fix is more replicas or a lower batch cap, not a faster kernel.

  </Accordion>
  <Accordion title="Write the cost expression for a request that uses prompt caching.">

    `in_tokens * p_in + out_tokens * p_out + cached_in_tokens * p_in * r`, where `r` is the cache-read multiplier, typically around a tenth.

  </Accordion>
  <Accordion title="Input 12,000 tokens at 1.25 per million and output 600 at 5 per million. What is the cost, and at 50,000 requests a day?">

    `0.015 + 0.003 = 0.018` per request, so 900 a day and about 27,000 a month.

  </Accordion>
  <Accordion title="If 10,000 of those input tokens are cache-read at a tenth price, what happens?">

    Input becomes `2000 * 1.25 + 10000 * 0.125` per million, about 0.00375, so the request drops to roughly 0.00675, a 62 percent reduction.

  </Accordion>
  <Accordion title="Name the two most common sources of runaway token spend.">

    Full conversation history re-sent every turn, so per-turn cost grows with session length, and over-retrieval, where `top_k` returns twenty chunks nobody reads.

  </Accordion>
  <Accordion title="Which number does a semantic cache report and which one should you watch?">

    Hit rate gets reported. The false-hit rate is the one that matters, measured by sampling hits and flagging stale or wrong answers.

  </Accordion>
  <Accordion title="Why must a semantic cache key include tenant, prompt version, and model id?">

    Without tenant namespacing you serve one customer's answer to another. Without version keys, text generated by a retired prompt never expires.

  </Accordion>
  <Accordion title="How do prompt caching and semantic caching differ in what they eliminate?">

    Prompt caching removes prefill work for a shared prefix and bills it at a discount. A semantic cache removes the call entirely for a matching query, multiplied by its hit rate.

  </Accordion>
  <Accordion title="Distinguish data drift from concept drift and name a detector for each.">

    Data drift is a shifted input distribution, found with PSI, a KS test, or embedding centroid movement. Concept drift is a changed input-to-answer relationship, found only through labeled proxies such as async judge scores, escalations, or periodic human review.

  </Accordion>
  <Accordion title="What is the standard PSI interpretation and where does it mislead?">

    Below 0.1 is stable, 0.1-0.25 is watch, above 0.25 is significant. It misleads right after a deliberate corpus change, where the baseline needs re-anchoring on purpose.

  </Accordion>
  <Accordion title="What is an error budget and what does it change operationally?">

    A target plus window gives a permitted failure allowance, and burn rate alerts on how fast it is consumed. When half the budget is gone, releases pause, which converts a subjective argument into a number.

  </Accordion>
  <Accordion title="What makes production telemetry compound rather than decorative?">

    The edge from reviewed trace failures into the golden dataset, so monitoring feeds the pull-request gate instead of ending in a chart.

  </Accordion>
</Accordions>
