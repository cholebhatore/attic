When an application line such as `db.users.findUnique(...)` or `SELECT * FROM users` executes, the request traverses seven software and hardware layers before touching physical storage.

## The Seven Architectural Layers

### Layer 1: Application Code

The application layer initiates the action—invoking an ORM method, constructing a query via a query builder, or composing raw SQL text with parameterized values (such as `["user_42"]`).

### Layer 2: Client Driver

The client driver (`pg` in Node.js, `asyncpg` or `psycopg` in Python) bridges programming language data structures and the database network protocol. It serializes primitive types (UUIDs, timestamps, JSON) into binary wire protocol payloads and manages socket write buffers.

### Layer 3: Connection Pool

The pool intercepts the driver's request to borrow an active, pre-authenticated socket. If all pooled sockets are currently servicing other queries, the request waits in an in-memory queue until a connection returns.

### Layer 4: Network Socket

The operating system transmits packets over TCP. If the application and database reside on different cloud servers, packets travel across private VPC subnets. TLS 1.3 encrypts and authenticates every byte in transit.

### Layer 5: Database Server Worker

The database daemon accepts the incoming bytes on port 5432 and assigns the socket to an idle worker process (PostgreSQL) or thread (MySQL). The worker reads the SQL statement from the socket buffer and hands it to the query execution engine.

### Layer 6: Buffer Pool and Storage Engine

The storage engine determines where the requested data resides:

- **Read Path**: The engine checks the **Buffer Pool** in RAM. If the requested 8 KB page is cached, it reads it directly with zero physical disk I/O (a buffer hit). If missing, it issues an asynchronous read syscall (`pread`) to load the page from disk into RAM.
- **Write Path**: The engine writes the mutation into the **WAL Buffer** in RAM, immediately invokes `fsync()` to flush that WAL record to disk sequentially, and marks the page in the Buffer Pool as "dirty".

### Layer 7: OS Kernel and Physical Disk

The operating system filesystem driver (ext4, XFS) and physical NVMe SSD controller receive the flush command. The flash memory controller commits the bits to non-volatile NAND flash cells.

## Write vs Read Path Comparison

| Stage                | Read Query (`SELECT`)                                 | Write Query (`INSERT` / `UPDATE`)                                             |
| :------------------- | :---------------------------------------------------- | :---------------------------------------------------------------------------- |
| **Network**          | Sends SQL; receives data rows                         | Sends SQL + parameters; receives row count                                    |
| **Parsing**          | Checked against table schemas & permissions           | Checked against types & integrity constraints                                 |
| **RAM Cache**        | Scans Buffer Pool for matching data pages             | Mutates target page in Buffer Pool (marks page dirty)                         |
| **Disk I/O**         | Zero I/O on buffer hits; random read on buffer misses | Flushes sequential WAL record via `fsync()`; dirty page written to disk later |
| **Commit Guarantee** | Read completes immediately from snapshot              | Returns success only after WAL reaches durable storage                        |
