Developers often start storing data using the simplest available tool: writing JSON objects to local disk, logging rows to CSV files, editing a spreadsheet, or caching key-value pairs in memory. Each mechanism solves a specific problem, but collapses under multi-user concurrency, structured querying, or scale.

## 1. Raw Filesystems (JSON, CSV, Flat Files)

Writing application data to a `users.json` or `orders.csv` file works during local prototyping, but introduces critical structural flaws as soon as load increases.

### Read and Write Amplification

Updating a single user record inside a 500 MB JSON file requires reading the entire 500 MB file into memory, parsing the JSON string into application objects, mutating the target key, serializing the full object tree back into JSON text, and rewriting all 500 MB back to disk.

```typescript
// Typical flat-file update: O(n) read and O(n) write cost for a single field change
const raw = fs.readFileSync('users.json', 'utf8');
const users = JSON.parse(raw);
users['user_42'].status = 'active';
fs.writeFileSync('users.json', JSON.stringify(users));
```

A database engine avoids this by organizing data into fixed-size disk blocks (typically 4 KB or 8 KB pages). Updating a record requires locating the specific page on disk, modifying only that page in memory, and appending an entry to a write-ahead log.

### Concurrency and File Locking Hazards

If two HTTP requests attempt to modify `users.json` concurrently:

1. Process A reads the file (state `v1`).
2. Process B reads the file (state `v1`).
3. Process A writes user 42 updates (state `v2A`).
4. Process B writes user 99 updates (state `v2B`), completely overwriting and discarding the modifications written by Process A.

Operating system file locks (`flock`) can prevent simultaneous writes, but this serializes the entire application into a single-threaded queue where all requests block waiting for disk I/O.

## 2. Spreadsheets (Excel, Google Sheets)

Spreadsheets provide a visual grid with calculations and cell formatting designed for human analysts.

### Limitations in Production Systems

- **Record volume constraints**: Excel limits worksheets to 1,048,576 rows and 16,384 columns. Exceeding these limits forces file fragmentation.
- **Absence of strict schema enforcement**: A single column can hold an integer in row 10, a date string in row 11, and free-form text in row 12.
- **No row-level transactional isolation**: Multiple automated processes cannot update adjacent rows with ACID guarantees.
- **High latency APIs**: Querying Google Sheets via REST APIs incurs HTTP overhead with strict API rate limits (typically 60 to 100 requests per minute).

---

## 3. In-Memory Key-Value Stores (Redis, Memcached)

In-memory data stores keep their primary dataset in DRAM, delivering sub-millisecond read and write latency.

### The Trade-offs

- **Memory cost**: RAM is 5x to 10x more expensive per gigabyte than NVMe flash storage. Storing terabytes of historical transactional records in RAM is cost-prohibitive.
- **Query flexibility**: In-memory key-value stores prioritize lookups by explicit key (`GET user:42`). Complex relational queries requiring arbitrary filters, multi-table joins, or window functions require loading datasets into application memory and computing manually.
- **Durability configuration**: In-memory stores provide persistence options (such as Redis RDB snapshots or AOF logs), but default configurations trade durability for throughput. Flushing every write with `fsync` reduces memory throughput to disk throughput.

## Comparative Matrix

| Feature                   | Flat Files (JSON / CSV)   | Spreadsheets                 | In-Memory Stores (Redis)      | Relational Database (PostgreSQL)   |
| :------------------------ | :------------------------ | :--------------------------- | :---------------------------- | :--------------------------------- |
| **Primary Storage Media** | Disk                      | Cloud / Disk                 | RAM (with optional disk logs) | Disk (with RAM buffer cache)       |
| **Typical Read Latency**  | `10 – 500 ms`             | `50 – 1,000 ms`              | `< 1 ms`                      | `1 – 15 ms`                        |
| **Write Concurrency**     | Poor (file-level lock)    | Poor (cell/sheet conflicts)  | Single-threaded atomic ops    | High (row-level locks, MVCC)       |
| **Data Integrity**        | App-level only            | Loose cell types             | Basic key-value constraints   | Strict types, Foreign Keys, Checks |
| **Query Mechanism**       | Full scan in memory       | Visual filters, VLOOKUP      | Key lookup, specific commands | SQL (indexes, joins, aggregations) |
| **Durability**            | Vulnerable to torn writes | Dependent on cloud auto-save | Configurable (AOF, snapshot)  | ACID guaranteed via WAL            |

<Callout type="info">
  Modern architectures combine these tools instead of picking one exclusively: PostgreSQL serves as
  the persistent transactional system of record, Redis caches hot read-heavy sessions, and flat
  files store immutable export artifacts.
</Callout>
