When data volume grows from ten thousand rows to ten million rows, reading raw files sequentially requires hundreds of seconds of disk I/O. A database solves this through declarative query languages and indexed storage structures.

---

## Declarative vs Imperative Querying

In traditional programming languages, querying flat files requires writing **imperative** procedural loops:

```typescript
// Imperative: The programmer specifies HOW to loop, filter, and allocate
const matchingUsers = [];
for (const user of fileRecords) {
  if (user.country === 'CA' && user.age >= 21) {
    matchingUsers.push({ id: user.id, email: user.email });
    if (matchingUsers.length === 50) break;
  }
}
```

In a database, the developer writes a **declarative** SQL query specifying **what** data is needed:

```sql
SELECT id, email
FROM users
WHERE country = 'CA' AND age >= 21
LIMIT 50;
```

The database query optimizer analyzes this request, checks available statistics and index paths, and chooses the most efficient physical execution strategy:

- Scanning an index on `(country, age)`
- Reading only the matching 50 index pointers
- Fetching only those specific 8 KB data pages from disk or buffer memory

## Sequential Scan vs Indexed Lookup

Without an index, the database engine executes a **Sequential Scan** (Table Scan), checking every row from the first disk page to the last.

| Metrics              | Sequential Scan (`O(n)`)              | B-Tree Index Lookup (`O(log n)`)   |
| :------------------- | :------------------------------------ | :--------------------------------- |
| **10,000 Rows**      | `~10,000` rows examined               | `3 – 4` page reads                 |
| **1,000,000 Rows**   | `~1,000,000` rows examined            | `4 – 5` page reads                 |
| **100,000,000 Rows** | `~100,000,000` rows examined          | `5 – 6` page reads                 |
| **Disk I/O Cost**    | Reads entire multi-GB table from disk | Reads a few 8 KB pages into memory |
| **Execution Time**   | Seconds to minutes                    | `0.1 – 2 milliseconds`             |

## How Indexes Work Behind the Scenes

An index is an auxiliary data structure on disk that holds a sorted copy of specific columns paired with physical row pointers (Tuple IDs / CTIDs).

```sql
-- Creating an index on the email column
CREATE INDEX idx_users_email ON users (email);
```

1. The database creates a balanced tree (B-Tree) sorted alphabetically by `email`.
2. Each leaf entry holds the string value and a pointer in the format `(Page Number, Item Offset)`.
3. When searching for `WHERE email = 'sarah@example.com'`, the engine navigates the tree from root to leaf in `3` page lookups.
4. It extracts the pointer `(Block 812, Offset 4)` and reads only that single 8 KB block from disk into memory.

## Datasets Exceeding Physical RAM

A common myth is that database servers hold entire databases in RAM. Production systems routinely store 2 TB of data on servers with only 64 GB of RAM.

A database manages this seamlessly through **buffer pooling** and **paged I/O**:

- Tables are partitioned into fixed-size disk pages (8 KB in PostgreSQL, 16 KB in MySQL InnoDB).
- The engine loads pages into the RAM buffer pool on demand.
- When RAM is full, the engine applies an eviction policy (such as Clock-Sweep or Least Recently Used) to write dirty pages to disk and swap fresh pages into memory.
- Queries that retrieve small, indexed subsets run at memory speed even when the total dataset is 30 times larger than available RAM.

<Callout type="info">
  Indexes are not free. Every `INSERT`, `UPDATE`, or `DELETE` statement must update the base table
  and each secondary index defined on that table. Balance query performance with write overhead.
</Callout>
